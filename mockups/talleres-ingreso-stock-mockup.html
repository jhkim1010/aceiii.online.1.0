Corte → etapas → Recepción final → Stock

제안한 작업이 화면에서 어떻게 보이는지에 대한 mockup입니다. 데이터는 운영 DB 실측값(LOT-2026-003 / LOT-2026-005, store 6)이고 SKU·공정 경로·지점명 모두 실제입니다. 변형별 수량을 받는 곳은 두 곳뿐입니다 — corte(실제 재단량, 재고 영향 없음)와 última etapa(실제 입고량, 재고 기록). 중간 공정은 총량만 다룹니다.

흐름

양 끝 두 곳에서만 색×사이즈를 다룹니다. 그래야 차이가 “재단 차이”와 “공정 손실”로 갈립니다.

Cut ticket Matriz de plan 색×사이즈 계획. cutDate 찍히면 잠김.
Etapa 1 · corte Cantidades cortadas 색×사이즈 실제 재단량. 재고 영향 없음 — 기준선일 뿐.

설계 노트
  • 왜 corte 를 추가했나 — 매트릭스는 cutDate 가 찍히는 순간 잠깁니다(lote.service.ts:1244 INV-C, 재설정도 INV-D). 즉 매트릭스는 재단 계획이고 실제 재단량은 지금 어디에도 기록되지 않습니다. 원단이 모자라 한 색을 덜 재단하면 그 차이는 1번 공정에서 이미 생기는데, 지금 설계로는 마지막에 가서야 뭉뚱그려 알게 됩니다.
  • 운영 로트 5건 전부 routing 1번이 corte 이고, 로트 10은 실제로 envío #1 → recepción #1 을 거쳤습니다. 새 공정을 만드는 게 아니라 이미 있는 단계에 입력을 붙이는 것입니다.
  • corte 항목은 같은 talleres_recepcion_items 에 담고 헤더를 inventory_status = NOT_APPLICABLE 로 둡니다 — 재고에 영향 없이 변형별 수량만 남습니다. 새 테이블이 늘지 않습니다. stock_id 는 corte 항목에서 항상 null.
  • 최종 공정 판정은 MAX(order) 를 찾는 게 아닙니다. buildRoutingPath(lote.service.ts:1180)가 order 를 1..N 으로 재정규화하므로 스냅샷 안에서는 동점이 생기지 않습니다. 규칙: canonical 검증(비어 있지 않음 · order 가 정확히 1..N · etapaId 중복 없음) → 통과하면 배열의 마지막 원소가 최종. 검증에 걸리면 자동 입고를 하지 않고 관리자 확인을 요구합니다.
  • ★ 마스터 데이터 문제는 따로 있습니다 — talleres_etapas(store 6)에 order 5 가 둘입니다(costurero id 6, planchero id 5). 공정을 명시 지정하지 않고 만든 로트는 order 동점을 id 순으로 깨므로 planchero 가 앞서고 costurero 가 최종이 됩니다 — 업무상 뒤바뀐 순서입니다. 현재 5개 로트는 전부 명시 지정이라 영향이 없지만 마스터 order 는 고쳐야 합니다.
  • ★ 재작업(rework) 중복 입고 방어가 필요합니다. talleres_envios 에 reworkOrderId / sourceRecepcionId 가 이미 있습니다(envio.model.ts:71,99). 최종 공정에서 불량 처리된 옷이 재작업 후 다시 최종 수령으로 들어오면 “최종 etapa 수령이면 자동 입고”만 보고 같은 옷을 두 번 입고합니다. 재작업 수령은 원 수령의 불량분을 대체하는 흐름으로 따로 판정해야 합니다.

설계 노트 — 왜 이렇게 했는가
  • 기준선이 cortado 입니다. 실제로 존재하는 물건이 496장이지 500장이 아니기 때문입니다. plan 은 우측 합계 열과 요약 바에만 남겨 비교는 가능하게 하되, 셀은 가볍게 유지했습니다.
  • ★ 변형별 상한을 강제하면 안 됩니다. 이 예시가 그 이유입니다 — CARAMELO XL 은 91 + 5 = 96 < 100, CAMELEÓN L 은 4 > 0. 셀 단위로는 안 맞는데 총합은 496 으로 정확히 맞습니다. 공정 중 색상 혼입은 현장에서 실제로 일어납니다. 셀 단위는 경고, 총합 초과(recibido + rechazado > cortado)만 관리자 확인을 요구합니다.
  • 계획 밖 조합도 입력 가능합니다(파란색). 막으면 사용자가 엉뚱한 칸에 몰아넣습니다. 단, 대응 변형이 없는 조합은 저장을 거부합니다(현행 skipped > 0 → rollback 유지).
  • 하단은 저장 전 미리보기입니다 — 몇 개의 원장 행이 어느 지점에 생기는지 숫자로 먼저 보여줍니다. 재고를 건드리는 버튼은 누르기 전에 결과가 보여야 합니다.
  • Rechazado 는 재고에 들어가지 않습니다. 불량 창고는 만들지 않고 기존 QC/rework 흐름을 씁니다.
  • 기준선 출처를 헤더에 표시합니다 — Referencia: corte real / Referencia: plan. 조용히 바뀌면 사용자는 무엇과 비교하는지 모릅니다. corte 수령 일부에만 변형 항목이 있는 부분 기준선은 corte 기준으로 쓰지 않고 plan 으로 폴백합니다.
  • cortado 는 corte 수령의 양품(received)만 누적합니다 — 불량(rejected)은 기준선에 넣지 않습니다.
  • 헤더 합계와 항목 합계는 같은 트랜잭션에서 일치를 강제합니다(SUM(items.received) = header.received). 안 그러면 envio.pending_quantity 는 헤더로, 재고·기준선은 항목으로 움직여 갈라집니다.
  • 부분 수령은 수령할 때마다 그만큼 즉시 입고합니다. 전량 도착까지 기다리면 창고에 실물이 있는데 재고에 없는 지금 문제를 축소해서 반복하게 됩니다.
