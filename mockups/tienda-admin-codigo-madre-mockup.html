부분 실패 — 성공한 것과 실패한 것을 따로 말한다
설계 노트 — 이 화면이 지키는 세 가지
  • 손댄 것만 보낸다. 가격 저장은 부모+자식 전부를 한 값으로 덮습니다. 안 만진 가격유형까지 요청에 넣으면 기존 차등가가 조용히 사라집니다 — 그래서 값이 바뀐 유형만 payload 에 들어갑니다.
  • 갈려 있으면 미리 말한다. 부모와 자식(또는 자식끼리) 금액이 다른 가격유형은 입력칸 아래에 범위($최소 – $최대)와 함께 경고를 띄우고, 확인창에도 ⚠ unifica todas las variantes 로 다시 표시합니다. 저장하면 그 차이는 되돌릴 수 없습니다. 로컬 실측으로 부모×가격유형 77개 조합 중 10개가 실제로 갈려 있었습니다 — 드문 예외가 아닙니다.
  • 부분 실패를 숨기지 않는다. 세 엔드포인트는 권한 가드가 서로 다릅니다. 하나가 403 이어도 앞의 것은 이미 커밋됐고, 보상 요청도 같은 이유로 실패할 수 있어 롤백하지 않습니다. 대신 Guardado: Nombre, Tienda Web. / Precios: sin permiso (403) 처럼 항목별로 밝히고 목록을 재조회합니다.
  • 이름은 서버가 대문자로 정규화합니다(updateProducts). 미리 알려주지 않으면 "내가 쓴 대로 저장이 안 됐다"는 문의가 옵니다 → 입력칸 아래 Se guarda en MAYÚSCULAS.

가격유형GET /price-typesadmin/gerente/vendedor status=1 만. 이름에 PRECIO 가 든 것이 base → 맨 앞에 정렬(웹 levels 규칙과 동일)
이름 수정PUT /products/:ideditar-un-producto 서버가 name 을 대문자로 정규화
가격 수정POST /products/bulk-update-pricescambiar-precio-individual [{ productId, prices:[{priceTypeId, newAmount}] }] — 부모면 부모 + 자식 전부 upsert, base 유형이면 products.price 도 동기화
공개몰 게시PUT /products/publish-shoppublicar-o-no-publicar-producto { productIds:[id], published } — 일괄 토글이라 단건도 배열
가격 라우트를 왜 이것으로 골랐나
  • bulk-update-explicit 은 대상이 부모면 자식만 고치고 부모 자신의 prices 행과 price 는 건드리지 않습니다 → 화면을 다시 열면 옛 값이 보입니다.
  • PUT /prices/:id 는 그 행 하나만 바꿉니다 → 정작 POS 가 파는 자식 가격이 안 바뀝니다. 없는 가격 행을 만들지도 못합니다.
  • 웹 CodigoVistaView 도 bulk-update-prices 를 씁니다 — 두 화면이 갈라지지 않게 맞춰 뒀습니다.
