# 타임 캡슐 — 부분 복구 설계 조사

2026-08-21 · 사용자 제안("퍼미션·SKU 상태만 보존했다가 되돌린다")에 대한 조사와 설계안.
근거는 **운영 DB 실측 · 기존 시스템(ACE) 실측 · 업계 사례** 순으로 붙였다.

---

## 1. 요건이 W6 의 전제를 바꾼다

W6 SPEC 은 "매장 전체 논리 복구" 였다. 그런데 실제 요구는 다르다:

> 고객이 "일주일 전으로 돌려달라" 고 할 때 **판매나 모든 상태를 지우라는 말이 아니다.**
> **SKU 상태(가격을 비롯한 속성)만** 돌려달라는 말이다.

★ 이 한 문장이 설계를 통째로 바꾼다:

| | 전체 복구(종전 가정) | 타임 캡슐(실제 요건) |
|---|---|---|
| `sales` | 지운다 | **건드리지 않는다** |
| `stocks` 원장 | 되돌려야 한다 → **`trg_stocks_immutable` 과 충돌** | **건드리지 않는다** |
| 위험 | 되돌릴 수 없다 | 되돌릴 수 있다(캡슐이 또 남으므로) |
| 막혀 있던 판단 | "보정 행이냐 유지보수 DELETE 냐" 는 **회계 결정** | **필요 없어진다** |

★ 즉 내가 "사용자 판단이 필요하다" 고 세워 뒀던 그 결정은 **잘못된 요건 위의 질문**이었다.
요건을 좁히니 질문 자체가 사라진다.

## 2. 기존 시스템(ACE)이 실제로 한 것 — 개념은 옳았고 저장이 비쌌다

Phase 86 조사에서 `codigos_tmp` 를 실측해 뒀다:

| | 값 |
|---|---|
| 행 수 | **3,105,051** |
| 내용 | 코드 2,552개 × **1,691회 반복** (2023-12-05 ~ 2026-08-12) |
| 성격 | **일별 가격 스냅샷 로그** |
| 압축 해제 크기 | **244MB** — 한 매장 백업 용량의 대부분 |

★ **안 바뀐 날에도 매일 전 품목을 다시 적었다.** 그래서 Phase 86 은 이 테이블을
가져오지 않기로 확정했다(§2.3 F1). 개념(되돌릴 수 있게 상태를 남긴다)은 맞았지만
**저장 방식이 규모를 못 견뎠다.**

### 변경분만 적으면 얼마나 싼가 — Ventago 실측

| 방식 | 60일치 행 수 |
|---|---|
| 일별 전체 스냅샷 (ACE 방식) | `prices` 769행 × 60일 = **46,140** |
| 변경분만 (delta) | **530** |

**87배 차이.** 그리고 변경은 몰려서 일어난다 — 하루 153건인 날이 있고 대부분의 날은 0이다
(`prices` 769행 중 **726행은 생성 이후 한 번도 안 바뀌었다**). 스냅샷 방식은 그
"아무 일도 없었음" 을 매일 769행으로 적는다.

## 3. 이미 있는 것으로는 안 된다 — `audit_logs` 실측

`audit_logs` 는 구조가 훌륭하다: `entity_type · entity_id · action · old_values ·
new_values · user_id · store_id · created_at`. 변경 로그에 필요한 것이 다 있다.

**그런데 데이터가 없다:**

| | 실측 |
|---|---|
| 전체 | 890행 |
| `new_values` 있음 | 882 |
| **`old_values` 있음** | **7** |
| 그 7건의 정체 | **전부 `talleres_lote`** — 오직 한 모듈만 이전 상태를 남긴다 |
| 가격 변경 | **entity_type 목록에 아예 없다** (`priceType` 은 있지만 실제 가격이 아니다) |
| 일관성 | `Producto` 와 `producto` 가 **둘 다** 존재 |

★ **"무엇이 되었는지" 는 적고 "무엇이었는지" 는 안 적는다.** 되돌리기에 필요한 것은
후자인데 그게 없다. 구조가 있다고 기능이 있는 것이 아니다 —
이 저장소의 `@Audit` 데코레이터는 이미 같은 형태로 한 번 문제가 됐다.

**결론: 타임 캡슐은 자기 자신의 기록을 가져야 한다.** `audit_logs` 위에 세울 수 없다.

## 4. 업계는 어떻게 하는가

### Shopify — 네이티브 undo 가 **없다**
대량 편집을 되돌리려면 다시 대량 편집하거나 **내보낸 CSV 를 덮어쓰기로 재수입**해야 한다.
즉 "그날의 카탈로그 스냅샷" 이 유일한 복구 수단이다. (ACE 의 `codigos_tmp` 와 같은 발상)

### 서드파티 앱이 채우는 두 가지 형태

| 형태 | 예 | 방식 |
|---|---|---|
| **연속 이력** | Restory | 설치 시 **전체 기준선 스냅샷** + 그 이후 **모든 변경을 자동 기록**(가격·제목·설명·이미지·variant·SEO·태그·상태) → 임의 시점 복원 |
| **작업 단위 스냅샷** | Bulk Discount Price Pro · Revnous · Edify | 위험한 대량 작업 **직전에 스냅샷** → 그 작업만 1클릭 롤백. 세일 종료 시 자동 원복 |

★ **정확히 사용자가 말한 "타임 캡슐" 이 업계 표준 형태다.** 그리고 두 형태 중
Restory 가 쓰는 **"기준선 + 변경분"** 이 §2 의 87배 계산과 맞는다.

★ 작업 단위 스냅샷도 따로 값어치가 있다 — "가격 일괄 수정" 처럼 **한 번에 크게 바뀌는
경로**는 그 자리에서 캡슐을 뜨는 것이 사후에 시점을 찾는 것보다 훨씬 쓰기 쉽다.

## 5. 설계안

### 5.1 캡슐이 담는 것 (도메인 단위)

| 도메인 | 테이블 | 왜 |
|---|---|---|
| **SKU / 카탈로그** | `products` · `ProductBranch` · `prices` · `product_promotions` · `product_visibility` | 사용자가 지목한 것 |
| **퍼미션** | `roles` · `role_functions` · `user_functions` | 사용자가 지목한 것. `role_functions` 만 11,790행 |

**담지 않는 것**: `sales` · `stocks` · `stock_balances` · 현금/정산.
되돌리기 대상이 아니라 **사실의 기록**이다.

### 5.2 기록 방식 — 기준선 + 변경분

- 도메인별 **기준선 1회** + 이후 **변경분만** 적는다(87배 근거).
- 보존 기간은 기존 시스템과 같은 **2개월**부터 시작한다(그쪽이 실제로 쓰던 값).

### 5.3 ★ 기록 지점은 **DB 트리거**여야 한다 (애플리케이션이 아니라)

이 저장소가 반복해서 당한 형태가 근거다:

- `audit_logs` 의 `old_values` 가 890건 중 7건 — **애플리케이션 계층 기록은 실제로 안 남았다**
- 이 저장소에는 "쓰기 경로가 여럿" 인 사례가 계속 나왔다 —
  원장 쓰기가 주입 모델 뒤에 숨어 8개 파일을 놓치고, 수령을 만드는 경로가 셋이고,
  부모 가격 저장 경로가 셋인데 하나만 자식을 갱신했다.
- 그때마다 **한 곳만 고쳐 나머지가 조용히 빠졌다.**

트리거는 **경로가 몇 개든 상관없이** 한 곳에서 잡는다. Phase 85 가 W4·W8·W6-A 에서
쓴 것과 같은 논지다: **차이는 성실함이 아니라 강제 지점의 유무다.**

### 5.4 되돌리기 의미 — ★ 여기 결정이 하나 있다

시점 T 로 되돌릴 때 **T 이후에 새로 생긴 SKU** 를 어떻게 하는가:

| | 처리 | 문제 |
|---|---|---|
| (가) | 속성만 되돌리고 **행은 그대로 둔다** | 새 SKU 는 남는다. 하지만 그 사이 **팔렸을 수 있고**, `sale_items.product_id` FK 가 그 행을 붙잡고 있다 |
| (나) | T 이후 생긴 SKU 를 **지운다** | 팔린 상품이면 FK 위반으로 실패하거나, 판매 이력이 깨진다 |

★ **(가)를 권한다.** 판매는 되돌리지 않기로 한 이상, 팔린 상품을 지우는 것은
그 결정과 모순된다. "되돌린다" 는 **상태를 되돌리는 것**이지 존재를 지우는 것이 아니다.
다만 되돌리기 결과 화면에 **"T 이후 생긴 SKU N개는 그대로 뒀다"** 를 반드시 보여줘야 한다 —
안 보이면 사용자는 전부 되돌아간 줄 안다.

### 5.5 안전장치

- **되돌리기 자체가 캡슐을 남긴다** → 되돌리기를 되돌릴 수 있다
- 미리보기 필수: "무엇이 몇 건 바뀌는가" 를 먼저 보여주고 확인받는다
- 트랜잭션은 배치 INSERT/UPDATE 만 감싼다(`statement_timeout=30s` 고려)

# 7. 요건 변경 — "가격·퍼미션 변경은 **반드시 `audit_logs` 에 존재해야 한다**"

사용자 지시(2026-08-21). 따라서 §3 에서 찾은 감사 누락은 **우회 대상이 아니라 고칠 결함**이다.
타임 캡슐과 감사는 갈라지지 않는다 — **같은 기록을 쓰고 용도만 둘**이다.

## 7.1 근본 원인 (코드에서 확인)

`src/common/interceptors/audit.interceptor.ts:81`

```ts
oldValues: auditOptions.action === 'edit' ? body.oldValues : undefined,
```

★ **이전 상태를 DB 에서 읽지 않고 요청 본문에서 받는다.**
- 클라이언트가 `oldValues` 를 보내야만 남는다 → 아무도 안 보내서 **890건 중 7건**
- 게다가 **값을 클라이언트가 정한다** → 감사 기록으로서 신뢰할 수 없다.
  "무엇이었는지" 를 바뀐 당사자에게 물어보는 구조다.

## 7.2 제약 (전부 실측)

| 제약 | 값 | 왜 걸리는가 |
|---|---|---|
| `audit_logs.user_id` | **NOT NULL + FK → users(id)** | 트리거가 남기려면 행위자가 반드시 있어야 한다. 크론·마이그레이션·직접 SQL 은 행위자가 없다 |
| pgbouncer | `pool_mode = transaction` | `SET LOCAL` 은 **같은 트랜잭션 안**에서만 유효하다. 요청 시작 시 한 번 걸어두는 방식이 통하지 않는다 |
| 가격 쓰기 경로 | `productsPrice.service.ts` 3개(`bulkUpdateBaseAndTypes`·`bulkUpdateExplicit`·`bulkUpdatePrices`) + `product-visibility.service.ts` | 앱 계층으로 하면 경로마다 배선해야 한다 |
| 마이그레이션 규약(W4) | 기존 테이블 ALTER 는 `lock_timeout` 필수, CHECK 는 `NOT VALID`, 인덱스는 `CONCURRENTLY` | spec 이 강제한다 |
| 검증 환경 | 로컬 ventago **0 테이블**. 스테이징 `ventago_staging`(6432) | 로컬 테스트 불가 → 스테이징에서 검증 |

## 7.3 설계 선택지

### (A) 애플리케이션 계층을 제대로 고친다
서비스가 **DB 에서 이전 상태를 읽어** 감사에 넘긴다(요청 본문 신뢰 폐기).

- ✔ 행위자·IP·UA 를 정확히 안다. 스키마 변경 없음
- ✘ **경로마다 배선한다.** 나중에 다섯 번째 경로가 생기면 조용히 빠진다 —
  이 저장소가 반복해서 당한 형태다(원장 쓰기 8개 파일 누락 · 수령 경로 셋 · 부모 가격 경로 셋)

### (B) DB 트리거가 남긴다 ← **권장**
`prices` · `role_functions` · `user_functions` 에 트리거. `OLD`/`NEW` 를 그대로 jsonb 로.

- ✔ **경로가 몇 개든 한 곳에서 잡는다.** 새 경로가 생겨도 자동으로 남는다
- ✔ 이전 상태가 **DB 가 아는 진짜 값**이다 — 클라이언트가 못 속인다
- ✘ 행위자를 모른다 → 세션 GUC 로 전달해야 한다
  (`ventago.actor_user_id`. 이 저장소에 이미 `ventago.allow_madre_stock` ·
  `ventago.stocks_maintenance` 전례가 있다)
- ✘ `user_id NOT NULL` 과 충돌 → **NULL 허용이 필요하다**

### ★ `user_id` 를 어떻게 할 것인가 — 이 저장소의 원칙이 답을 준다

> **"근거 없는 귀속은 '모른다' 보다 나쁘다 — 틀린 지목 한 번이 정산 사고다."**

따라서 **아무 사용자로 채우지 않는다.** `user_id` 를 nullable 로 바꾸고
**NULL = 시스템/미귀속**으로 읽는다. 대안 둘은 모두 나쁘다:
- 감사 실패 시 가격 변경을 막는다 → **감사 때문에 POS 가 멈춘다**
- 아무 사용자(예: 관리자)로 귀속한다 → **하지 않은 일을 한 것으로 기록한다**

### ★ 성질이 좋은 점: 실패가 우아하게 무너진다
GUC 를 거는 것을 잊으면 **행위자만 NULL 이 되고 기록 자체는 남는다.**
"조용히 아무것도 안 남는" 지금과 정반대다.

## 7.4 권장안 = (B) + (A)의 배선

1. 마이그레이션 — `audit_logs.user_id` **DROP NOT NULL** (`lock_timeout` 포함, 메타데이터 변경이라 재작성 없음)
2. 공용 트리거 함수 `audit_row_change()` → **아래 대상 전부**에 부착

   ★ **정정 (codex 지적 P1 2건, 2026-08-21).** 처음 목록은 `prices` ·
   `role_functions` · `user_functions` 셋뿐이었다. **두 군데가 틀렸다:**

   | # | 무엇이 틀렸나 |
   |---|---|
   | P1-1 | **내 문서 안에서의 자기모순** — §5.1 은 복구 대상에 `products` · `ProductBranch` · `product_promotions` · `product_visibility` 를 넣어 놓고 §7.4 트리거 목록에서 뺐다. 그대로 만들면 **상품명·상태·노출·프로모션 변경이 기록되지 않아** 시점 복구를 재구성할 수 없다 |
   | P1-2 | **권한의 실제 소재를 놓쳤다** — 판정은 `role_functions × role_function_actions` 를 조인한다(`permission-resolver.service.ts`). 실측: `role_functions` 11,790행인데 **`role_function_actions` 는 36,396행**. CRUD 권한은 그쪽에 있다. 부모만 감사하면 **"읽기만" 을 "삭제 가능" 으로 바꿔도 아무 기록이 안 남는다** |

   **최종 대상**

   | 도메인 | 테이블 |
   |---|---|
   | SKU / 카탈로그 | `products` · `ProductBranch` · `prices` · `product_promotions` · `product_visibility` |
   | 퍼미션 | `roles` · `role_functions` · **`role_function_actions`** · `user_functions` · **`user_function_actions`** |

   `user_functions` / `user_function_actions` 는 지금 **0행**이지만 목록에 넣는다 —
   쓰이기 시작하는 날 조용히 빠지는 것이 이 Phase 가 계속 잡아 온 실패 양식이다.
3. 행위자는 `current_setting('ventago.actor_user_id', true)` 에서 읽는다
4. 가격·퍼미션 쓰기 경로가 트랜잭션 시작 시 `SET LOCAL ventago.actor_user_id` 를 건다
   (pgbouncer transaction pooling 때문에 **같은 트랜잭션 안**이어야 한다)
5. spec 으로 강제 — 트리거가 붙어야 할 테이블 목록을 선언하고, 빠지면 빌드를 깨뜨린다
   (W6-A 와 같은 형태). ★ **이번 P1 2건이 정확히 그 spec 이 잡았어야 할 부류다** —
   "복구 대상으로 선언한 테이블" 과 "트리거가 붙은 테이블" 이 갈라진 것이고,
   사람이 목록 두 개를 손으로 맞추면 반드시 갈라진다. 두 목록을 **한 곳에서** 만든다.

## 7.5 codex 에 묻는 것

1. **(B) 트리거가 맞는가?** 가격 변경은 대량 편집이 하루 153행까지 간다(실측).
   행 단위 트리거가 `audit_logs` 에 같은 수의 INSERT 를 만든다 — 그 비용과 잠금은?
2. **`user_id` NULL 허용**이 옳은 판단인가? 감사 기록의 무결성 관점에서
   "미귀속 기록을 남긴다" vs "기록을 못 남기면 쓰기를 막는다" 중 무엇이 맞는가?
3. `SET LOCAL` + pgbouncer transaction pooling 조합에서 **놓치기 쉬운 함정**은?
   특히 트랜잭션 없이 실행되는 Sequelize 단문(autocommit)은 어떻게 되는가?
4. `OLD`/`NEW` 를 통째로 jsonb 로 남기면 **가격표에 민감 정보가 섞일 여지**는 없는가?
   (W6-A 에서 백업이 자격증명을 싣던 것과 같은 부류의 실수를 반복하고 싶지 않다)
5. 되돌리기(타임 캡슐)를 **감사 로그에서 재구성**하는 것이 맞는가, 아니면 감사와 별개로
   복원 전용 저장소를 두는 것이 맞는가? 하나로 합치면 어떤 결합이 생기는가?

# 8. 레거시 실물 해부 — `evase_20260821_160408.backup` (2026-08-21)

사용자가 지목한 백업(29MB, PGDMP)을 Phase 86 리더로 직접 열었다.
**추정이 아니라 실물이다.** §2 의 kandente4 통계보다 훨씬 많은 것을 말해 준다.

## 8.1 레거시는 테이블 **셋**으로 이 기능을 했다

| 테이블 | 행 | 역할 |
|---|---|---|
| `codigos` | 2,139 | **현재 상태.** `utime` · `utime_modificado` · `borrado`(소프트삭제) 보유 |
| `codigos_tmp` | 60,136 | **매일 아침 전 품목 스냅샷** |
| `codigos_recover` | 0 | **복구 스테이징** — 적용 직전에 담는 그릇 |

```sql
CREATE TABLE codigos_tmp (              CREATE TABLE codigos_recover (
  id_codigo_tmp integer,                  id_codigo_recover integer,
  codigo varchar(30),                     codigo varchar(50),
  descripcion varchar(300),               pre1..pre5 double precision,
  pre1..pre5 double precision,            fecha_recover varchar(50),
  preorg double precision,                ref_id_codigo integer,
  fecha varchar(30),  hora varchar(30),   ref_id_todocodigo integer,
  ref_id_codigo integer,                  b_is_todocodigo boolean,
  b_is_todocodigo boolean );              utime timestamp default now() );
```

★ **`codigos_recover` 에는 `descripcion` 이 없다 — 가격(`pre1..pre5`)뿐이다.**
즉 실제로 되돌린 것은 "SKU 상태" 가 아니라 **가격**이었다. 요구를 정확히 좁혀 준다.

★ **복구를 곧바로 적용하지 않고 스테이징 테이블을 거쳤다.** 이것은 §5.5 에서 내가
"미리보기 필수" 라고 쓴 것과 같은 판단이고, **실제 운영에서 그렇게 했다는 증거**다.

## 8.2 캡처 방식 — 매일 아침 크론이 전부 다시 적었다 (실측)

| | |
|---|---|
| 기간 | 2026-07-21 ~ 2026-08-21 (**27일**) |
| 서로 다른 `(fecha, hora)` 이벤트 | **27** — 하루 정확히 한 번 |
| 이벤트 시각 | 매일 **07:54 ~ 08:02** (아침 크론) |
| 이벤트당 행 수 | 2,192 ~ 2,337 (**전 품목**) |

## 8.3 ★★ 그 스냅샷 중 실제로 바뀐 것은 얼마인가 — **그들 자신의 데이터로 계산**

| 방식 | 27일치 행 수 |
|---|---|
| 스냅샷 (실제로 한 것) | **60,134** |
| 변경분만 | **2,730** = 기준선 2,337 + 값변경 **36** + 추가 112 + 삭제 245 |
| **절감** | **22배** |

★★ **한 달 동안 값이 실제로 바뀐 것은 36건이다.** SKU 2,200개 중에서.
나머지 60,098행은 **"아무 일도 없었음" 을 매일 다시 적은 것**이다.
그리고 26일 중 **4일은 아무 변화도 없었는데** 그날도 2,200행을 적었다.

★ 변화의 대부분은 **값 변경(36)이 아니라 추가·삭제(357)** 다. `codigos.borrado` 가
소프트삭제이므로 스냅샷에서 사라지는 것은 곧 `borrado=true` 다.

## 8.4 ★ 가장 중요한 것: **수단이 있었는데 안 썼다**

`codigos` 에는 이미 **`utime_modificado timestamptz DEFAULT now()`** 가 있다.
변경 시점을 알 수 있었다는 뜻이다 — **변경분만 적을 수 있었는데 전량 스냅샷을 택했다.**
그 선택이 kandente4 에서 244MB / 3,105,051행이 되어 Phase 86 이
**"가져오지 않는다" 고 결정**하게 만들었다(§2).

즉 이 기능은 **자기 저장 방식 때문에 이식조차 포기된** 상태다.
새로 만들 때 같은 실수를 반복하지 않는 것이 이 조사의 결론이다.

## 8.5 설계에 반영할 것

| 레거시가 한 것 | Ventago 에서 |
|---|---|
| 매일 전량 스냅샷 | **기준선 + 변경분** (같은 데이터로 22배 근거 확보) |
| 복구는 **가격만** | 1차 범위를 **가격**으로 좁힌다. 나머지 SKU 속성은 그다음 |
| `codigos_recover` 스테이징 후 적용 | **미리보기 → 확인 → 적용** 3단계를 그대로 계승 |
| `fecha`·`hora` 가 **varchar** | timestamptz. 매장 타임존은 이 저장소가 이미 겪은 함정이다 |
| 삭제는 `borrado` 소프트삭제 | Ventago 도 존재/비존재를 값 변경과 **구분해서** 기록해야 한다 |
