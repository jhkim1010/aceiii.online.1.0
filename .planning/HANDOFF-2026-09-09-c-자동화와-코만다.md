## 3. ★ GitHub Actions jest 게이트는 「느렸던」 게 아니라 **죽어 있었다**

넣은 진단이 처음 실행돼 실체를 보여줬다(run 34379233619):

- jest 시작 **36초** 만에 `FATAL ERROR: JavaScript heap out of memory`
- 그 뒤 **82개 suite** 가 SIGTERM 연쇄 사망
- **통과한 suite 0개** — 어떤 suite 도 끝나기 전에 터졌다

즉 「20회 연속 30분 타임아웃」은 증상이고, 1분 만에 죽어 44분을 헛돌았다.
원인: `NODE_OPTIONS=--max-old-space-size=2048` 이 **러너 기본값보다 낮다**.
메모리를 아끼려고 준 값이 게이트를 통째로 껐다. → **8192**.

★ 같은 값을 로컬 커밋 훅에 베꼈다가 **무해한 커밋이 차단되는** 사고도 났다.
  **환경마다 값이 다르다. 베끼지 말고 그 환경에서 재라.**

**아직 모른다:** 8192 로 전수가 45분 안에 끝나는지. 한 번도 완주한 적이 없어 기준선이 없다.
마지막 run(34396230324)은 33분+ 진행 중이었다(=적어도 더 이상 즉사하지 않는다).
다음 세션은 그 run 의 「느린 suite 상위 20」을 먼저 볼 것.

## 4. 감시(ventago-health-watch) — 두 서버 배포 완료

sha256 **저장소 ≡ 운영 ≡ srv2** 동일. 양쪽 1회 실행 `Result=success`, 오경보 없음.

★★ **srv2 는 유닛 이름이 다르다** — `ventago-health-watch-externo.service/.timer`.
  환경 override 가 있다(`ETIQUETA=EXTERNO(srv2)` · `CONTENEDORES=`(비움) ·
  `FALLOS_PARA_ALERTA=3` · `ENV_FILE=/etc/ventago-health-watch.env`).
  **표준 설치 스크립트를 돌리면 그 override 를 덮어 영구 오경보가 난다**(과거 실측 사고와
  같은 형태). 그래서 **스크립트만 교체**했다. 유닛은 건드리지 않았다.
  ⤷ 처음에 "타이머가 없다 = 안 돌고 있다" 로 읽었는데 **틀렸다.** 이름만 달랐다.

설치 직전에 잡은 결함: 8회 프로브(각 10초)가 `TimeoutStartSec`(운영 60초·srv2 90초)를
넘길 수 있었다 → **하필 응답이 느려지는 상황에 감시가 잘린다.**
per-probe 4초 + 전체 예산 15초로 바꾸고, 「필드 부재」 판정을 `ausente >= vistos` 로
고쳤다(종전 식은 예산 초과 시 부재를 영원히 못 잡았다).

## 6. 아키텍처 결정 — **엣지**로 간다 (Electron 분리 아님)

사용자 질문("판매·productos·reportes 를 Electron 으로 떼는 것 vs 현재 앱 + 엣지")에 답한 결론.

1. **어려운 부분은 UI 가 아니라 로컬 데이터 + 동기화다.** Electron 으로 떼도 그건 그대로
   남는다 — 엣지가 하는 일을 하나도 줄이지 못하고 앱만 하나 늘어난다.
2. **지점당 쓰는 주체가 여러 개가 된다.** 오늘 고친 결함이 전부 그 형태였다(카하 두 지점
   동시 개시 12일치 · 같은 서랍 세션 2개 · 코만다 2장). 지점별 일일 채번
   (`uq_sales_branch_daylocal_dn`)은 채번 권한이 한 곳일 때만 성립한다.
3. **규모**: 엣지는 조회 API ≈10개. Electron 은 `ventago-app` 1,231개 ts/tsx 중 공용 층까지
   따라와 **UI 코드베이스가 영구히 2개**가 된다.
4. **배포 이력이 경고다**: 이미 Electron 앱 둘(print-agent·zebra-agent)의 배포가 막혀 있었다.

**배치만 두 가지:** 다단말 지점 → 엣지 전용 PC 1대 / 단말 1대 지점 → **그 POS 에 설치**
(edge-agent 는 Node + PostgreSQL 이라 같은 기계에 올라간다).

**약점(솔직히)**: 엣지 PC 가 죽으면 그 지점은 오프라인 능력을 통째로 잃는다. 대안은
이중화가 아니라 **빨리 아는 것** — 72h 신선도 게이트 + 엣지 생존 감시(Phase 87 W4).
엣지는 이미 `branch_agents`(`agent_type='edge'`)에 등록되고 15초 health probe 가
`last_seen_at` 을 갱신하므로 **감시 배선은 새로 만들 게 아니라 연결만** 하면 된다.

### 매장 로컬 DB 의 실체 (사용자 질문 "백업 DB 가 매장에 1군데 있어야 하는 것 아닌가")
