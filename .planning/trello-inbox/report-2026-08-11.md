### ★ 4-1. [Ventas suspendidas](https://trello.com/c/06TCj16i) — 지점 간 데이터 누수 (우선순위 1)

> "si se suspende una venta en una sucursal, aparece en la otra tambien … esta es sucursale helguera"

한 지점에서 보류한 판매가 **다른 지점 POS 목록에 그대로 노출**된다.

**근거**

| 위치 | 내용 |
|---|---|
| `api-ventago/src/app/suspended-sales/suspended-sales.service.ts:344-346` | `findByStore(storeId)` where 절이 `{ storeId }` **단 하나** |
| `api-ventago/src/app/suspended-sales/suspended-sales.controller.ts:69-71` | `GET /suspended-sales` 가 branchId 쿼리를 **아예 받지 않음** |
| `ventago-app/src/views/homes/components/DraftAndDebtors/DraftAndDebtorsList.tsx:42` | 프론트도 파라미터 없이 호출. `:327` `visibleSales` 는 편집행 숨김일 뿐 지점 필터 아님 |
| `useSuspendedSaleSocket.ts:44` | `register_user {userId, storeId}` → **store room** 가입. `emitToStore(storeId,'suspended-sale:changed')` |

**데이터는 이미 있다** — `ventas_suspendidas.branch_id` 컬럼 존재(`db-schema-tables.md:3175`, `suspended-sales.model.ts:36-40`). 쓰기 경로는 전부 채운다: POS `ProductList.tsx:1017`, 재보류 `DraftAndDebtorsList.tsx:118`, WP `wp-webhook.service.ts:272`, 모바일 `mobile-sales.service.ts:42-53`(null 이면 거부).

**근본 원인** — 조회 경로만 Phase 67 멀티테넌트 작업 때 **store 단위로만** 하드닝됐다. 지점 필터가 빠진 게 아니라 애초에 store 를 격리 단위로 잡았다. 소켓도 store room 이라 타 지점에 토스트까지 뜬다.

**수정 방향**

1. `suspended-sales.controller.ts` — `@Query('branchId')` 수용. 일반 사용자는 서버가 `user.branchId`(또는 열린 caja 의 `box.branchId`)로 **강제**, admin/gerente/superadmin 만 쿼리값 허용 (멀티테넌트 규약: 클라이언트가 준 branchId 를 소유권 확인 없이 쓰지 않는다)
2. `suspended-sales.service.ts:344` — `where: { storeId, ...(branchId ? { branchId: { [Op.or]: [branchId, null] } } : {}) }`. **레거시 NULL 행 처리 결정 필요** — `Op.or` 로 남길지, 백필 마이그레이션 후 `{ branchId }` 단독으로 완전 격리할지
3. `DraftAndDebtorsList.tsx:42` — `?branchId=${selectedBranchId ?? user?.branchId}`, `getSuspendedSales` useCallback deps 에 추가
4. 소켓 — `emitToBranch` 추가, 최소한 클라이언트에서 `payload.branchId`(이미 `useSuspendedSaleSocket.ts:8` 인터페이스에 존재)와 대조해 필터

**회귀 체크리스트**

- [x] 조회 전용 — 트랜잭션·외부 I/O·락 순서 해당 없음
- [ ] `store_id` + `branch_id` 스코프 — **이번 수정의 본체**
- [ ] 소켓 room 범위 = 화면 격리 범위 일치
- [ ] **기존 `branch_id IS NULL` 행이 새 필터에 걸려 사라지지 않는가** ← 반드시 운영 DB 로 사전 확인
- [ ] 마이그레이션(백필) 선택 시 로컬 5432 + 운영 5434 양쪽

**착수 전 운영 조회 (read-only, 승인 불필요)**

```sql
SELECT store_id, branch_id IS NULL AS sin_branch, count(*)
FROM ventas_suspendidas GROUP BY 1,2 ORDER BY 1;
```

### 4-3. [REingreso de productos](https://trello.com/c/AkpJUsbI) — 수량이 조용히 버려짐

> "al re ingresar en otra fecha un articulo lo reconoce como un codigo que no estuvo en ingreso. Asi que no agrega codigo ni corrije"

**근거** (전부 `ventago-app`)

| 위치 | 내용 |
|---|---|
| `src/views/products/list/ProductsView.tsx:256-259` | 그리드 소스 = `inventory-by-date-branch` 의 **전체 variant (날짜 무관)** |
| `:300, 322-327` | 그 전체 variant 가 전부 `_isExisting: true` 로 표시됨 |
| `:345` | 저장 기준선 `originalChildren: detail.children` |
| `components/ProductsList.tsx:48-52` | `_children` 출처 = `GET /products/stock-today?date=` → **그 날짜에 net 입고가 있는 행만** |
| `:675-681` | `handleMadreSave` — `originalChildren.find(...)` 로 variantId 조회. **`if (origChild)` 에 else 가 없다** |

**근본 원인** — 그리드(전체 variant)와 저장 기준선(당일 입고분만)의 **출처가 다르다.** 다른 날짜에 입고된 코드는 `originalChildren` 에 없어 `find` 가 실패하고, `_isExisting === true` 라 `addVariants` 분기(`:683`)에도 못 들어간다. 결과: 입력한 수량이 `updateVariants`·`addVariants` 어디에도 안 실려 **경고 한 줄 없이 통째로 버려지고 PUT 은 성공 토스트를 띄운다.** ("부재가 침묵한다" — 이 저장소의 단골 실패 형태)

**백엔드는 정상** — `api-ventago/src/app/products/productStock.service.ts:2283-2298` 이 "그날 입고 없으면 첫 입고 행으로 INSERT" 를 이미 처리하고, `addVariants` 경로(2325~)도 `findOne({parentId,colorId,sizeId})` 로 기존 variant 를 재사용한다. **variantId 만 실려 나가면 동작한다.**

**범위** — 좌측 「Historial del día」 클릭 경로 **전용**. 우측 「Códigos madres」 경로(`ProductParentList.tsx:205,226`)는 `setEditingMadre(null)` → `fetchStockBaseline` → `correct-today` 를 타서 버그 없음.

`git blame`: 해당 블록은 `609ba75f`(2026-04-16) / `f19c13ee`(2026-04-29) 이후 **미변경**. 08-07 productos 수정 러시(`607c3b3` "수량 변경이 조용히 버려지던 문제")는 `handleSubmit` 저장 분기만 단일화했고 이 매칭 실패 경로는 남았다.

**수정 방향**

1. `handleMadreClick` — `inventoryVariants`(전체 variant, `id` 포함)를 그리드에 쓸 때 **같은 배열을 `originalChildren` 으로 저장**(`:345`). 기준선과 그리드 출처를 하나로 (`stock-baseline.ts` 가 이미 세운 원칙)
2. `handleMadreSave` `:675-681` — `else` 추가. 조용히 버리지 말고 `console.error` + `toast.error('No se pudo identificar la variante …')`, 가능하면 `addVariants.push({colorId,sizeId,stock})` 폴백 (백엔드가 기존 variant 재사용하므로 안전)
3. 회귀 테스트: 「그리드에 보이는 셀은 반드시 저장 payload 에 실린다」

**회귀 체크리스트**

- [ ] 저장 payload 누락 없음 — 그리드 행 수 = updateVariants + addVariants 합
- [ ] 매칭 실패가 화면에 드러남 (조용한 실패 금지)
- [ ] 우측 「Códigos madres」 경로 회귀 없음
- [ ] `product_branch_id` 기준 유지 (`product_id` 컬럼 없음)
