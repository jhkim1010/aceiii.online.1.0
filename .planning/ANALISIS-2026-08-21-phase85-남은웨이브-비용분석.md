# Phase 85 남은 웨이브 — "지금 다 하면 시스템이 느려지는가" (2026-08-21 실측)

질문(사용자): *"언젠가 반드시 해야 하는 일이라면 8개를 모두 하고, 만일 이를 할 때
시스템이 전체적으로 느려지는 일이 발생하는가 분석해줘."*

**한 줄 답: 두 웨이브는 지금 하면 실제로 느려지고(W4), 한 웨이브는 운영을 위협한다(W8을
같은 서버에서). 나머지 넷은 안전하거나 조건부로 안전하다.**

---

## 0. 실측 기준선 (2026-08-21 운영)

```
데이터        sales 168행 · sale_items 685 · stocks 1,806 · sync_outbox 0
              products 367(전 매장 합) · stores 12 · users 26
              2만 행 넘는 테이블: 0개
서버          RAM 32GB (available 16GB) · swap 0 · CPU 8 · load 0.21
컨테이너      api_ventago 785MB · api_staging 779MB · ventagoapp 78MB
느린 쿼리     최근 누적 35건, 최대 473ms — sales/stocks/sale_items 는 **한 건도 없음**
```

지금 이 시스템은 느리지 않다. 그러므로 "느려지는가" 는 **우리가 무엇을 더 얹는가**의 문제다.

## W4 파티셔닝 — ❌ **느려진다. 그리고 되돌리기 어렵다.**

### 근거 1: `sales` 에 외래키가 **17개** 꽂혀 있다

```
afip_vouchers · credit_ledger · discount_reasons · mp_movements · mp_refund_attempts
mp_refunds · online_orders · restaurant_deliveries · restaurant_tables · sale_discounts
sale_items · sale_payment_methods · sale_recharges · sale_senias · sales(자기참조)
cheques · sale_idempotency_keys        — 전부 `REFERENCES sales(id)`
```

PostgreSQL 은 파티션 테이블의 **모든 UNIQUE/PK 에 파티션 키가 포함**돼야 한다.
날짜로 자르면 `sales_pkey` 가 `(id, created_at)` 이 되고, 그 순간
**`REFERENCES sales(id)` 17개가 전부 무효**가 된다(단독 `id` 에 유일 인덱스가 없어진다).

→ 자식 16개 테이블에 날짜 컬럼을 추가하고 FK 17개를 복합키로 재작성해야 한다.
   ORM 연관과 조인도 전부 따라 바뀐다. **168행 때문에.**

### 근거 2: 파티션 키로 안 거르는 쿼리는 전부 느려진다

`WHERE id = ?` · `WHERE store_id = ?` · `WHERE terminal_id = ?` 는 날짜를 안 준다 →
**모든 파티션을 연다.** 지금은 테이블 전체가 몇 페이지라 seq scan 한 번이면 끝나는 것이
파티션 N개 open + N개 인덱스 탐색이 된다. `sales` 인덱스는 **18개**라 파티션마다 복제된다.

### 판정

- **지금**: 순수한 손해. 느려지고, 마이그레이션 규모가 크고, 기준(무엇으로 자를지)이 없다.
- **그때**: `sales` 가 수천만 행이 되면 필요하다. 그때는 대부분의 조회가 날짜 범위를 준다.
- SPEC 자신이 이렇게 적어 뒀다: *"행 수 실측 **후에** 대상 확정. ★ 추측으로 파티셔닝하지
  않는다 — 잘못 자르면 되돌리는 비용이 자르는 비용보다 크다."* **실측이 나왔고, 답은 '아직'이다.**

### 그래서 W4 에서 지금 하는 것

- ✅ **규약**(expand → migrate → contract · `CREATE INDEX CONCURRENTLY` · NOT NULL 은 백필 후
  별도 단계 · 큰 테이블 ALTER 는 잠금 시간 사전 측정)을 **CLAUDE.md 에 못 박는다.** 공짜다.
- ✅ **착수 조건을 숫자로 적어 둔다** — 아래 「트리거」.
- ❌ 파티셔닝 자체는 하지 않는다.

## W7 야간 rollup — ⚠️ **느려지진 않지만 새 고장 모드가 생긴다**

- 168행을 사전 집계하면 조회가 오히려 한 단계 늘어난다(rollup + 미반영분 보정).
- 진짜 비용은 성능이 아니라 **신선도**다. 이 저장소가 이미 겪은 형태다:
  *"자동화를 붙이면 '1회 조회' 화면이 거짓말한다 — 낡은 값이 작으면 오류도 안 난다."*
- 12매장·168판매에서는 rollup 이 맞는지 **검증할 방법도 없다**(원본과 항상 같다).

**판정: 지금은 유지비만 남는다.** 트리거 조건을 적어 두고 보류.

---

## W5 무중단 배포 — ⚠️ **조건부 안전. RAM 상한이 전제다**

- 지금은 배포 = 컨테이너 재생성 = **모든 소켓 끊김 + 짧은 502**. (오늘 밤 5회 배포에서 매번 관측)
- 무중단으로 바꾸면 전환 순간 **구/신 컨테이너 2개 동시 가동** → +785MB. 여유(16GB)로는 충분.
- ★ **문제는 Jenkins 가 같은 서버에서 돈다는 것이다. swap 은 0이다.**
  빌드(nest/next) + API 2개 + 운영 Postgres 가 겹치는 순간이 생긴다. swap 0 에서 OOM killer 가
  무엇을 죽일지는 고를 수 없다.

**판정: 한다. 단 컨테이너에 메모리 상한(`mem_limit`)을 걸고, 전환 조건은 healthcheck 통과로 한다.**
바꾸는 것은 "잠깐 끊김" → "잠깐 무거움" 이다. 그 교환은 이득이지만 상한 없이는 안 된다.

## W6 매장별 논리 복구 — ✅ **상시 부하 없음**

on-demand 다. 다만 매장 1개 내보내기가 **133개 테이블**을 훑으므로 실행 순간은 무겁다.
읽기 전용 + 야간 + 배치 크기 제한으로 가둔다. 상시 성능에는 영향이 없다.

**판정: 한다.** 사업 요건이고 데이터 크기와 무관하다.

## W8 300매장 회귀 자동화 — 🔴 **여기가 가장 위험하다**

계획: *"309매장 스테이징 준비를 스크립트 1개로 · **주 1회 자동 실행**(심야)"*

- 이 저장소의 기록: **"Jenkins 는 운영 서버 위에서 돈다 (swap 0) — 무거운 작업을 빌드에
  넣으면 운영 Postgres 가 위험"**.
- 309매장 부하 시험은 무거운 작업의 정의 그 자체다. 같은 물리 서버에서 돌리면
  **운영 Postgres 와 CPU·RAM·디스크 IO 를 다툰다.** swap 0 이라 완충이 없다.
- 심야라도 안전하지 않다 — 야간 크론(백업·rollup·캠페인)이 그 시간에 돈다.

**판정: 부하 시험 자체는 별도 호스트가 없으면 자동화하지 않는다.**
대신 W8 을 두 조각으로 나눈다:

| 조각 | 지금 | 이유 |
|---|---|---|
| **p95 배포 게이트** | ✅ 한다 | 부하를 만들지 않는다. 이미 측정 중인 값으로 배포를 막을 뿐이다 |
| **불변식 회귀 검사** | ✅ 한다 | 단위/통합 spec 수준 — 부하가 아니다 |
| **309매장 부하 리그 자동 실행** | ❌ 보류 | 별도 호스트 확보가 선행 조건 |

## W3 pageSize — ✅ **하되, POS 로컬 필터는 건드리지 않는다**

사용자 선택: "조용한 잘림을 시끄럽게".

- 상한 초과 시 경고를 실어 보내는 비용은 무시할 수준이다.
- ★ **POS 를 서버 검색으로 바꾸면 지금은 오히려 느려진다.** 현재 POS 는 상품 191개를
  한 번 받아 **로컬에서 0ms 로 필터**한다. 서버 검색으로 바꾸면 키 입력마다 왕복이다
  (그 엔드포인트 실측 376ms).
- 그래서 이렇게 한다: **로컬 필터를 유지하고, 서버 검색을 폴백으로 붙인다.**
  이것은 기존 결함을 고치는 것이기도 하다 — *"POS 검색엔 서버 폴백이 없다: 목록 where 에서
  빠지면 그 제품은 아예 못 판다."* 카탈로그가 상한을 넘는 매장이 생기면 그때 폴백이 받는다.
- Phase 73 의 결정(*"서버 상한을 50 으로 잡으면 정상 화면이 조용히 잘린다"*)은 **뒤집지 않는다.**
  잘림을 없애는 게 아니라 **들리게** 만든다.

## ★ 트리거 — "언젠가" 를 숫자로

보류하는 것은 잊기 쉽다. 그래서 **언제 하는지를 지금 적는다.** W8 의 게이트가 이 값을 잰다.

| 웨이브 | 착수 조건 (하나라도 넘으면) |
|---|---|
| W4 파티셔닝 | `sales` ≥ **5,000만 행** 또는 `stocks` ≥ **1억 행** 또는 월 단위 조회 p95 > 300ms |
| W7 rollup | 매장 ≥ **100개** 또는 월말 보고서 p95 > 1s 또는 보고서 쿼리가 slow_query_log 상위 5 |
| W8 부하 리그 자동화 | 부하 시험 전용 호스트 확보 (운영 서버 공유 금지) |

★ 파티셔닝 기준을 "5,000만" 으로 잡은 이유: 그 아래에서는 인덱스가 있는 한 파티셔닝이
  이득이 아니고, 위의 FK 17개 재작성 비용을 정당화하지 못한다.
