<objective>
Two server rules for the new app's login token:
1. D-06 — the same people who use the web can use the phone: admin, gerente and vendedor log in through `/mobile/auth/login` with `app: 'ventago-movil'`; branch scope is not required (the approved device fixes the branch, Plan 15).
2. D-22 — a revoked phone loses ALL access immediately: the new app's token is confined to `/mobile/pos/*`, so it is worthless on web routes and sockets; inside `/mobile/pos/*` revocation deletes its session (Plan 15) and the next request fails. No residual 6 h window.

Research for scoping (2026-10-15, read from the Flutter sources): only `mobile-sales-app` uses `/mobile/auth/login`; it calls `/mobile/*` plus `/attendance/punch` and `/products/:id/images` with that token. `tienda-admin-app` and `ventago-admin-app` use `/auth/login` (web tokens); `talleres-vendor-app` uses `/vendor-portal/auth/login`; `/reseller/*` has its own login. Therefore the rejection is keyed on a NEW claim that only the new app's logins carry — every existing consumer is untouched.

Output: login DTO/service change with spec; token-client helper + spec; JwtStrategy call site + spec; 4 gateway handshakes.
