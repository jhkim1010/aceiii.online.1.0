<objective>
D-21: the phone charges Mercado Pago with the same dynamic-QR flow as the web POS (`PaymentSummaryModal.tsx` + `McdpgQrPanel.tsx` → `POST /mercadopago/qr`, approval via webhook/polling, `DELETE /mercadopago/qr/:id`). This plan wraps the existing server services under `/mobile/pos/mp/*` with device-derived scope, and gives Plan 05 the check that links an approved intent to exactly one sale payment line.

How the web works (studied 2026-10-15, so the executor does not need to rediscover it):
- `POST /mercadopago/qr` body {storeId, branchId, amount, pendingVentaId, terminalId} — note the web sends `pendingVentaId = cashRegister.id` (the open caja session) and takes storeId/terminalId FROM THE BODY; `MpQrService.createIntent` resolves the MP account (branch first, then store; refuses MP_NO_ACCOUNT / MP_ACCOUNT_DISCONNECTED / MP_NO_EXTERNAL_POS_ID), inserts `mp_payment_intents` (status pending, expiresAt now+3 min, locked TTL), calls MP, stores qrData.
- Approval: webhook sets status approved + paymentId (UNIQUE) + approvedAt and credits the MP wallet; the web listens on socket `mercadopago:approved` and polls `GET /mercadopago/payment-intents/:id` every 5 s; on approval the web auto-submits the sale. Nothing on the sale row records the intent today.
- `GET /mercadopago/payment-intents/:id` and `DELETE /mercadopago/qr/:id` do NOT filter by store — the mobile wrapper must (tenant isolation).
Phone differences (Claude's discretion, documented): polling every 3 s instead of the socket (Plan 18 refuses ventago-movil tokens on sockets — D-22); the QR image is rendered on the server with the `qrcode` package already in api-ventago (no new Flutter dependency → no package-legitimacy checkpoint); the intent is recorded on the payment line (`sale_payment_methods.mp_payment_intent_id`, Plan 01) — that is the «enlazado a la línea de pago» of D-21.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-111-90 | Tampering | QR charged to another store's MP account / another terminal | mitigate | storeId/branchId/terminalId only from deviceCtx; createIntent resolves the account from the store/branch (the store's own MP account); spec asserts the createIntent argument |
| T-111-91 | Information Disclosure | polling/cancelling another store's intent (web endpoints lack store filter) | mitigate | every lookup filtered by store AND terminal; 404 for foreign ids; mutation on the terminal filter |
| T-111-92 | Repudiation | double charge on retry (customer pays twice / one payment used for two sales) | mitigate | same-amount pending intent is reused instead of a new QR; approved intent accepted for exactly one sale line (validarIntentParaVenta + UNIQUE index from Plan 01 + FOR UPDATE); recovery list of approved-without-sale intents; app persists intentId with the checkout key (Plan 13) |
| T-111-93 | Tampering | amount mismatch between QR and sale | mitigate | sale line amount must equal the approved intent amount in centavos (MP_MONTO) |
| T-111-94 | Denial of Service | cancelling clears the shared MP POS order of a web terminal | mitigate | no automatic cancel; explicit cancel only by the seller on their own pending intent |
| T-111-95 | Denial of Service | external HTTP inside a DB transaction | mitigate | createIntent called outside any transaction (CLAUDE.md) |
| T-111-96 | Elevation of Privilege | charging without permission | mitigate | same @Auth roles as the web MP routes; metadata spec |
