## 1. W0 — 평일 로그 확인 (5분, **가장 먼저**)

배포 후 표본이 **토요일 5,737요청(평일의 약 18%)** 뿐이다. 평일 1~2일치를 봐야 굳는다.

```bash
ssh jhkim-server '
f=/var/lib/ventago-logs/api/combined-$(date +%F).log
echo "요청 $(sudo grep -ac "\[HTTP\]" $f)"
echo "누수 $(sudo grep -ac "격리 누수 감지" $f) / 검증불가 $(sudo grep -ac "격리 검증 불가" $f)"
echo "★ store 가 숫자인 것: $(sudo grep -a "격리 누수 감지" $f | grep -cE "store=[0-9]+")"
sudo grep -a "격리 누수 감지" $f | grep -E "store=[0-9]+" | head -5
'
```

| 결과 | 조치 |
|---|---|
| `store=<숫자>` **0건** | 예정대로 배경 트랙 유지 |
| `store=<숫자>` **1건 이상** | ★★ **실제 오염이다. Phase 94 를 중단하고 최우선으로 올린다.** 경보에 `파일:줄`·매장·user 가 실려 있으므로 그 자리부터 본다 |
| 경보가 **양쪽 다 0인데 요청도 적다** | 표본 부족 — 판정 보류, 다음 영업일에 다시 |

★ **「0건」을 「안전」으로 읽기 전에 요청 수를 본다.** 트래픽이 없으면 0은 아무 뜻이 없다
  (일요일엔 8개 매장 전부 개시 0 — `most-stores-are-dormant-alerts-must-filter`).

## 2. W1 — raw SQL 런타임 감시 (약 3~4시간)

`sequelize.query` 219곳은 훅을 안 탄다. **막지 않고 먼저 본다.**

- Sequelize `beforeQuery` 훅에서 raw SQL 문자열을 검사:
  테넌트 테이블(§3-d 의 14개 + `store_id` 보유 171개)을 건드리는데
  `store_id` 조건이 없으면 **기록**한다.
- 형식은 2026-09-26 에 만든 것과 **같게** — `파일:줄` 3단 사슬 + 매장 + user,
  throttle 은 **위치별**. (같은 형식이어야 한 화면에서 같이 읽힌다.)
- ★ **막지 않는다.** raw SQL 은 마이그레이션·리포트·워커가 정당하게 쓰는 경로가 많아,
  차단부터 하면 멀쩡한 것을 죽인다. W3 에서 판정한 뒤에 좁힌다.

**검증**: 대조군 필수 —
① store 조건이 있는 raw SQL 은 **안 찍힌다**
② 없는 것은 **찍힌다**
③ 테넌트 테이블이 아닌 것(예: `pg_stat_activity`)은 **안 찍힌다**
④ 돌연변이: 판정을 지우면 시험이 죽는가

## 3. W2 — 커밋 게이트 (약 1~2시간)

새로 쓰는 raw SQL 이 같은 형태면 **커밋을 막는다**. `.claude/hooks/verify-before-commit.sh` 에 얹는다.

- 대상: 추가된 줄의 `sequelize.query` 중 테넌트 테이블 + `store_id` 조건 없음.
- 예외는 **그 자리에 사유 주석**(`-- tenant-exempt: 이유`) — 이 저장소의 `w4-exempt` 와 같은 방식.
- ★ **대조군**: 무해한 raw SQL 변경이 **통과하는지**를 반드시 같이 시험한다.
  통과하지 않으면 그 게이트는 사람을 막는 장치가 된다
  (`control-group-can-pass-too` · `guard-must-not-check-outside-its-scope`).

## 4. W3 — 204곳 판정 (W1 배포 후 **영업일 1~2일 뒤**)

W1 이 모은 실행 기록으로 **실제로 도는 것만** 추린다. 죽은 코드에 시간을 안 쓴다.

판정 기준 — **셋이 겹칠 때만 결함이다**:
1. 매장 소유 행을 읽는가
2. store 필터가 없는가
3. 그 결과를 **특정 매장의 거래**에 쓰는가 (superadmin 이 전 매장을 보는 리포트는 **의도**다)

고위험 우선: §3-d 의 **매장별-유일 키 14개 테이블** + 쓰기 경로(`sales`·`stocks`·`products`).

## 5. W4 — 선택적 매장 인자를 필수로 (범위는 W3 결과가 정한다)

```ts
if (storeId) where.storeId = storeId;   // ← 이 형태 35곳
```

가드가 구해 주고 있지만 **크론·워커·평범한 superadmin 경로에서는 안 구해진다.**
`findGenericProduct(storeId?)` 부터 — `sku='GEN-0001'` 이 **14개 매장에 겹치는** 유일한 값이라
여기가 가장 구체적이다.

★ **전부 바꾸지 않는다.** 리포트류는 「전 매장」이 의도다. W3 판정을 통과한 것만.

## 6. 하지 않기로 한 것

- **RLS + 세션 GUC — 지금은 안 한다.** 근거는 `95-CONTEXT.md` §4:
  `pool_mode=transaction` 이라 세션 GUC 가 못 살고, 풀 커넥션이 요청 간 재사용되므로
  평범한 `SET` 은 **앞 요청의 매장 id 를 다음 요청에 남긴다 — 지금보다 나빠진다.**
  요청마다 트랜잭션으로 감싸면 커넥션을 요청 내내 붙잡아 `pool_size=50` 을 압박한다.
  견적 **2~3주**. 별도 프로젝트로 둔다.
- **raw SQL 을 W1 단계에서 차단하지 않는다** (§2 의 이유).
- **35곳을 일괄 치환하지 않는다** (§5 의 이유).
