## 사용자 전략 (원안)

> 병렬 서버는 장차 반드시 필요하다. 지금 운용하면 오히려 느려지지만, **스위치**를 준비해서
> 평소엔 단독 서버로 일하고, 아무도 안 쓰는 시간에 스위치를 켜서 진행 상태를 확인·점검·개선하고
> 다시 꺼서 단독으로 일주일을 보낸다. 그렇게 2~3년 준비해 **쉽게 옮길 수 있는 상태**를 만든다.
> 단독 서버일 때는 **텔레그램 메시지 하나로 복구**되면 좋겠다.
> 그리고 (1) 단독 복구 기능을 점검하는 테스트, (2) 병렬 작동을 점검하는 테스트를
> **coolsistema 매장**으로 한다.

## 왜 이 전략이 현 계획보다 나은가

`75-PLAN.md` W7 은 "G1~G6 를 충족한 뒤 2호기를 붙인다"이다. 그런데 **게이트 충족 여부를 판정하는
유일한 방법이 2호기를 붙여보는 것**이라, `66-PLAN.md:109` 의 순환 논법을 G1~G6 로 대체했음에도
순환이 완전히 풀리지 않았다.

스위치는 이걸 **리허설**로 바꾼다. 되돌릴 수 없는 결정이 주 1회 되돌릴 수 있는 실험이 된다 —
**일방향 문이 왕복 문이 된다.** 게이트는 "언젠가 판정할 기준"이 아니라 **매 리허설이 채우는 값**이 된다.

그리고 3년 뒤에 남아야 하는 것은 사람 머릿속 지식이 아니라 **하네스와 시계열**이다.
그래서 모든 리허설 결과는 처음부터 `daily.jsonl`(Phase 75 W1, 이미 Dropbox 오프사이트까지 도는 경로)에 쌓는다.

## 원안에서 고쳐야 할 전제 3가지

### 1. "주말엔 아무도 안 쓴다" 는 검증되지 않은 가정이다

아르헨티나 소매업에서 **토요일은 통상 최대 매출일**이고 일요일이 한산하다.
"주말"을 한 덩어리로 보면 **가장 바쁜 날에 실험**하게 된다.

다행히 이제 추측하지 않아도 된다 — Phase 75 W0-8 로 route p95 와 동시 소켓이 **요일별로 축적**되기
시작했다(2026-08-07~). **첫 리허설 창은 7일치 데이터를 보고 정한다.**
현재 가설은 "일요일 밤~월요일 새벽"이지만, 가설로 정할 일이 아니다.

### 2. 부하 없는 리허설은 아무것도 증명하지 못한다 ★ 가장 중요

병렬 노드의 실패 모드 — 캐시 미스 N배(β) · 크론 중복 · 커넥션 예산 · 소켓 라우팅 · hot-row 경합 —
는 **전부 부하가 있어야 나타난다.** 사용자 0명인 창에서 2노드를 켜면 **전부 통과한다.**
그것은 정보가 아니라 **잘못된 확신**이고, USL 하강 구간을 용량 부족으로 오독하는 것과 함께
확장 실패의 전형적 경로다.

**따라서 부하 생성기가 이 phase 의 실질 핵심이다.** 가장 안 화려하고 가장 결정적이다.

### 3. 스위치는 "컨테이너 하나 더"가 아니다

켤 때 **함께 움직여야 하는 것**들이 있고, 전부 Phase 75 W6/W5 항목이다.

| 스위치가 건드리는 것 | 현재 | 선행 |
|---|---|---|
| 크론 정확히 1회 | `CRON_ENABLED` 수동 env — **2호기에서 안 주면 중복** | Phase 75 W6-1 (advisory lock) |
| 커넥션 예산 | `replicas` 개념 없음(워커만 계산) | Phase 75 W6-4 |
| 캐시 일관성(β) | 워커 로컬. Redis 는 무효화만 전파 | Phase 75 W5-6 (Redis L2) |
| 공개몰 pool 격리 | host 문자열 비교 — 부팅 로그 `격리=no` 실측 | Phase 75 W6-3 |
| 소켓 워커간 중계 | Redis 어댑터 **이미 있음** ✓ | — |

**원안은 Phase 75 W6 을 대체하지 않는다. W6 에 목적과 기한을 준다** —
"언젠가 필요할지도"가 "1차 리허설 전까지 필요"가 된다.

### 3-b. 주 2일만 도는 노드는 조용히 어긋난다

이미지·env·마이그레이션이 갈라진 채 리허설하면 **운영에 존재하지 않는 구성**을 검증하게 된다.
스위치는 매번 **같은 아티팩트로 새로 만들고**(장기 존속 pet 금지),
켤 때 양 노드의 **빌드 SHA·마이그레이션 상태 동일성을 preflight 로 검사**한다.

## 복구 기능 — 티어를 나눈다

"메시지 하나로 복구"는 **무엇을 복구하느냐**에 따라 위험도가 전혀 다르다.

| 티어 | 동작 | 한 메시지로? | 근거 |
|---|---|---|---|
| T1 | 앱 재시작 (`pm2 reload` / `compose up -d`) | ✅ | 멱등, 데이터 무영향 |
| T2 | 마지막 정상 이미지로 컨테이너 재생성(롤백 태그) | ✅ 확인 1회 | 되돌릴 수 있다 |
| T3 | 호스트 재부팅 (Hostinger API) | ⚠️ 2단계 확인 | 전체 서비스 중단 동반 |
| T4 | **DB 백업 복원** | ❌ **절대 금지** | 되돌릴 수 없는 데이터 손실 경로 — Phase 74 절차 |

### 어디서 도는가가 설계의 핵심이다

**서버 안에서 도는 복구기는 서버가 죽으면 같이 죽는다.** 2026-08-06 에 정확히 그 형태를 겪었다 —
ssh-agent 가 비어 Mac 워치독이 매시간 `판정 보류` 만 남기고 있었고, 백업이 멈춰도 알림이 가지 않는
상태였다. 그 전에는 launchd 에이전트 5개가 등록 해제된 채 방치돼 있었다.

- **T1·T2** — 서버 안 responder 로 충분(앱만 죽고 호스트는 살아 있는 경우)
- **T3** — 반드시 **밖에서**. Mac launchd 워치독이 자연스러운 자리다(이미 Telegram·heartbeat 상호 감시 보유).
  **한계 명시: Mac 이 꺼져 있으면 무력하다.** 이 한계를 문서에 남기지 않으면 나중에 "왜 안 왔지"가 된다.

### 채팅이 제어 채널이 되는 순간 그것은 인증 경로다

**chat_id 허용목록 · 2단계 확인(명령 → 일회용 토큰 → 확인) · 레이트 리밋 · 전 명령 감사 로그.**
타협 대상이 아니다.

## 테스트 2종

### (A) 복구 드릴 — 월 1회 자동

일부러 컨테이너를 죽이고 T1 이 복구하는지, 소요 시간이 얼마인지 기록한다.
**점검한 적 없는 복구 기능은 없는 것과 같다** — 2026-08-06 의 launchd 5개가 그 상태였다.

### (B) 병렬 리허설 — 창이 열리면 자동

기동 → preflight(SHA·마이그레이션 동일) → **부하 생성** → 지표 수집 → 종료 → 단독 복귀 → Telegram 리포트.
**실패 시 자동으로 단독 복귀**(fail-safe). 사람이 새벽에 지켜보지 않아도 안전해야 한다.

**합격 기준을 첫 리허설 전에 정한다.** 안 그러면 "괜찮아 보인다"로 끝난다. 그 기준이 곧 G1~G6 다.

| 측정 | 판정 |
|---|---|
| 크론 잡별 실행 횟수 = 정확히 1 | G4 |
| 동일 참조 쿼리 수가 **2배가 되지 않음** | **G3 = β 실증. 핵심** |
| `cl_waiting` 0 유지 | G1 |
| 같은 부하에서 p95 vs 단독 노드 | **2호기가 실제로 빠른가 = 최종 판정** |
| 한 매장 집중 부하에서 판매 커밋 정합(Phase 64 스위트) | 데이터 안전 |

### coolsistema 매장을 쓰는 것에 대해

적절하다 — **hot-row 경합은 한 매장에 집중돼야 재현**되므로 단일 매장 대상이 오히려 맞다.
다만 쓰기 테스트이므로 (1) 생성 데이터에 **표식**을 남겨 사후 정리 가능하게 하고,
(2) 리허설 데이터가 **매출 리포트를 오염시키지 않게** 한다.

## 리허설 사다리 — 2단계

**1단계: 같은 호스트의 2번째 컨테이너** (비용 0)
β · 크론 · 커넥션 · 캐시를 전부 검증한다. **지금 필요한 것은 사실상 이것뿐이다.**

**2단계: 별도 물리 서버** (필요 시 주말만 임대)
네트워크 지연·파티션 차원은 같은 호스트로는 **절대** 검증되지 않는다.

**1단계를 수십 회 반복해 안정되기 전에는 2단계에 돈을 쓰지 않는다.**

### DB 는 끝까지 1대다

앱만 병렬이다. 이 경계가 흐려지면 DB 복제 프로젝트로 번지고 그것은 완전히 다른 규모다.
읽기 분산·standby 는 Phase 74 및 별도 결정 사안으로 남긴다.
