# Phase 76: 운영 복구 자동화 + 병렬 리허설 하네스 — Specification

**Created:** 2026-08-07
**Source:** `76-CONTEXT.md`
**Requirements:** 5 (R1~R5)
**성격:** 장기 phase(2~3년). 산출물은 기능이 아니라 **반복 가능한 하네스와 시계열**이다.

## Goal

**병렬 전환을 되돌릴 수 있는 실험으로 만들고, 단독 운영 중의 장애를 사람이 서버에 로그인하지 않고
복구할 수 있게 한다.**

두 가지를 한 문장으로 묶으면: **운영자가 노트북 없이도 시스템을 되살릴 수 있고,
2호기 도입 여부를 의견이 아니라 축적된 숫자로 판단할 수 있는 상태.**

**Current** = 현행, **Target** = 목표, **Acceptance** = 완료 판정.

### R1. 복구 명령 채널 (Telegram) — Wave 1

- **Current:** 장애 시 복구 수단은 **SSH 로그인 → docker 명령**뿐이다. 그리고 그 SSH 자체가
  2026-08-06 에 조용히 막혀 있었다(ssh-agent 빈 상태 → Mac 워치독이 매시간 `판정 보류`).
  알림은 오는데(uptime-watchdog) **알림을 받은 사람이 할 수 있는 일이 없다** — 노트북이 있어야 한다.
- **Target:**
  1. **T1~T3 티어 분리 구현.** T4(DB 복원)는 **이 채널에 존재하지 않는다** — 명령 자체를 만들지 않는다.
     "위험하니 조심"이 아니라 **경로를 없앤다.**

     | 티어 | 명령 | 확인 |
     |---|---|---|
     | T1 | 앱 재시작 | 즉시 실행 (멱등) |
     | T2 | 마지막 정상 이미지로 재생성 | 1단계 확인 |
     | T3 | 호스트 재부팅 | **2단계 확인**(일회용 토큰) |

  2. **실행 위치 이원화** — T1·T2 는 서버 내 responder, **T3 는 서버 밖**(Mac launchd).
     서버 안에서 도는 복구기는 서버가 죽으면 같이 죽는다.
     **Mac 이 꺼져 있으면 T3 는 불가하다는 한계를 문서와 알림 문구에 명시**한다.
  3. **인증·감사** — `chat_id` 허용목록 · 명령별 2단계(발급된 토큰 없이는 실행 불가) ·
     레이트 리밋(연타로 재부팅 반복 방지) · **모든 명령 시도를 성공·실패 무관하게 감사 로그**로 남긴다.
  4. 상태 조회 명령(`/status`) — 컨테이너 상태·헬스체크·마지막 배포 SHA·백업 나이.
     **복구 전에 무엇이 고장났는지 보는 수단이 없으면 복구는 도박이다.**
- **범위 밖:** DB 복원 · 마이그레이션 실행 · 임의 셸 명령. **셸을 열어주는 순간 이 채널은 백도어다.**
- **Acceptance:** 허용목록 밖 `chat_id` 의 명령이 **전부 거부**되고 감사 로그에 남는다 ·
  T3 가 토큰 없이 실행되지 않는다 · T1 이 실제로 죽은 앱을 되살린다(R2 드릴로 확인) ·
  `/status` 가 SSH 없이 장애 판단에 충분한 정보를 준다 · **T4 명령이 존재하지 않는다**.

### R2. 복구 드릴 (테스트 기능 ①) — Wave 2

- **Current:** 복구 절차가 **한 번도 점검된 적 없다.** 2026-08-06 실측에서 launchd 에이전트 5개가
  등록 해제된 채였고 아무도 몰랐다. **점검한 적 없는 복구 기능은 없는 것과 같다.**
- **Target:**
  1. **월 1회 자동 드릴** — 저부하 창에서 컨테이너를 의도적으로 중단시키고 T1 복구를 검증한다.
  2. 기록 항목: 중단 감지까지 걸린 시간 · 복구 완료까지 걸린 시간 · 그 사이 실패한 요청 수 ·
     복구 후 헬스체크 통과 여부. **`daily.jsonl` 에 누적**한다(추세로 봐야 열화를 안다).
  3. 드릴 실패 시 즉시 Telegram 긴급 — 드릴이 조용히 실패하면 감시의 감시가 다시 없어진다.
  4. **드릴 자체의 중단 스위치** — 운영 중 사고가 진행 중일 때 드릴이 겹치면 안 된다.
- **Acceptance:** 드릴이 스케줄대로 실행되고 결과가 시계열에 남는다 · 복구 소요 시간이 기록된다 ·
  드릴 실패가 알림으로 도달한다 · **드릴이 실사용 트래픽이 있는 시간에 실행되지 않는다**.

### R3. 병렬 스위치 — Wave 3

- **Current:** 2호기 개념이 코드에 없다. `API_REPLICA_COUNT` 미도입(Phase 75 W6-4),
  크론 리더는 수동 env(`CRON_ENABLED`), 공개몰 격리는 host 문자열 비교(부팅 로그 `격리=no`).
  **지금 2번째 노드를 띄우면 크론이 두 번 돌고 캐시가 두 벌이 된다.**
- **Target:**
  1. **스크립트 1개로 up/down.** 사람이 여러 단계를 기억해야 하면 새벽에 실패한다.
  2. **preflight 동일성 검사** — 양 노드의 빌드 SHA·마이그레이션 상태·env 해시가 같아야 기동한다.
     다르면 **기동을 거부**한다(운영에 없는 구성을 리허설하지 않기 위해).
  3. **매번 같은 아티팩트로 새로 만든다** — 2호기를 장기 존속시키지 않는다(주 2일 pet 은 반드시 어긋난다).
  4. **자동 복귀(fail-safe)** — 헬스체크 실패 · 크론 중복 감지 · `cl_waiting` 상승 중 하나라도 걸리면
     **사람 개입 없이 단독으로 되돌린다.** 그리고 되돌렸다는 사실을 알린다.
  5. **창 스케줄링** — 리허설 창은 Phase 75 W0-8 의 요일별 실측으로 정한다.
     **"주말"이라는 말로 정하지 않는다** — 토요일은 소매업 최대 매출일일 가능성이 높다.
  6. nginx upstream 2노드 + 드레이닝. 종료 시 진행 중 요청을 끊지 않는다.
- **선행:** Phase 75 **W6-1**(advisory lock 리더) · **W6-3**(격리 플래그) · **W6-4**(replica 예산).
  이 셋 없이 켜면 리허설이 아니라 사고다.
- **Acceptance:** 스크립트 1회 실행으로 병렬 전환·복귀 · preflight 불일치 시 기동 거부 ·
  헬스체크 실패 시 **자동 단독 복귀** · 전환/복귀 중 **판매 요청 실패 0건** ·
  크론 중복 실행 **0건**.

## Success Criteria (what must be TRUE)

- 노트북 없이 **T1~T3 복구가 가능**하고, 허용목록 밖 요청은 전부 거부·기록된다
- **T4 경로가 존재하지 않는다**
- 복구 드릴이 월 1회 자동 실행되고 **복구 소요 시간이 시계열로 쌓인다**
- 병렬 전환·복귀가 **스크립트 1회**로 되고, 실패 시 **자동으로 단독 복귀**한다
- preflight 불일치 시 기동을 거부한다
- 부하 생성기가 **재현 가능한 수치**를 내고, 단독·병렬 **양쪽 기준선**이 존재한다
- 리허설 1회가 G1~G5 를 자동으로 채우고 결과가 `daily.jsonl` 에 누적된다
- 전환·복귀·드릴 전 과정에서 **판매 요청 실패 0건 · 크론 중복 0건 · 기능 회귀 0**
- 리허설 데이터가 **운영 매출 집계를 오염시키지 않는다**

## 되돌리기 어려운 작업

- **R1 T3(호스트 재부팅) 구현** — 잘못 트리거되면 영업 중 전체 중단. 2단계 확인 + 레이트 리밋이 방어선
- **R3 자동 복귀 로직** — 잘못 만들면 정상 상태에서 계속 되돌리거나(플래핑), 반대로 사고 시 안 되돌린다
- **R4 쓰기 부하** — 운영 DB 에 실제 행을 만든다. 표식·정리 절차가 먼저 서야 한다
- **R2 드릴의 의도적 중단** — 실사용 트래픽과 겹치면 진짜 사고다. 창 판정이 선행
