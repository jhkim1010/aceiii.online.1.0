<objective>
매트릭스 여러 셀을 **한 번에** 보정하는 배치 엔드포인트를 만든다:
`POST /reports/stocks-cockpit/adjust-batch`.

Purpose: 이 기능의 위험은 "여러 개를 쓴다" 가 아니라 **화면이 낡은 값 위에서 절대값을
보낸다**는 데 있다. 사용자가 8을 입력하는 동안 판매가 일어나면, 서버는 그 판매까지
상쇄하는 보정을 기록한다(CODEX C1). 그래서 이 플랜의 본체는 배치가 아니라 **기준값 대조**다.
</objective>

<constraints>
- **항목마다 `expectedStock` 을 받는다.** 락 획득 후 `available` 과 대조해 하나라도 다르면
  **INSERT 를 시작하지 않고 409** + 충돌 셀 목록 반환(C1).
- **검증과 쓰기를 섞지 않는다** — ①검증 ②전 대상 락 ③기준값 비교 ④부모/소유/지점 검증
  ⑤전부 통과 후 INSERT. 앞쪽부터 쓰다 뒤에서 충돌을 발견하는 구현 금지(C2).
- 락은 **`product_id ASC, product_branch_id ASC`** 순서로 순차 획득(C3, CLAUDE.md 락 순서 규약).
  요청 배열 순서를 믿지 않는다. 중복 PB 는 400.
- 이론값은 **`stock_balances.available`** — `on_hand` 금지(예약분 포함, 운영 44건 불일치).
- 조회는 **집합 쿼리**로. 단일 로직을 루프로 N번 호출하지 않는다(C5).
  단 advisory lock 만 순차.
- 배치 상한 **50**, `realStock >= 0`, `note` 500자, 전 PB 가 요청자 store·선택 branch 소속인지
  집합 검증(C4).
- 권한은 기존 조정과 동일: `@Auth(admin, gerente, superadmin)`.
- 트랜잭션 안에서 외부 I/O 금지(CLAUDE.md).
</constraints>

<tasks>
1. DTO 신설 — 배열 크기·정수·중복·범위. class-validator 사용.
2. `stock_adjust_batches` 테이블 마이그레이션(수행자·store·branch·시각·note·항목 수) +
   `stocks` 에 nullable `adjust_batch_id`. ★ 기존 마이그레이션 파일을 고치지 말 것(C6).
   운영·로컬 **양쪽 적용**, owner 를 coolsistema 로(신규 테이블 규약).
3. 서비스 `adjustStockBatch()`:
   - PB 메타 집합 조회(`pb.id IN`) → store/branch/부모 검증 → 정렬 → advisory lock 순차
   - `stock_balances` 집합 조회 + 잔액 없는 PB 만 `GROUP BY` 폴백
   - `expectedStock` 전수 대조 → 불일치 시 409(아무것도 안 씀)
   - diff ≠ 0 인 항목만 다중 VALUES INSERT, 전 행에 같은 `batchId`
   - 응답: `{ batchId, adjustedCount, unchangedCount, totalAbsoluteDiff, items[] }`
4. 재시도 안전성 — `Idempotency-Key` 헤더(선택) + `(store_id, request_id)` UNIQUE,
   같은 키 재요청은 최초 결과 반환(C7). 판매 생성 경로의 기존 구현을 참고하되
   **판매 전용 테이블에 넣지 않는다**.
5. 기존 단일 `adjustStock` 은 그대로 둔다(Panel D 가 계속 쓴다).
</tasks>
