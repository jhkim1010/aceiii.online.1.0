<objective>
Build the QR 출퇴근 통제 (Fichaje/Asistencia) backend: two new isolated tables (`seller_attendance`,
`reseller_store_qr_auth`), the `attendance/` NestJS module (QR generation gated to Windows/macOS desktop,
role-routed punch, monthly report, admin adjust, reseller-auth revoke), the `RequireAttendanceGuard`
(vendedor clock-in gate) wired onto the existing `/mobile/*` work endpoints, the `RequireStoreAuthGuard`
skeleton (revendedor store-auth, activates with Phase 24), the caja-cierre force-close hook, and a
`clockedIn` field on `GET /mobile/me`.

Purpose: A single daily HMAC QR shown on the caja desktop, scanned by the mobile app, role-routes:
vendedor → attendance session toggle (entrada/salida); revendedor → permanent store-selling authorization.
Before clocking in, a vendedor is fully disabled. caja cierre force-closes open sessions.

Output: 1 migration (2 tables), 2 models, 2 utils (HMAC + store-TZ date), AttendanceService,
AttendanceController, 2 guards, DTOs, Jest specs, module wiring into app.module + cashRegister.module,
and additive guard/field edits on the Wave 1/2 mobile code.

CRITICAL ISOLATION MANDATE (criterion 8 — 소매/식당 무회귀):
- This wave creates NEW tables only. It performs NO `ALTER TABLE` on any existing table.
- The only edits to existing files are ADDITIVE: attaching `RequireAttendanceGuard` to mobile controllers,
  adding a force-close call inside `closeCashRegister`, and adding `clockedIn` to `getMe`.
- The caja-cierre hook is a NO-OP when there are no open sessions → retail/restaurant caja close is unaffected.
</objective>
