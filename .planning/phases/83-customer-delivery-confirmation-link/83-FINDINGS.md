# Phase 83 — 실측 (2026-08-17)

## 계기

Phase 82 를 계획하다 사용자가 물었다: *"모든 transporte 회사의 API 와 연결이 안 될 텐데
어떻게 배달이 완료되었는지 확인하지?"*

→ **운송사 연동은 없다.** `delivered_at` 은 직원이 Despacho 보드에서 누른 시각이다
(`deliverOrder()` … `by=${userName}`). 즉 지금의 "배달 완료" 는 **클릭 습관**이다.

사용자 제안: **고객에게 추적 링크를 보내 "OK(Confirma)" 를 받고, 잊으면 직원이 대행**한다.

## ★ 제안에서 뺀 것 하나

원안의 마지막 단계 — *"직원이 confirm → 그것에 대해 고객이 OK"* — 는 **스스로를 막는다.**
고객이 첫 번째를 안 눌러서 직원이 대행하는 건데, 그 결과를 다시 고객 OK 에 걸면
주문이 계속 열린 채 남아 **처음 문제로 돌아온다.**

→ **운영 종결**과 **증거 품질**을 분리한다:

| | 누가 | 목록에서 종결 | 증거 등급 |
|---|---|---|---|
| 고객 확인 | 고객이 링크에서 탭 | ✅ | **높음** |
| 직원 확인 | gerente/encargado | ✅ **즉시** | 중간 |
| 자동 | — | ❌ 하지 않음 | — |

직원 확인 뒤 고객에게는 **통지만** 보낸다 —
*"Registramos la entrega el 14/08. **Si no lo recibiste, avisanos.**"*
응답을 요구하지 않으므로 멈추지 않고, 고객이 "안 받았다" 를 누르면 **`En disputa`** 로 올라온다.
침묵 = 동의(전자상거래 표준 패턴).

## 자동 확인 금지 — 회계 경로 때문

신규 주문은 `shipOrder` 에서 매출이 확정되고 `deliverOrder` 는 물류 마일스톤만 찍는다.
**그러나 레거시 폴백(`mirrorSaleId == null`)은 여전히 매출·외상(`sale_credit`)을 만든다**
(`online-orders.service.ts:1206~1300`). "N일 뒤 자동 배달 처리" 가 그 경로를 건드리면
**아무도 안 누른 회계 기록**이 생긴다.

## 필요한 것

- 스키마: `delivered_confirmed_by`('customer'|'staff') · `delivered_confirmed_at`(클릭 시각) ·
  `delivered_on`(도착일, 직원이 입력 가능) · 분쟁 상태
  ★ `delivered_at` 하나에 "도착일" 과 "클릭 시각" 을 같이 담으면 **늦게 누른 만큼 지연으로 기록**된다
- 공개 페이지 + **추측 불가능한 토큰**(주문번호로 남의 주문을 열면 안 된다)
- WhatsApp 발송 — 이미 발급 흐름에 WhatsApp 이 있다(`PartialInvoiceModal`)
