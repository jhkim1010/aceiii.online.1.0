# Phase 115 — 수평 확장: 매장별 샤드(운용1 + 운용3) + N+1 대기(운용2) — 미래, 착수 조건 전엔 시작하지 않는다

등록 2026-10-17. 사용자와 대화로 정한 방향만 적는다. 설계는 착수 시점에 discuss 부터.

## 사용자 제안 (원문 요지)
1. 운용1·운용3 을 같이 쓴다 — 무거운 매장은 1, 가벼운 매장은 3. 하나가 죽으면 다른 쪽으로 합쳐 운행.
2. 보완안: 운용2 를 두어 1·3 의 데이터를 항상 복제하고, 하나가 죽으면 2 가 그 몫을 대행(N+1).

## 목표 구조
```
운용1 (매장 A군 primary) ──스트리밍 복제──┐
                                          ├─→ 운용2 (A군 replica + B군 replica, 평소 대기)
운용3 (매장 B군 primary) ──스트리밍 복제──┘
장애 → 운용2 가 죽은 쪽 클러스터만 승격. 살아 있는 쪽은 영향 없음
```
전환·복귀·부활 가드는 Phase(운용3 대기 서버, `scripts/standby/`)에서 실측된 것을 클러스터별로 재사용.

## 왜 지금이 아닌가 (2026-10-17 실측)
- 운용1 load average 0.18 / 8코어 · 낮 활동 사용자 대개 ≤10명 — 성능상 나눌 이유 없음.
- 장애 대비는 운용1 + 운용3(대기)로 이미 확보: 전환 55s · 복귀 90s · 부활 가드 실측(PLAN-2026-10-16-servidor-standby.md).
- 운용3 = 4코어·7GB, 운용1 = 8코어·32GB.

## 거부된 대안
- **운용3 에서 API 만 돌리고 DB 는 운용1** — 서버 간 왕복 **64ms**(운용3→운용1 TCP connect 실측). 판매 1건 쿼리 수십 개 → 건당 2~3초 증가 + 잠금 장기 점유.
- **멀티마스터(양쪽 쓰기)** — 시퀀스·`uq_sales_branch_daylocal_dn`·재고 원장 트리거와 충돌.

## 착수 전에 풀어야 할 것 (공사의 본체 = 「DB 를 둘로 쪼개기」)
- 공유 데이터: users(로그인)·stores·**global_clients(절대 불가침 — 분할/동기화 방식 자체를 사용자와 결정)**·reseller 스키마·관리자 콘솔·Pedidos 봇(agent@app).
- id 충돌: 샤드별 시퀀스 범위/간격 또는 전역 id. 나중에 합칠 때를 전제로.
- 라우팅: 로그인 시점엔 매장을 모른다 → 사용자→샤드 디렉터리 + 관문(nginx/API gateway).
- 전 매장 화면 재작성: 슈퍼어드민·admin-console·집계 배치(reseller stats 등)가 두 샤드를 조회.
- 매장 이동(A군↔B군) 절차, 백업·복원 2벌, 감시 2벌.

## 순서 (성능이 필요해질 때)
1. 무거운 **읽기**를 운용3 복제본으로(보고서·대시보드·admin-console·Power BI Phase 114·집계). 쓰기는 운용1. 주의: 복제 지연(방금 쓴 것 재조회 화면은 운용1), 긴 쿼리가 복제 반영을 밀어 RPO 를 늘리지 않게 statement_timeout.
2. 운용1 사양 증설.
3. 그래도 모자라면 이 Phase(샤딩 + 운용2 N+1).

## 착수 조건 (하나라도)
- 운용1 CPU 지속 > 60%
- 쓰기 경로(판매 생성 등) p95 > 300ms
- 운용1 한 대로 감당 못 할 매장 수/트래픽 전망
