# Phase 57 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder (from orchestrator):** this phase's *web* UI surface is exactly 2 touchpoints. Everything else in the 7 SPEC requirements (ESC/POS ticket layout, A4 PDF document layout) is fiscal-document rendering (print-agent HTML→PNG→ESC/POS, `pdfkit` A4), not web UI — it is referenced below only as a visual-parity source, not as something this contract governs pixel-by-pixel.

1. **Botón "A4 PDF"** (D-06 / R4) — `ventago-app/src/views/facturacion/EmitidasPanel.tsx` (row action) + `ventago-app/src/views/facturacion/PartialInvoiceModal.tsx` (POS, post-CAE success state, D-06 "tras F10").
2. **Selector Factura A/M** (D-08 / R5) — `ventago-app/src/views/admin/stores/details/components/ModalBranch.tsx`, visible only when `ivaCondition === 'RI'`.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (shadcn not applicable) |
| Preset | not applicable |
| Component library | MUI 5 — existing project-wide "materio" template (`ventago-app/src/@core/theme/*`) already in use by both touched files |
| Icon library | none introduced — both touchpoints use text-only `Button` labels, matching the existing sibling pattern (`CutTicketTab.tsx`'s PDF download button is also text-only, no icon) |
| Font | Roboto (project default, `theme.typography.fontFamily`) — unchanged |

**shadcn gate decision (auto-mode call, documented rather than asked):** `components.json` does not exist and this is a Next.js app, which would normally trigger the shadcn init question. Skipped deliberately: `ventago-app` is a mature production codebase fully built on MUI 5 (`@mui/material` + the "materio" admin template, ~150+ existing views). Introducing shadcn/Tailwind for a 2-button, 1-radio-group phase would create a second parallel design system inside one page tree (`ModalBranch.tsx` already imports `CustomTextField`/`FormDialog`/MUI `Grid` — a shadcn island next to them would look and behave inconsistently). Recommendation stands unless the user overrides it.

**Theme deviation — documented, not silent:** the project's `sketch-findings-ace-online` skill (dark navy `#1a1a2e` + gold `#f5a623`) is the validated direction for the **Phase 4 "new UI/UX" toggle surfaces** and the Phase 29 Mercadopago sketch suite — it is **not** the live theme of the pages this phase touches. Verified this session: `ventago-app/src/configs/themeConfig.ts` sets `mode: 'light'`, and `ventago-app/src/@core/theme/palette/index.ts` resolves `primary.main = '#05a7cf'` (materio cyan-blue), `error.main = '#EA5455'`, `warning.main = '#FF9F43'` in that light mode — not gold, not navy. `EmitidasPanel.tsx` and `ModalBranch.tsx` render today entirely inside this light materio theme (plain `Card`/`Table`/`FormDialog`). Forcing hardcoded dark-navy/gold hex onto 2 small elements inside those existing light-themed containers would be a visibly broken patch, not a design upgrade. **Contract below uses ambient MUI `theme.palette.*` tokens (via `color="primary"`/`color="error"` props), never hardcoded hex**, so the two touchpoints automatically stay consistent with whatever theme (light today, dark if the user later flips `themeConfig.mode`) is actually active — this is the correct application of "don't reinvent the palette," just anchored to the palette that is actually live on these two files today, not the aspirational one.

**One exception, reused not reinvented:** `ventago-app/src/views/facturacion/tipoBadge.ts::tipoBadgeColor(letra)` already exists in the codebase and already maps `M → '#f5a623'` (gold) / `A → '#2196f3'` (blue) / `B → '#7e57c2'` / `C → '#43a047'` / `E → '#26c6da'`, used today in `PartialInvoiceModal.tsx`'s preview `Chip`. Any letra-colored chip introduced by this phase (e.g. an A/M preview chip in `ModalBranch.tsx`) MUST reuse this helper — do not introduce a second letra→color map.

## Component States & Interaction Details

*(Extra precision beyond the template's required fields — for executor unambiguity, per the two touchpoints' exact call sites.)*

### 1. "A4 PDF" button — `EmitidasPanel.tsx`

- **Placement:** inside the existing Acción `TableCell` (`EmitidasPanel.tsx:66-80`), to the left of the current NC/ND buttons (or right — either order acceptable, but keep all 3 in the same `Box`/`Stack` with `gap: 1` / 8px, matching the file's existing header-row gap convention). Renders for **every** voucher row (NC/ND-issued or not) — unlike NC/ND (which hide once `v.notaCredito` is true), the A4 PDF button is always available per D-06 ("cualquier comprobante con CAE").
- **Idle:** `<Button size="small" variant="outlined" color="primary">PDF A4</Button>`.
- **Loading:** button `disabled`, label swaps to `"Generando…"` (matches `CutTicketTab.tsx`'s existing `pdfLoading` boolean pattern — reuse that exact state-machine shape: `setPdfLoading(true)` → fetch → `finally setPdfLoading(false)`).
- **Success:** blob download triggered immediately (see Data Contract below) — no modal, no confirmation, matches D-06 "abre/descarga el PDF" and the existing `CutTicketTab.tsx` precedent (`URL.createObjectURL` + synthetic `<a download>` click + `URL.revokeObjectURL`). No success toast needed (the file download itself is the confirmation, matching the existing PDF-download precedent in the codebase, which also does not toast on success).
- **Error:** inline `Alert severity="error"` rendered directly below the table (or as a `Snackbar`-adjacent row if per-row inline space is too tight — executor's call, but MUST be visible without scrolling away from the clicked row) **+** `toast.error(...)` simultaneously (never only one, per `feedback_error_visibility`).
- **Filename convention (recommended, not SPEC-mandated):** `factura-${v.tipoComprobante}-${String(v.puntoVenta).padStart(5,'0')}-${String(v.afipNumber).padStart(8,'0')}.pdf` — reuses the exact zero-padding already displayed in the same row (`EmitidasPanel.tsx:61-62`).

### 2. "Descargar PDF A4" — `PartialInvoiceModal.tsx` (POS, post-F10)

- **Current gap this touchpoint fills:** today, `onConfirm()`'s success path calls `onIssued()` immediately (`PartialInvoiceModal.tsx:45`), closing the modal with no chance for the user to grab the PDF. D-06 requires a POS-side A4 entry point "tras F10" — the contract is to insert a **success sub-state inside this same modal**, not a new separate screen (keeps the F10 keyboard-driven flow contained to one component).
- **New state:** `const [issued, setIssued] = useState<{voucherId:number; tipo:string; afipNumber:number} | null>(null)`. On successful `res.ok`, instead of calling `onIssued()` immediately, `setIssued({...})` and keep the `Dialog` open showing a success sub-view (replaces the `RadioGroup`/preview table content, keeps the same `Dialog`/`DialogTitle`).
- **Success sub-view content:** a `Chip` (letra, via `tipoBadgeColor`) + `Typography` **"Comprobante emitido — CAE obtenido"** + the "Descargar PDF A4" button (idle/loading/error states identical in shape to touchpoint 1, calling the same `GET /afip/vouchers/:voucherId/pdf` blob pattern) + a **"Continuar"** button that calls `onIssued()` (now deferred to this point instead of firing automatically).
- **Keyboard:** the existing `F10`/`Enter` global listener (`PartialInvoiceModal.tsx:56-67`) must be guarded so it does not re-trigger `onConfirm()` once `issued` is set (would attempt to re-emit) — `Esc` in this sub-state should map to "Continuar" (dismiss), not "Omitir" (there is nothing left to omit — CAE already issued).
- **Error (PDF fetch fails in this sub-state):** same inline `Alert` + toast pattern as touchpoint 1 — CAE issuance itself already succeeded (that's `res.ok`), so this error is scoped only to "PDF regeneration failed," never implies the sale/CAE needs retrying. Copy must not conflate the two: use the same "No se pudo generar el PDF…" text, not the CAE-issuance error copy already defined above for `error` state.

### 3. A/M selector — `ModalBranch.tsx`

- **Field:** `invoiceType` (new, maps 1:1 to `afip_issuers.invoice_type`), default `'A'`. Added to the existing `branchSchema`/`branchDefaultValues` (`./DataConfig`) and to the `onSubmit` payload sent to `PUT /afip/issuers/by-branch/:branchId` — same spread pattern already used for `invoiceSucursal` (`ModalBranch.tsx:106`).
- **Visibility gate (D-08, exact SPEC wording):** render **only when** the form's current `ivaCondition` value is `'RI'`. Since `ModalBranch.tsx` today only destructures `register/reset/handleSubmit/control/formState` from `useForm` (no `watch`), the executor MUST add `watch` to that destructure to read the live `ivaCondition` value for conditional rendering (cannot rely on `errors` or `control` alone for this). Placement: directly below the existing "Condición IVA" `CustomTextField` select (`ModalBranch.tsx:220-233`), inside the same `Grid item xs={6}` column or a new full-width `Grid item xs={12}` beneath it — executor's call on exact grid slot, but it must sit visually adjacent to the IVA field it depends on, not at the bottom of the unrelated fields list.
- **Control:** `RadioGroup` (not `Select`/dropdown) — exactly 2 mutually exclusive options, matches the SPEC's exact option copy (see Copywriting Contract above). Use `Controller` (react-hook-form) the same way `isMain`'s `Switch` is already wired (`ModalBranch.tsx:159-176`), since a plain `register()` doesn't give the controlled `checked`/`value` behavior a `RadioGroup` needs cleanly alongside conditional visibility.
- **Idle:** default value `'A'` pre-selected (matches DB column default) for both new-branch creation and any existing issuer loaded without `invoiceType` set.
- **No loading/error states of its own** — this field is part of the existing `ModalBranch` form submission; its error/success feedback is the existing form-level `toast.success('Sucursal actualizada')` / `toast.error('Ups, ocurrió un error')` (`ModalBranch.tsx:121,124`), unchanged. No new per-field async validation needed (`@IsIn(['A','M'])` is a synchronous backend DTO constraint, not something the frontend needs to probe live).
- **Hidden state:** when `ivaCondition !== 'RI'` (i.e. `'MONO'` or `'EXENTO'`), the field must not render at all (not just disabled/greyed) — matches SPEC acceptance criterion "el selector A/M no aparece para sucursal MONO/EXENTO" literally (a disabled-but-visible control would fail that criterion).

### Data contract for the PDF download (both touchpoints, identical shape)

Reuse the exact existing precedent from `ventago-app/src/views/talleres/cut-ticket/CutTicketTab.tsx` (already blob-download-tested in production):

```tsx
const resp = await apiConnector.get(`/afip/vouchers/${voucherId}/pdf`, { responseType: 'blob' })
const blob = new Blob([(resp as any).data ?? resp], { type: 'application/pdf' })
const url = URL.createObjectURL(blob)
const a = document.createElement('a')
a.href = url
a.download = `factura-${tipo}-${String(puntoVenta).padStart(5,'0')}-${String(afipNumber).padStart(8,'0')}.pdf`
document.body.appendChild(a)
a.click()
a.remove()
URL.revokeObjectURL(url)
```

Backend endpoint (`GET /afip/vouchers/:id/pdf`) already exists and already works end-to-end (`api-ventago/src/app/afip/afip.controller.ts:240-266`) — this phase's frontend work is 100% wiring, matching REQ-4's "pure frontend addition, low risk" characterization in `57-RESEARCH.md`.
