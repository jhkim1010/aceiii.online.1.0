# Phase 74: 백업 RPO 축소 · 복구 검증 — Specification

**Created:** 2026-08-06
**Source:** `74-CONTEXT.md` 운영 서버 실측 (2026-08-06)
**Scope:** Wave 1 ~ Wave 5 (결함 7건)
**Requirements:** 6 locked (R1~R6)

## Goal

**하루치 데이터를 잃지 않게 만들고, 백업이 실제로 복구된다는 것을 증명한다.**

현재 백업은 매일 03:17 에 돌고 Dropbox 까지 올라가며 정상 동작한다. 부족한 것은 두 가지다 —
**주기가 24시간**이라 장애 시각에 따라 그날 영업 전체가 사라지고, **한 번도 복구해 본 적이 없어**
그 덤프가 쓸모 있는지 아무도 모른다.

이 phase 는 신규 서버를 세우지 않는다. 기존 백업 위에 **연속 WAL**·**복구 리허설**·**실패 알람**·**암호화**를
얹어 RPO 를 24시간에서 수 초로, 복구 신뢰도를 "추정"에서 "실증"으로 옮긴다.

## Background

사용자 요청은 "안전성을 위한 병렬 서버"였다. 그러나 서버 2호기는 **서버가 죽는 것**을 막을 뿐,
잘못된 `DELETE` 나 논리적 손상은 2호기에도 그대로 복제된다. 그리고 현재 실측된 위험은
하드웨어 고장이 아니라 **RPO 24시간**이다.

POS 시스템에서 이것은 크다. 22:00 에 DB 가 깨지면 03:17 백업으로 돌아가야 하고,
그날의 판매·재고 이동·수금·현금 마감이 전부 사라진다. 매장은 그것을 종이 영수증으로 복원할 수 없다.

동시에, 백업 자체가 **검증된 적이 없다.** 파일이 매일 생기고 크기도 그럴듯하지만,
`pg_restore` 로 실제로 살아나는지, 205개 테이블이 다 들어 있는지 확인한 기록이 없다.
백업 운영에서 가장 흔한 실패는 "백업이 없었다"가 아니라 **"백업이 있는 줄 알았다"**이다.

여기에 조용한 실패 경로가 겹친다. 두 크론 모두 `>/dev/null 2>&1` 이라 cron mail 도 안 가고,
`dropbox_sync.sh` 의 `exit 1` 은 아무 데도 도달하지 않는다. rclone refresh token 이 만료되면
**아무도 모르는 채로** 오프사이트가 끊긴다.

다행히 조건은 좋다. `wal_level=replica` 가 이미 켜져 있어 **재시작 없이** 연속 WAL 을 받을 수 있고,
DB 가 작아(dump 2 MB) 리허설 비용이 사소하며, Telegram 알림 경로(`tools/uptime-watchdog.sh`)와
복구 검증에 쓸 불변식 뷰(`v_stock_balance_drift`·`v_stock_tenant_leak`)가 이미 존재한다.
**새로 만들 인프라가 거의 없다.**

## Requirements

각 요구사항 = 결함 1건 이상. **Current** = 현행(실측됨), **Target** = 목표, **Acceptance** = 완료 판정.

### R1. 연속 WAL 확보 — RPO 24시간 → 수 초 (결함 1) — Wave 3

- **Current:** `archive_mode=off`, `wal_level=replica`. WAL 이 체크포인트 후 재활용되어 사라진다.
  복구 가능 지점은 **매일 03:17 하나뿐**이다. 최악의 경우(03:16 장애) 약 24시간치 손실.
- **Target:**
  1. 물리 복제 슬롯 1개 생성 + **`pg_receivewal`** 을 systemd 서비스로 상시 실행해 WAL 세그먼트를
     `/var/lib/postgresql/pg_wal_archive/` 에 연속 수신한다. `--synchronous` 는 **쓰지 않는다**
     (운영 커밋이 수신기 지연에 묶이면 판매가 멈춘다 — 내구성보다 가용성을 우선).
  2. **`archive_mode` 는 건드리지 않는다.** 재시작이 필요하고, `pg_receivewal` 이 같은 목적을 달성한다.
  3. 기저(base) 백업 — 주 1회 `pg_basebackup` 을 `pg_wal_archive` 와 같은 보존 주기로 남긴다.
     논리 덤프만으로는 WAL 재생 시작점이 없어 PITR 이 성립하지 않는다.
  4. **디스크 안전판 필수** — `max_slot_wal_keep_size` 를 설정해(제안 10GB) 수신기가 죽었을 때
     슬롯이 WAL 을 무한 축적해 데이터 디스크를 채우고 **PostgreSQL 자체를 정지시키는 것**을 막는다.
     이 값을 넘으면 슬롯이 invalidated 되고 PITR 연속성만 끊긴다(서비스는 산다).
     이것은 `ALTER SYSTEM` + `reload` 로 적용 가능해 재시작이 필요 없다.
  5. WAL 아카이브 보존은 서버 14일 + Dropbox 업로드(R5 암호화 적용 후).
- **Acceptance:** `pg_stat_replication_slots` 에 슬롯이 active=true 로 존재 ·
  `pg_wal_archive/` 에 신규 세그먼트가 지속 생성됨 · `SHOW max_slot_wal_keep_size` 가 설정값 ·
  **재시작 이력 없음**(`pg_postmaster_start_time()` 이 작업 전후 동일) ·
  W4 리허설에서 "백업 시점 이후 임의 시각"으로 복구 성공.
- **위험:** 슬롯 축적 → 디스크 고갈 → **DB 정지**. 4번 안전판 없이는 착수 금지. 승인 게이트 대상.

### R2. 백업 내용 자동 검증 (결함 3) — Wave 1

- **Current:** 덤프가 매일 생성되지만 **내용을 검사하지 않는다.** 플래그 실수나 권한 문제로
  일부 테이블이 빠져도 파일 크기만 그럴듯하면 정상으로 보인다.
- **Target:**
  1. `pg_backup_ventago.sh` 말미에 `pg_restore -l` 목록 검사를 붙인다 —
     `TABLE DATA` 항목 수가 **기준선(현행 스키마 205개 테이블) 대비 하한** 밑이면 실패로 간주.
     하한은 고정 숫자가 아니라 "직전 성공 백업의 90%" 로 잡아 테이블 추가·삭제에 견디게 한다.
  2. `pg_restore -l` 이 아예 실패하면(손상 덤프) 즉시 실패 처리.
  3. 검사 결과를 `/var/lib/postgresql/pg_backups/verify.log` 에 남기고 R4 알람에 연결.
  4. **먼저 현행 덤프를 1회 수동 검사**해 기준선을 확정한다. 이미 반쪽이면 이 phase 의 최우선 사항이 바뀐다.
- **Acceptance:** 검증 단계가 크론 경로에 포함됨 · 정상 덤프에서 통과 ·
  일부러 손상시킨 덤프에서 실패 감지 · `verify.log` 에 항목 수 기록.

### R3. 복구 리허설 (결함 2) — Wave 4

- **Current:** 복구를 시도한 기록이 **0건**. RTO 를 아무도 모른다.
- **Target:**
  1. **격리된 임시 클러스터**(별도 포트, 제안 5435)에 최신 덤프를 `pg_restore` 한다.
     운영 클러스터(5434)·로컬 개발 DB(5432) **어느 쪽도 건드리지 않는다.**
  2. 복구된 DB 에서 검증 3종:
     - 주요 테이블 행수 대비 — `sales` · `sale_items` · `stocks` · `stock_balances` · `products` · `users`
     - **기존 불변식 뷰 재사용** — `v_stock_balance_drift` 0행 · `v_stock_tenant_leak` 0행
     - `globals_*.sql.gz` 복원 후 role(`coolsistema`) 및 시퀀스 owner 정상 여부
  3. R1 완료 후에는 **PITR 리허설**도 수행 — 기저 백업 + WAL 재생으로 "임의 시각"에 도달.
  4. 소요 시간을 측정해 **RTO 를 문서화**한다. 추정하지 않는다.
  5. 절차를 `74-RUNBOOK.md` 로 남긴다 — 실제 장애 시 이 문서만 보고 복구할 수 있어야 한다.
     문서는 스페인어 병기 없이 한국어로 쓰되, 명령은 복사해 붙일 수 있는 형태로 적는다.
  6. 리허설을 **분기 1회 반복**하도록 크론 또는 캘린더에 고정한다. 1회성 검증은 6개월 뒤 무의미해진다.
- **Acceptance:** 임시 클러스터에서 복구 성공 · 행수 대비 결과 기록됨 · 두 불변식 뷰 0행 ·
  측정된 RTO 가 `74-RUNBOOK.md` 에 기재됨 · 운영 DB 무영향(`pg_postmaster_start_time()` 불변, 연결 수 변동 없음).

### R4. 실패 알람 (결함 4·7) — Wave 2

- **Current:** 두 크론 모두 `>/dev/null 2>&1`. `dropbox_sync.sh` 의 `exit 1` 이 아무 데도 도달하지 않는다.
  백업이 며칠 실패해도, Dropbox 토큰이 만료돼도 **알 방법이 없다.**
- **Target:**
  1. 백업·업로드·검증(R2)·WAL 수신(R1) 실패 시 **Telegram 알림**.
     `tools/uptime-watchdog.sh` 의 `send_telegram()` 패턴과 자격증명 관리 방식(`.uptime.env`, gitignore)을
     그대로 따른다 — **새 알림 채널을 만들지 않는다.**
  2. **성공 침묵 원칙** — 성공 시 알림을 보내지 않는다. 매일 오는 성공 알림은 곧 무시된다.
  3. **부재 감지(dead man's switch)** — "실패 알림"만으로는 크론 자체가 안 도는 경우를 못 잡는다.
     최신 덤프 파일의 mtime 이 **26시간을 넘으면** 알림. 이 검사는 서버가 아닌
     **Mac(launchd)** 에서 돌린다 — 서버가 죽으면 서버 안의 감시도 같이 죽기 때문이다.
     `uptime-watchdog.sh` 와 같은 위치·같은 방식으로 붙인다.
  4. 크론에서 `>/dev/null 2>&1` 을 제거하고 스크립트 내부 로깅으로 대체한다.
- **Acceptance:** 백업 실패를 인위적으로 유발했을 때 60초 내 Telegram 수신 ·
  덤프 파일을 26시간 이상 낡게 만들었을 때 Mac 워치독이 알림 · 정상 운영 중 알림 0건(소음 없음).

### R5. 오프사이트 암호화 (결함 5) — Wave 5

- **Current:** 고객 개인정보·AFIP 세금 데이터를 담은 dump 가 **평문**으로 Dropbox 에 무기한 상주.
  Dropbox 계정이 침해되면 전 매장(CART·coolsistema·genius·ACE) 데이터가 통째로 나간다.
- **Target:**
  1. 업로드 **전** 단계에서 `age`(권장, 단일 바이너리·키 관리 단순) 또는 `gpg` 로 암호화한다.
     Dropbox 에는 `.dump.age` 만 올린다.
  2. **복호 키를 Dropbox 에 두지 않는다.** 키가 백업과 같은 곳에 있으면 암호화가 무의미하다.
     키 보관 위치를 `74-RUNBOOK.md` 에 명시하되 **키 값 자체는 저장소에 커밋하지 않는다**
     (Phase 65 W7 「저장소 평문 자격증명 0건」 원칙과 동일).
  3. **서버 로컬 14일 사본은 평문 유지** — 실제 복구 시 키 없이도 즉시 복구할 수 있어야 한다.
     암호화는 "서버 밖으로 나가는 사본"에만 적용한다.
  4. R3 리허설에 **암호화된 사본에서의 복구**를 1회 포함한다. 복호가 안 되는 백업은 백업이 아니다.
- **Acceptance:** Dropbox 에 평문 `.dump` 0개 · 암호화 사본에서 복구 성공 1회 ·
  저장소에 키 값 0건(스캔) · 서버 로컬 사본은 평문 유지 확인.

### R6. DB 밖 자산 백업 (결함 6) — Wave 5

- **Current:** `api-ventago/docker-compose.yml` 이 마운트하는 두 디렉터리가 백업 대상 밖이다.
  - `../certificados` → `/app/certificates` (RW) — **AFIP 인증서 + TA 토큰 캐시**. 재발급은 AFIP 절차라 즉시 복구 불가
  - `../manuales` → `/app/manuales` (ro) — Phase 26 매뉴얼 원본
  - `.env` — DB·Redis·Telegram·MP·AFIP 자격증명. **값은 백업하지 않되 항목 인벤토리가 없다**
- **Target:**
  1. `certificados` · `manuales` 를 일 1회 tar + 암호화해 같은 Dropbox 경로에 올린다.
     인증서에는 개인키가 있으므로 **R5 암호화 필수**(평문 업로드 금지).
  2. `.env` 는 **값을 백업하지 않는다.** 대신 "어떤 키가 필요한지" 목록만
     `74-RUNBOOK.md` 에 남긴다 — 신규 서버 구축 시 무엇을 채워야 하는지 아는 것이 목적이다.
     Phase 65 W7(자격증명 위생)과 충돌하지 않도록 값은 절대 기록하지 않는다.
  3. Redis 는 백업 대상 **아님** — socket.io pub/sub 전용이고 `--appendonly no` 로 이미 비영속이다
     (`api-ventago/docker-compose.yml`). 유실돼도 무방하다는 것이 설계 의도다.
- **Acceptance:** Dropbox 에 두 자산의 암호화 사본 존재 · 복구 리허설에서 인증서 복원 확인 ·
  `.env` 키 인벤토리 문서화(값 0건).

## 실행 순서

```
W1 (검증 기준선) ─┐
W2 (실패 알람)   ─┴→ 즉시 착수 가능 · 무위험 · 승인 불필요
                     ↓
W3 (연속 WAL) ── 승인 게이트: 복제 슬롯 디스크 위험
                     ↓
W4 (복구 리허설) ── W3 이후여야 PITR 까지 검증 가능
                     ↓
W5 (암호화 + DB 밖 자산) ── W4 와 병렬 가능하나 리허설에 1회 포함
```

**W1·W2 만으로도 실효가 크다.** 백업이 반쪽인지 알게 되고, 실패했을 때 알게 된다.
W3 착수가 늦어져도 이 둘은 먼저 끝낸다.

## Success Criteria (what must be TRUE)

- 최신 덤프의 `TABLE DATA` 항목 수가 기준선 이상 — **자동으로** 매일 검증됨
- 백업·업로드·검증·WAL 수신 실패 시 60초 내 Telegram 도달
- 덤프가 26시간 이상 갱신되지 않으면 **Mac 에서** 알림 (서버 밖 감시)
- 정상 운영 중 알림 0건 (소음 없음 — 소음은 알람을 죽인다)
- 복제 슬롯 active + `max_slot_wal_keep_size` 설정됨 + **PostgreSQL 재시작 0회**
- 임시 클러스터에서 복구 성공, `v_stock_balance_drift` / `v_stock_tenant_leak` **양쪽 0행**
- 측정된 RTO 가 문서에 기재됨 (추정 아님)
- Dropbox 에 평문 `.dump` 0개, 암호화 사본에서 복구 1회 성공
- AFIP 인증서 암호화 사본 존재 + 복원 확인
- **운영 서비스 무중단** — 전 과정에서 API·PostgreSQL 재시작 0회
- **앱 pool 무영향** — `pg_receivewal` 은 replication 연결, `pg_dump` 는 5434 직결.
  둘 다 pgbouncer(5432) 를 경유하지 않으므로 `pool_size=50` 예산에 영향 없음

| 복제 슬롯 생성 (R1) | 수신기 중단 시 WAL 무한 축적 → **디스크 고갈 → DB 정지** | `max_slot_wal_keep_size` 선설정 필수 · 디스크 여유 사전 측정 · 슬롯 lag 알람 |
| `ALTER SYSTEM` + reload (R1) | 오타 시 설정 파일 오염 | 변경 전 `postgresql.auto.conf` 사본 · reload 직후 `SHOW` 로 확인 |
| 크론 수정 (R2·R4) | 편집 실수로 **백업 자체가 멈춤** | 수정 전 `crontab -l` 사본 저장 · 수정 후 다음 실행 결과 확인까지 완료로 보지 않음 |

## 금지 사항

- **운영 PostgreSQL(5434) 재시작 금지** — `archive_mode` 를 켜고 싶은 유혹이 이 phase 의 가장 큰 함정이다.
  `pg_receivewal` 로 충분하다.
- **운영 DB 에 복구 시도 금지** — 리허설은 반드시 별도 포트의 임시 클러스터에서 한다.
- **로컬 개발 DB(5432) 를 리허설 대상으로 쓰지 않는다** — 사용자 작업 환경을 덮어쓴다.
- **`pg_dump` 를 pgbouncer(5432) 경유로 바꾸지 않는다** — transaction pooling 에서 세션 스냅샷이 깨진다.
  현행 5434 직결이 정답이다.
- **`--synchronous` 로 `pg_receivewal` 실행 금지** — 수신기 지연이 운영 커밋을 막는다.
- **성공 알림 추가 금지** — 매일 오는 알림은 무시되고, 무시되는 알림은 실패도 함께 묻는다.
- **애플리케이션 코드 변경 금지** — 이 phase 는 운영 스크립트·크론·문서만 다룬다.
