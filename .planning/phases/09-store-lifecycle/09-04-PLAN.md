# Plan 09-04: Session Guard 강화 + 만료 알림

**Phase:** 09-store-lifecycle
**Status:** Not started
**Depends on:** Plan 09-02, Plan 09-03
**Estimate:** 1일

## Goal

SUSPENDED/ARCHIVED 매장의 사용자 접근을 완전 차단하고, trial 만료 임박 시 알림을 전송한다.

## Scope (In)

### 백엔드 — 접근 차단
- `guards/session.guard.ts`:
  - sessionToken validation 시 Store JOIN으로 lifecycle_state 획득
  - `IN ('SUSPENDED','ARCHIVED','DELETED')` → 401 `STORE_SUSPENDED`
  - 응답 body: `{ code: 'STORE_SUSPENDED', state: 'SUSPENDED', message: '...' }`
- `auth.service.ts` 로그인 플로우:
  - 자격증명 검증 후 Store.lifecycle 체크
  - SUSPENDED/ARCHIVED → 로그인 거부 + 매장 상태 안내
- Store.transitionLifecycle() → SUSPENDED/ARCHIVED 전이 시 `active_sessions` 즉시 DELETE (이미 09-02에 포함)

### 프론트엔드 — 차단 안내
- `AuthContext.tsx`:
  - 응답 코드 `STORE_SUSPENDED` 감지 시 전용 모달 표시
  - 로그아웃 + `/login?reason=store_suspended` 리디렉트
- `LoginView.tsx`:
  - `?reason=store_suspended` 쿼리 감지 시 안내 메시지
  - "매장이 정지되었습니다. 결제 또는 관리자 문의가 필요합니다."
- `api.service.ts` 인터셉터:
  - 401 `STORE_SUSPENDED` 공통 처리

### 백엔드 — 만료 알림
- `store.cron.ts` 추가 cron:
  - `@Cron('0 9 * * *')` (매일 오전 9시)
  - 쿼리: `lifecycle_state='TRIAL' AND trial_ends_at BETWEEN now + 1d AND now + 7d`
  - 각 매장의 admin 유저에게 이메일 큐잉 (7일/3일/1일 각각 1회, 중복 방지 테이블 `trial_notifications`)
- 신규 테이블 `trial_notifications` (id, store_id, notification_type, sent_at) — 단순 dedup용
- superadmin용 일일 요약 메일: "오늘 trial 만료 임박 N건, 정지 M건"

### 이메일 템플릿
- `src/app/mail/templates/trial-ending.hbs` (7/3/1일 전 공용, 변수로 일수 전달)
- `src/app/mail/templates/store-suspended.hbs`
- `src/app/mail/templates/daily-admin-summary.hbs`

### 감사 로그
- Store의 `lifecycle_reason` + 전이 이력은 이미 Plan 09-02/03 에서 처리
- 추가: `auditoria` 모듈에 lifecycle 이벤트 기록 (기존 audit 모듈 재활용)

## Scope (Out)

- SMS/WhatsApp 알림 (추후 확장)
- 결제 게이트웨이 연동 (별도 phase)
- 자동 결제 갱신 (별도 phase)

## Success Criteria

1. SUSPENDED 매장 사용자가 기존 세션 토큰으로 API 호출 시 401 `STORE_SUSPENDED` 응답
2. SUSPENDED 매장 사용자가 로그인 시도 시 거부 + 안내 메시지
3. 매장이 ACTIVE → SUSPENDED 전이되면 모든 active_sessions 즉시 삭제
4. Trial 만료 7/3/1일 전 admin 이메일 자동 발송 (중복 없음)
5. superadmin에게 일일 요약 메일 발송 (만료 임박 + 정지 건수)
6. 모든 lifecycle 전이가 감사 로그에 기록됨
7. Pool 낭비 없음: session guard의 Store join은 단일 쿼리 내 처리

## Steps

1. `trial_notifications` 테이블 마이그레이션
2. `session.guard.ts` Store JOIN 추가
3. `auth.service.ts` 로그인 플로우 lifecycle 체크
4. 이메일 템플릿 3종 작성
5. 알림 cron 구현 (dedup 포함)
6. superadmin 요약 cron
7. 프론트 `STORE_SUSPENDED` 공통 처리
8. LoginView 안내 메시지
9. auditoria 모듈에 lifecycle 이벤트 소스 추가
10. E2E 테스트: 매장 정지 → 기존 세션 무효화 + 재로그인 차단 + 안내 표시

## Risks

- **Session guard 오버헤드**: 매 요청마다 Store JOIN → 캐시 or active_sessions 컬럼 denormalize 고려
- **이메일 발송 실패**: 큐 재시도 로직 필요
- **중복 알림**: `trial_notifications` 유니크 제약 `(store_id, notification_type)` 필수
- **시간대 이슈**: Store.timezone 고려하여 알림 시각 계산
