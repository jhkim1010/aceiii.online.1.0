<objective>
Enviado 보고서의 데이터를 만든다 — KPI · 구간 분해 · 3개 탭.

Purpose: Despacho 보드는 **지금**을 본다. 이 보고서는 **패턴**을 본다 —
얼마나 걸렸나 · 어디서 늦나 · 어느 운송사가 느린가 · 길에 묶인 재고가 얼마인가.
</objective>

<constraints>
- ★ **`shipped_at` 을 Enviado 의 정본으로 고정**한다. `dispatched_at` 도 있지만 둘을 섞으면
  두 숫자가 갈라진다(F1). 상수 파일 주석에 그 사실을 남긴다.
- ★ **정시 기준은 상수 하나**(`ON_TIME_MAX_DAYS = 5`). 화면·API·export 가 같은 값을 본다.
  이건 운송사의 약속이 아니라 **우리 내부 기준**이다 — 응답에 값을 실어 화면이 표기하게 한다.
- 취소 주문(`cancelled_at`)은 발송했더라도 **정시 계산에서 제외**한다(운영 9건 중 1건이 이 경우다).
- 날짜 경계는 매장 타임존으로 — `created_at::date` 를 그대로 쓰면 17% 가 어긋난다
  (메모리 `db-is-utc-so-today-needs-store-timezone`). 기존 리포트의 `TODAY_SQL` 규약을 따른다.
- `/api/reports/*` 는 Flutter 소비자가 있다 — **새 엔드포인트 추가만** 한다.
- 반품률은 만들지 않는다(데이터 없음 → 항상 0 인 칸이 된다).
</constraints>

<tasks>
1. `enviado.constants.ts` — `ENVIADO_TS = 'shipped_at'`, `ON_TIME_MAX_DAYS = 5`,
   `DELAY_WARN_DAYS = 3`, `DELAY_CRIT_DAYS = 7`. 각 값에 "왜 이 값인가" 한 줄.
2. `reportsEnviado.service.ts`:
   - `getKpis()` — 정시율(분모: 배달 완료, 취소 제외) · En tránsito(건수 + `SUM(total)`) ·
     주문당 배송비(+ 티켓 대비 %) · 배달까지 평균 일수. 기준값도 함께 반환.
   - `getStageBreakdown()` — 4구간 평균 일수(confirmado→preparado→despachado→transporte→entregado).
     ★ 각 구간은 **양쪽 타임스탬프가 모두 있는 주문만** 센다. 없는 것을 0 으로 채우면 평균이 낮아진다.
   - `getDemorados()` — 발송했으나 미배달, 경과일 내림차순 + 페이지네이션.
   - `getEnviados()` — 기간 내 발송 전체.
   - `getPorTransporte()` — 운송사별 건수·배달·평균일·정시율·미배달·배송비 합.
   - `getSinTracking()` — 발송됐는데 `tracking_code` 없음.
3. 컨트롤러 6개 GET. 권한 `@FunctionGuard('reporte-enviado', 'read')`.
4. 권한 시드 + 마이그레이션(운영은 시더 라우트가 없다 — Phase 80 과 같은 방식).
</tasks>
