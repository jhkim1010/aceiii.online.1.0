<objective>
설정 상태의 **덮어쓰기 위험**을 구조적으로 없앤다. 깜빡임보다 이쪽이 우선순위가 높다 —
71-FINDINGS F4 는 화면 문제가 아니라 **사용자가 저장한 설정이 사라지는 기능 결함**이다.

세 가지가 같은 뿌리다:
- `saveSettings` 가 전체 객체 교체형이라 낡은 스냅샷이 다른 변경을 되돌린다 (F6)
- `settingsContext` 의 복원 effect 가 한 함수 안에서 자기 결과를 덮는다 (F4)
- 반응형 교정 writer 가 `Layout.tsx` 와 `UserLayout.tsx` 두 곳에 있다 (F5)

Purpose: 로딩 표현을 아무리 다듬어도 상태가 서로를 덮으면 화면은 계속 튄다. 원인을 먼저 없앤다.
</objective>

<constraints>
- **`autonomous: false`** — 이 플랜은 사용자 확인 후 진행한다. `saveSettings` 는 호출부가 넓어
  시그니처 변경의 영향 범위를 먼저 합의해야 한다.
- **사용자의 layout 선택을 모바일 때문에 영구 변경하지 마라.** 현재 두 writer 모두 `settings.layout`
  자체를 `'vertical'` 로 써버린다. 데스크톱으로 돌아왔을 때 원래 선택이 남아 있어야 한다.
  → 저장값은 보존하고 **렌더 단계에서 `effectiveLayout` 만 계산**한다.
- `lastLayout` 을 쓰는 기존 로직(`Layout.tsx`)이 무엇을 보장하려던 것인지 먼저 파악할 것.
  단순 제거하면 데스크톱 복귀 시 레이아웃이 돌아오지 않는 회귀가 난다.
- 기존 호출부는 전체 객체 형태(`{ ...settings, k: v }`)로도 계속 동작해야 한다 —
  부분 업데이트를 **추가**하되 한 번에 전부 갈아엎지 않는다.
</constraints>

<tasks>
1. `saveSettings` 를 부분/함수형 업데이트로 확장한다.
   `Partial<Settings> | ((current: Settings) => Partial<Settings>)` 를 받아 `setSettings(current => ...)`
   안에서 병합·저장한다. Context value 는 `useMemo` 로 감싼다(CLAUDE.md 성능 규약).
2. `settingsContext` 초기 상태를 함수형으로 바꿔 **첫 렌더부터 저장값**을 쓴다 (F3).
   `typeof window === 'undefined'` 면 기본값 — SSR 안전.
3. 복원 effect 를 정리한다. `pageSettings` 병합은 함수형 업데이트로 바꿔 F4 를 없앤다.
   복원과 `pageSettings` 적용이 서로를 덮지 않는지 테스트로 고정한다.
4. `Layout.tsx` 에 `effectiveLayout` 을 도입한다 — `hidden ? 'vertical' : settings.layout`.
   렌더 분기는 `effectiveLayout` 으로 하고, **저장값은 건드리지 않는다.**
5. `UserLayout.tsx:139` 의 중복 교정 effect 를 제거한다. 교정이 정말 영구 저장돼야 하는 경우가
   있으면 `Layout.tsx` 한 곳으로 모은다.
6. hydration 경고가 나오는지 확인한다. 나오면 원인을 기록하고 쿠키 기반 전환(장기안) 필요 여부를
   판단 근거와 함께 남긴다 — 이번 phase 에서 쿠키로 넘어가지는 않는다.
</tasks>
