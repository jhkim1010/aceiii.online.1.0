<objective>
**QR 에 지점과 가격유형을 싣는다 — 하위호환을 깨지 않고.**

★★ **이 plan 은 「부가 기능」이 아니라 이 phase 의 구조적 한계를 실제로 줄이는 유일한 수단이다.**

`qr_print_log` 의 유니크 키는 `(branch_id, product_id, price_type_id)` **3개**인데
현재 QR URL 은 `s`·`p` **2개**만 싣는다(`print.service.ts:198, 311`).
그래서 89-04 의 공개 조회는 **「가장 최근에 인쇄된 아무 라벨」**을 고를 수밖에 없다 —
`printed_at DESC LIMIT 1` 은 모호성을 **없애는 것이 아니라 임의로 정하는 것**이다.
운영에 다중 행은 현재 0건이지만 **구조상 가능**하고, 그때 화면이 말하는 가격이
고객이 든 종이와 다른 라벨의 가격일 수 있다.

⤷ **`&b=`·`&pt=` 를 실으면 신 라벨에서는 3개 키가 다 채워져 그 행이 확정된다**
  (89-04 가 `labelMatch: 'exact-label'` 로 응답한다).
⤷ **구 라벨은 영원히 추정이다.** 이 plan 은 그것을 고치지 못한다 — 89-06 이 화면에
  「최신 인쇄분 기준」이라고 말하는 것으로 **드러낼 뿐**이다.

★ **`b`·`pt` 가 없어도 페이지가 동작해야 한다.** 이미 매장에 붙어 있는 라벨(운영
  `qr_print_log` 5행, 지점 6)이 그 상태다. 그것을 살리는 것이 이 phase 의 첫 가치이므로
  **필수로 만들면 안 된다.**

★ **추측하지 않는다.** 이 값들은 *지금 인쇄하는 지점·가격유형* 이다.
  `qr_print_log` 의 과거 값으로 유추하는 경로는 만들지 않는다 —
  근거 없는 귀속은 「모른다」보다 나쁘다.

Output: 두 QR URL 조립 지점에 `&b=`·`&pt=` 추가 + 회귀 시험.

private buildQrUrl(
  storeId: number,
  parentProductId: number,
  branchId?: number | null,
  priceTypeId?: number | null,
): string {
  const webBase = process.env.PUBLIC_WEB_URL || 'https://app.coolsistema.com';
  const opt = (clave: string, v: unknown): string => {
    const n = Number(v);

    return Number.isInteger(n) && n > 0 ? `&${clave}=${n}` : '';
  };

  return (
    `${webBase}/m/stock?s=${storeId}&p=${parentProductId}` +
    opt('b', branchId) +
    opt('pt', priceTypeId)
  );
}
