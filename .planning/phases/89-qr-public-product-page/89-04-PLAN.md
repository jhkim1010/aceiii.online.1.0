## ★ 이 API 가 **해결하지 못하는 것** (숨기지 말 것)

**한계 1 — 구 라벨에서는 어느 라벨을 스캔했는지 서버가 알 수 없다.**
`qr_print_log` 의 유니크 키는 `(branch_id, product_id, price_type_id)` **3개**인데
현재 URL 은 `s`·`p` **2개**만 싣는다(`print.service.ts:198, 311`). 따라서 구 라벨에서는
`printed_at DESC LIMIT 1` 로 「가장 최근 인쇄분」을 고를 수밖에 없다 —
그것이 **스캔한 그 라벨이라는 보장은 없다.** 최신 1건 규칙은 모호성을 **없애는 게 아니라
임의로 정하는 것**이다. 운영에 다중 행은 현재 0건이지만 구조상 가능하다.
⤷ 응답의 `labelMatch` 가 이 차이를 **드러낸다**. 89-07 이 `&b=`·`&pt=` 를 실어
  **신 라벨에서만** 모호성을 실제로 없앤다. 구 라벨은 영원히 추정이다.

**한계 2 — 숫자 ID 열거를 막지 못한다.**
`?s=6&p=1` 은 연번이고, 서버는 요청자가 실물 라벨을 들었는지 구분할 수단이 **없다**.
「목록 UI 가 없다」는 API 열거 방지가 아니다. `@Throttle` 은 속도를 늦출 뿐이다.
⤷ **부분 완화만 한다**: 공개몰을 안 켠 매장(`stores.slug IS NULL`)에서는
  **인쇄 기록이 있는 상품만** 상세를 내보낸다(아래 자격식). 인쇄된 적 없는 상품은
  연번을 순회해도 안 나온다. **인쇄된 라벨의 연번 열거 자체는 못 막는다.**
  불투명 토큰은 이 phase 범위 밖 — 후속 후보로 89-09 SUMMARY 에 기록한다.

★ 위 둘을 「해결했다」고 쓰면 거짓이다. plan·코드 주석·SUMMARY 에 한계로 남긴다.
