<objective>
Phase 38 백엔드 델타 계층: 신규 `qr_print_log` 테이블 + `QrPrintLog` 모델 + `PrintService` 델타 로직
2종(`getPendingQrDelta`, `markQrPrinted`) + 이를 노출하는 `PrintGateway` WebSocket ack 핸들러 2개
(`get_qr_pending`, `mark_qr_printed`). 지점별(D-4) 델타 추적의 원천.

Purpose: 운영자가 price-type 하나를 고르면, 마지막 출력 이후 신규(NUEVO)이거나 이름/가격이 바뀐(CAMBIO)
codigomadre parent 상품만 골라 반환한다(D-3). 출력 성공분만 스냅샷 upsert 되어(D-11) 다음 델타에서 빠진다.
store/branch 는 API key 에서 서버가 도출하므로(D-6) 클라이언트는 다른 매장을 넘볼 수 없다(IDOR 안전).

Output: 멱등 마이그레이션 1개(로컬 PG18 적용), `QrPrintLog` 모델, `PrintService` 델타 2메서드 +
base-price fallback, `PrintGateway` ack 핸들러 2개, `print.module` 모델 등록, Jest 스펙.

DECISION — 전송 계층은 REST 가 아니라 **WebSocket ack(emitWithAck)** 다. zebra-agent 의 유일한 인증
채널은 `/print-agent` 소켓이며, API key 는 `handleConnection` 에서 검증되어 `client.data.branchId` 로
고정된다. 기존 에이전트 데이터 요청 3종(`get_price_types`/`get_branches`/`get_stock_today`)이 전부 이
ack 패턴이고, print.controller 는 웹 패널 전용 JWT 가드(`@UseGuards(AuthGuard('jwt'))`)라 에이전트
API key 를 처리하지 못한다. 따라서 REST `GET /print/qr/pending` 대신 gateway ack `get_qr_pending` 로
구현한다 — 설계의 "API key 도출 branch/store, IDOR 안전"(D-6)을 재발명 없이 그대로 실현한다. 델타
데이터 계약(pending 리스트, mark-printed)은 REST 안과 동일하다. (기존 웹 `@Post('qr')` per-product
emit 은 폐기된 선행 흐름이며 본 배치 델타와 무관 — 건드리지 않는다.)
</objective>
