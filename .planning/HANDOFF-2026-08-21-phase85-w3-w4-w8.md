## ★★ 오늘 찾은 것 중 가장 중요한 것 — 소켓 rate-limit

게이트웨이 3개가 접속 제한 키로 `client.handshake.address`(TCP peer)를 썼다.
**nginx 뒤에서 그 값은 모든 클라이언트가 동일**하다(도커 브리지 172.18.0.1).
그래서 `SOCKET_CONNECT_LIMIT`(60/분)이 IP별 한도가 아니라 **전 매장 공용 버킷 하나**였다.

- 가용성 — 배포 후 전 클라이언트가 동시에 재연결하면 **61번째부터 거부**(`auth_error` + 강제 종료).
  12매장에서는 안 걸렸지만 300매장에서는 확실하고, 하필 **개점 시각**에 드러난다.
- 보안 — 브루트포스 백스톱인데 공격자를 분리 못 한다. **한 명이 60회를 태우면 전 매장이 막힌다.**

★ 이 저장소는 2026-08-11 에 같은 부류를 고치며 `trustedClientIp()` 를 단일 출처로 만들어
  뒀는데 **소켓 게이트웨이만 그것을 안 쓰고 있었다.** 헤더는 정상 도달한다 —
  `branch_ip_registries` 에 공인 IP(179.0.236.82 등)가 기록돼 있는 것이 증거다.

## W5/W6 착수 전 codex 자문 결과 (2026-08-21)

**codex 는 "오늘 둘 다 하지 말고, 전체 우선순위는 W5 가 먼저" 라고 했다.**

### W5 를 그대로 시작하면 첫 삽에서 막힌다
- `docker-compose.yml` 의 `container_name: api_ventago` 와 `ports: 5002:5002` 때문에
  **green 컨테이너가 아예 뜨지 않는다**(이름 충돌 · 포트 점유). nginx 에는 upstream 블록도 없고
  `proxy_pass http://127.0.0.1:5002` 가 하드코딩돼 있다.
  → compose project·컨테이너명·호스트 포트를 분리하고 nginx 가 active 를 가리키게 해야 한다.
- blue+green 동시 가동 = PM2 4워커 × pool 20 × 2 = **앱 측 커넥션 160** (pgbouncer pool 50).
  swap 0 인 호스트에서 Jenkins 빌드까지 겹친다 → 리허설에서 build peak RSS · 두 컨테이너
  동시 RSS · pgbouncer 대기시간을 **측정하고 시작할 것.**
- ★ **"WebSocket 이 한 번도 안 끊기는 무중단" 은 불가능하다.** 연결은 handshake 때 고른
  컨테이너에 수명 동안 고정된다. Redis 어댑터는 broadcast 를 중계할 뿐 연결을 옮기지 않는다.
  현실적 목표: **HTTP 무중단 + 신규 연결은 green + 기존 소켓은 제한 시간 drain 후 재연결.**
- nginx `/socket.io/` 의 `proxy_read_timeout 86400` 때문에 old 소켓은 최대 하루 남을 수 있다.

### W6 에서 가장 틀리기 쉬운 곳
- **MinIO 는 JSON 에 key 를 넣는 것만으로 백업이 아니다.** 객체가 삭제·덮어쓰기되면 복구
  불가다 → 객체 manifest + 존재/해시 검증 + 별도 version 또는 불변 사본이 필요하다.
- **시퀀스**: 새 ID 로 전면 재매핑이면 건드리지 않는다. 원 ID 보존 방식이면 각 sequence 를
  복원된 최대값보다 크게 `setval` 해야 한다.
- 이미 있는 것: `store.service.ts` 의 백업본 복원 경로. **내보내기 쪽은 미확인.**
