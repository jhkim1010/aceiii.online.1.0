## 4. ★★ 이 세션에서 배운 것 (같은 형태가 또 온다)

### ① 「아무도 안 잃는다」는 **절반**이다 — 누가 얻는지를 세라

5단계 시드를 `admin` 앱 아래에 두려 했다. CODEX 가 HIGH 로 짚었고 **실측이 맞다고 했다**:

- 권한은 위로 전파된다: 기능 1개 → 모듈 보임 → **앱이 `user.structure` 에 들어감**.
- 운영 실측: **120개 역할 중 27개가 `admin` 앱을 못 본다**.
- `allowedApps={['admin']}` **하나로만** 열리는 화면이 **32개** — `/configuracion/permisos`
  (권한 배분 화면!) · `/admin/tiendas` · `/admin/tenants` · `/configuracion/facturacion`.

⤷ 「매뉴얼 보기」를 심는 일이 **판매원에게 권한 배분 화면을 여는** 일이 될 뻔했다.
⤷ 기존 앱 중 **범용인 것이 없다**(그 앱이 없는 역할 수): reportes 8 · talleres 11 ·
  venta 19 · producto 23 · materia-prima 27 · admin 27. → 전용 앱 `herramientas` 로 해결.

### ② 숫자 방어는 「덜 실려 옴」만 막는다 — 「안 시킨 것」은 못 막는다

6단계에서 `conFuncion(…, true)` 가 조건 없이 기본값으로 **교체**했다. 이미 켜져 있던
기능의 액션이 사라졌는데 **서버에서 안 보인다** — 클라이언트가 그 회수를 정직하게
선언하고 서버가 같은 수를 계산하니 숫자가 맞아 통과한다.
⤷ 「켜기 ≠ 초기화」. 그리고 **지도를 못 읽으면 저장을 막는다**(경고만으로는 부족).

### ③ 숫자는 **동시성 제어가 아니다**

A 가 `update` 를, B 가 `delete` 를 빼면 **둘 다 「1건」**이다. A 가 먼저 쓰고 B 가
낡은 화면으로 쓰면 수가 맞아 통과하고 **A 의 회수를 되돌린다.** 행 잠금은 순서만
정할 뿐 내용을 비교하지 않는다. → `baseState`(읽은 상태 전문)를 잠금 안에서 대조.
★ 해시가 아니라 **전문**이다 — 충돌 하나가 「조용히 되살아난 권한」이 된다.

### ④ 검증 블록이 없으면 마이그레이션은 **멱등처럼 보인다**

`ON CONFLICT (role_id, function_id, store_id)` 가 **`store_id NULL` 인 전역 역할 4개**
에는 안 걸린다(PG 에서 NULL 둘은 안 부딪힌다). 두 번째 실행에 15행이 중복으로 들어갔고
**끝의 DO 블록이 잡았다.** → `IS NOT DISTINCT FROM`.

★★ 그리고 **재실행 가드가 처음엔 거짓말이었다** — 「변경 없음」을 찍기만 하고 안 봤다.
  실측: 부여 1건을 지우고 재실행했더니 **되살려 놓고** 변경 없다고 보고했다.

### ⑤ 「검사가 3중」이어도 같은 조건이면 한 겹이다

매뉴얼이 **없는 키 3개**(`F8`·`Re Pág`·`Av Pág`)를 안내하고 있었다. 감시가 「코드 ↔ 목록」
두 겹이었는데 **둘 다 매뉴얼을 안 봤다.** → `pos-shortcuts-sync` 에 세 번째 축 추가.

## 5. 도구·방법 메모

- **BSD `sed` 는 `\s` 를 모른다.** 가드 계약을 세다가 또 밟았다 — 219건이 잡힌 줄
  알았는데 정규식이 대부분 실패하고 원문이 그대로 통과했다. python 으로 다시 셌다(214).
- **`prettier --write` 를 파일 전체에 돌리지 말 것.** `auth.service.ts` 에서 **내 줄 밖
  102줄**을 건드려 되돌렸다. 내가 통째로 새로 쓴 파일만 포매터에 맡기고, 나머지는 손으로.
  (커밋 게이트가 이 세션에서 lint 를 **4번** 막았다 — 전부 유효했다.)
- **커밋 게이트는 `git add X && git commit` 을 거부한다.** add 를 따로 실행할 것.
- `codex exec` 는 파일 3개까지. 두 갈래로 나눠 병렬로 띄우면 한 번에 끝난다.
- 운영 마이그레이션은 **`BEGIN; … ROLLBACK;`** 으로 먼저 돌려 검증 블록 출력을 본 뒤
  `--single-transaction` 으로 실제 적용했다. 예상치와 정확히 일치했다.

## 6. ★ 미해결

1. **(B) 매장 관리자 전용 앱** — 사용자 제안(2026-09-24). `/configuracion/*` 과
   `/admin/*` **32개 화면**이 지금도 `allowedApps={['admin']}` 만으로 열린다.
   cashier·accountant·viewer 는 admin 기능이 있어 **지금도 URL 로 도달 가능**하다
   (API 는 별도로 막지만 화면은 뜬다). 이 화면들은 **모듈도 기능도 없다** — 권한 체계에
   아예 존재하지 않는다.
   ⤷ 사용자 결정: (A) 도구 4개를 먼저 배포하고 **(B) 는 다음으로**. 그 (A)는 끝났다.
   ⤷ 착수 시 주의: 잘못 조이면 **관리자가 자기 설정 화면에서 잠긴다.** 따로 재고 따로 배포.

2. **Repaso(Ctrl+R) 가 판매 때마다 시계 화면으로 바뀐다** (앞 핸드오프 §5-1).
   코드 조사는 **끝났고 배제 완료**: `setReviewMode(false)` 경로 4개 전부 사람이 눌러야
   하는 것 · 패널은 `saleCreated` 로 목록만 갱신 · `WithAccess` 의 `user` 는 판매 후
   안 바뀜(`setUser(null)` 은 최초 로드와 로그아웃뿐, `refreshUser()` 호출부 0) ·
   `StoreConfigContext` 의 `loaded` 는 `storeId` 변경 때만 내려감 · 전체 새로고침 없음.
   ⤷ **다음은 읽는 게 아니라 재는 것.** 그 매장 화면(NOIX 등)에서 순서대로:
     ① 콘솔에 `sessionStorage.v=(+sessionStorage.v||0)+1; window.__vida=Date.now()` 를
       붙여 두고, 증상 뒤 `window.__vida` 가 `undefined` 면 **새로고침된 것**.
     ② 새로고침이 아니면 Network 에서 `/auth/me` + 청크가 다시 나가는지 → 재마운트 여부.
     ③ 둘 다 아니면 `window.__k=[]; addEventListener('keydown',e=>window.__k.push(e.key),true)`.
   ⤷ ★ 먼저 **지금 빌드에서도 재현되는지** 확인할 것. 그 사이 배포로 사라졌을 수 있다.

3. **수표 중복을 서버가 막지 않는다** (앞 핸드오프 §7-2). 조사만 해 뒀다:
   · 쓰기 경로는 `ChequesService.createFromSale` **하나뿐**(`sales-create.service.ts:2584`).
   · 프론트 규칙은 `bank|number`(소문자·trim)로 이미 확정 — 같은 판매 안에서만 막는다.
   · 운영 수표 **2건**, 중복 0건 → UNIQUE 인덱스를 걸기엔 지금이 가장 싸다.
   · ★★ **함정**: `nullifySale` 은 수표를 **안 건드린다**(그 함수 안에 `cheque` 0건).
     그냥 UNIQUE 를 걸면 **판매를 무효화한 뒤 같은 수표를 다시 못 받는다.**
     → 먼저 「무효화 시 수표를 어떻게 할지」를 정해야 한다(상태 전이 or 부분 인덱스).

4. **같은 이름 descuento 를 말없이 거부** (앞 핸드오프 §7-3).
   `InvoiceAditional.tsx:547` `if (discounts.some(d => d.name === discountName)) return;`
   ★ **recargo 에도 같은 줄이 있다**(`:564`) — 핸드오프는 descuento 만 적었다.
   ★ 조용히 돌아가는데 패널은 **열린 채 남고** `handleAdjustKeyDown` 은 `focusSku()` 를

5. **프로비저닝 경로 결함 2건** (앞 핸드오프 §7-1) 그대로. `provisionStoreAndOwner` 가
