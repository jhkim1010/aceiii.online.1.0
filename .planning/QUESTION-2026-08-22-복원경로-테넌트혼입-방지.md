## 2. 실측 결함 B — 복원이 남의 매장을 가리키는 FK 를 만든다

복원은 FK 컬럼 값을 **그대로 복사**한다(대상 테이블은 복원하지 않으면서).
FK 그래프 전수 대조 결과 13종:

```
sale_items.product_id            -> products.id            (원본 매장 상품)
sale_items.promotion_id          -> product_promotions.id
sale_payment_methods.payment_method_id -> payment_methods.id
sale_payment_methods.option_id   -> payment_methods_options.id
sales.store_client_id            -> store_clients.id
sales.seller_id / clients.seller_id -> Sellers.id
sales.online_order_id            -> online_orders.id
sales.table_id                   -> restaurant_tables.id
sales.province_id / clients.province_id -> provinces.id     (전역 참조 — 이건 정상)
terminals.thermal_agent_id / zebra_agent_id -> branch_agents.id
```

원본 매장이 살아 있으면 → **새 매장의 판매 항목이 원본 매장 상품을 가리킨다.**
원본이 지워졌으면 → FK 위반으로 트랜잭션 전체가 터진다.
Phase 69 가 런타임에서 막은 테넌트 격리를 **복원 경로가 스스로 뚫는다.**

## 4. 실측 결함 D — 마스킹한 NOT NULL 컬럼은 복원을 터뜨린다

백업은 자격증명을 `null` 로 마스킹한다. 그중 **6개가 NOT NULL** 이다:

```
mp_accounts.access_token NOT NULL      mp_accounts.refresh_token NOT NULL
commerce_channels.channel_key NOT NULL commerce_channels.secret NOT NULL
wp_channels.channel_key NOT NULL       wp_channels.secret NOT NULL
```

복원이 이 테이블을 담기 시작하는 순간 NOT NULL 위반 → **단일 트랜잭션이므로 복원 전체가 실패**한다.

## 6. 내가 제안하는 설계

- **D1 — 소유권 권위를 관계로 바꾼다.** 인벤토리 재생성이 `store_id` 컬럼 스캔이 아니라
  **`stores` 로부터의 FK 도달 폐포**를 계산한다. 도달하는 테이블은 전부 "담김" 또는
  "이유 붙은 제외" 둘 중 하나여야 하고, 아니면 spec 실패.
- **D2 — 복원을 FK 그래프 기반 제네릭 엔진으로.** 런타임에 `information_schema` 에서
  FK 를 읽어 위상 정렬 → 테이블별 PK 재매핑(old→new) → 모든 FK 컬럼 재작성.
  (문서 `db-schema-fks.md` 를 런타임 근거로 쓰지 않는다 — 낡는다.)
- **D3 — 강제 지점: FK 컬럼별 처리 선언.** 복원 대상 테이블의 **모든** FK 컬럼은
  `REMAP`(복원 대상) / `KEEP`(전역 참조: provinces·functions·apps…) / `NULL`(복원 안 하는
  테넌트 테이블) 중 하나로 **선언돼야 하고, 미선언이면 spec 이 실패**한다.
  → "남의 매장을 가리키는 값을 그대로 복사" 가 **컴파일/테스트에서 불가능**해진다.
- **D4 — 커밋 전 테넌트 불변식 검사.** 복원 트랜잭션 안에서 교차참조 검사를 돌리고
  1행이라도 나오면 롤백.
- **D5 — 자격증명 NOT NULL 테이블은 "복원 불가" 로 선언**(재인증 필요). 조용히 빈 값을 넣지 않는다.
- **D6 — 부분 복원 금지.** 단일 트랜잭션 유지.
