실측하니 **12개**였다(`DEFERRED_FK_COLUMNS` 와 FK 카탈로그가 같은 컬럼을 둘 다
주장하는 10개를 안 셌다). **결론은 같지만 더 강해졌다 — 결과가 달라지는
우선순위 쌍이 0개**, 즉 7단계 사다리가 아무것도 결정하지 않고 있었다.

2R 에서 codex 도 스스로 정정했다(테넌트 가드 34 → **35**). 내 문장 세 곳도
34·24·24 로 갈라져 있었다.

### 적용한 것

| 무엇 | 결과 |
|---|---|
| 우선순위 **전부 제거** → 후보 수집 + 구조적 동등성 | 0개면 실패 / 1개면 채택 / 2개+ 는 같을 때만 근거 병합 |
| `source: string` → `sources: string[]` | 이긴 쪽만 남고 진 쪽이 사라지던 것 |
| **암묵적 fallback COPY 제거** | `SCHEMA_PLAIN_VALUE_COLUMN` 을 카탈로그에서 명시 생성 |
| `id` 를 이름 → **카탈로그 사실**(PK+default)에서 유도 | 두 번 좁혔다(단순 default 오탐 13 · 복합 PK 자연키) |
| 숫자를 문장에 안 박는다 | 재생성 스크립트가 세고, spec 은 `> 20` 대신 **정확히 35** |

### ★ 바꾸자마자 실제 결함 둘을 잡았다

1. `branch_agents.socket_id` 를 한쪽은 `RESET(null)`, 다른 쪽은 `CLEAR` —
   **뜻은 같은데 어휘가 둘**이었다 → "비운다" 를 한 이름으로 합침
2. **`stores.slug_canonical` 은 `GENERATED ALWAYS AS` 컬럼**이라 INSERT 자체가
   안 되는데 내가 `SERVER_IDENTITY`("서버가 값을 골라 쓴다")로 선언해 뒀다
   → `OMIT` 액션 신설, 카탈로그의 `GENERATED` 표시에서 유도

## ★★★ ② 범위 재조정 — 이 세션의 핵심

사용자: **"복원이 왜 잠겨있지? codigos(SKU) 만 복원하는 것으로 하면 그리 어렵지 않은데"**

### 잠근 이유는 어려워서가 아니었다

기존 복원 버튼이 **이미 틀린 데이터를 만들고 있었다** — 백업 119개 중 13개만
되돌리며 `"성공"` 반환 + FK 를 그대로 복사(복원된 매장이 원본 매장 상품을 가리킴).

**그런데 그 다음에 내가 한 선택이 문제였다: 백업이 152개를 담으니 복원도 152개를
되돌려야 한다고 범위를 백업에서 물려받았다.** 그건 요건이 아니었다.
(메모리 `blocked-means-question-the-requirement.md` 가 정확히 이 형태다.)

### 실측 차이

|                | 전체 복제 | **카탈로그만** |
|----------------|---------:|-------------:|
| 테이블          | 152      | **15**       |
| 컬럼            | 1,826    | **145**      |
| FK 컬럼         | 351      | **29** (11개가 store_id) |
| 트리거          | 58       | **9**        |
| UNIQUE(비PK)    | 83       | **13 — 전부 매장 범위** |
| 거부(REJECT)    | 5        | **0**        |

★ 어려웠던 것이 **대부분 범위 밖**이었다: `audit_logs` 다형 참조 · 캠페인 재발송 ·
카하 자동마감 · AFIP/MP 외부 식별자 · `users.email` 전역 충돌.
**감사 트리거 억제(codex 가 "첫 확정 블로커" 라 한 것)도 필요 없어진다** —
전체 복제는 가짜 감사로그 5,652행이지만 카탈로그만이면 **약 100행**이다.

### 사용자 결정 둘

1. **같은 매장으로 복구** (`CATALOG_IN_PLACE`)
2. **152개용 선언·검사는 남겨두고 범위만 좁힌다**

### ★ 같은 매장이라 문제의 성질이 바뀐다

`store_id` 가 **재매핑이 아니라 `VERIFY_SAME_STORE`** 다 — 값이 같아야 하고
다르면 남의 매장 데이터다. CLONE 의 `DESTINATION_STORE`(새 매장 ID 를 써 넣는다)와
**정반대 판정**이다.

→ **핵심 문제가 재매핑에서 "기존 행과의 충돌" 로 옮겨간다.**

### 만든 것

`store-restore-scopes.ts` + spec 12개:
- 범위 15개 테이블 선언(각각 이유)
- 범위 **밖**을 가리키는 FK 16개 전부 선언 (`VERIFY_SAME_STORE` 11 ·
  `VERIFY_EXISTS_IN_STORE` 1 · `KEEP_GLOBAL` 4)
- 범위 안 UNIQUE 가 전부 매장 범위임을 강제
- 예외 하나를 이유와 함께: `ProductBranch (product_id, branch_id)` 는 `store_id` 를
  글자로 안 쓰지만 두 컬럼 다 매장에 매여 있고 `tenant_chk_productbranch_same_store`
  가 DB 에서 일치를 강제한다

대조군 3종 확인(선언 삭제 · 판정 바꿔치기 · 범위에 `sales` 혼입).

## ★ 다음 — 먼저 정해야 할 것 (사용자 답변 대기)

**같은 매장 복구의 충돌 정책**: 대상 매장에 이미 그 SKU 가 있으면 무엇이 이기나.

| 안 | 내용 | 위험 |
|---|---|---|
| **추가만** (내 추천) | 없는 것만 넣고 기존 행은 **건드리지 않는다** | 값이 망가진 상품은 안 고쳐진다 |
| 덮어쓰기 | 백업 값으로 기존 행을 갱신 | 판매가 참조 중인 상품을 바꾼다 |
| 선택 | 사람이 행별로 고른다 | 화면·상태가 필요하다 |

★ 추가만을 추천하는 이유: 이미 있는 상품은 **판매가 참조하고 있을 수 있다.**
  그리고 POS 검색에는 서버 폴백이 없어 목록 조건에서 빠지면 **아예 못 판다** —
  반쪽 복원이 판매를 막는다.
