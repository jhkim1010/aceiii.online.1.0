## 결정 6건

### ① 오프라인 판매 식별자 — **`offline_number` + 「NO FISCAL」** (CODEX 안 채택)

오프라인 영수증을 **세무 문서가 아니게** 만든다. `offline_number` 를 찍고
영수증에 **«NO FISCAL»** 을 표시한다. 서버 `daily_number` 는 동기화 때 서버가 정상 채번한다.

> 구현(A-1)에서는 절단 UUID 대신 **ULID 전체**를 쓴다 — `OFF-<26자>`. 12 hex 로 자르면
> 48비트라 누적 건수가 늘수록 충돌이 생기고 순서성도 잃는다(CODEX 지적).

> 내 원안은 「서버가 번호 구간을 미리 예약해 준다」였다. CODEX 안이 낫다 —
> 예약 구간 관리가 사라지고, 「고객에게 준 종이와 장부가 갈라진다」 문제가
> **발생 자체를 안 한다**(종이가 세무 번호를 주장하지 않으므로).

### ② 재고 — **거부하지 않고 conflict 로 수용**

오프라인 판매는 **이미 일어난 사실**이다. 물건은 나갔다. 동기화 경로에서
`allowSaleWithoutStock` 로 거부하면 그 판매가 영영 장부에 못 들어간다.
음수 잔액을 허용하고 **검토 큐**로 보낸다.

### ③ 전자영수증 — **pendientes → 복구 후 발급** (사용자 결정 2026-09-08)

오프라인 판매는 CAE 없이 저장하고 기존 `GET /afip/pendientes` 큐에 얹는다.

★★ **기한이 있다.** ARCA COMPG v4.0 `CbteFch` 원문:
> Concepto=1(Productos) 은 발급일이 생성일 기준 **최대 5일 전후**,
> **제출 월(mes de presentación)을 넘을 수 없다.** Concepto 2·3 은 10일.

→ pendientes 화면에 **D-day 를 띄우고 기한 임박·초과를 경보**해야 한다.
  **월말 정전이면 창이 5일보다 짧아진다.** 안 그러면 조용히 발급 불가가 된 전표가 쌓인다.

CODEX 는 **CAEA**(`FECAEASolicitar`, 보름 단위, 사후보고 `FECAEARegInformativo` ·
`FECAEASinMovimientoInformar`)를 권했다. 매뉴얼로 실재를 확인했다. 오프라인에서도
**세무상 유효한** factura 를 줄 수 있고 월말 제약도 없다. 다만 구현이 크고 평소에
보름마다 요청·보고 의무가 생긴다 → **2단계**로 남긴다. 정전이 잦거나 긴 매장이
생기면 그때 올린다.

### ④ 응답 모양 — **엣지에 클라우드와 같은 모양의 엔드포인트**

엣지의 `/api/offline/table/:key` 는 원시 행을 준다. 클라우드 API 는 가공된 모양이다.
프런트에 어댑터를 두면 모양이 두 곳에서 관리돼 갈라진다 → **엣지가 클라우드 모양을
흉내내고 프런트 호출부는 안 건드린다.** POS 한 바퀴에 약 10개.

### ⑤ 신선도 — **마지막 완전 동기화 72시간 이내에만 오프라인 판매 허용**

낡은 미러로 팔면 옛날 가격이 나간다. 엣지 `/api/health` 가 freshness 를 실어 주고
프런트가 게이트한다.

### ⑥ 오프라인 판정 — **병렬 프로브 · 빠른 진입 · 느린 복귀**

```
앱 시작 ─┬─ edge  /api/health   timeout 300~500ms
         └─ cloud 경량 probe    timeout 1.5~2s
   edge OK + cloud 실패 → 즉시 offline → 캐시 세션 + edge ticket → POS 진입
   cloud OK             → 정상 /auth/me
```
- `navigator.onLine` 은 **힌트로만**
- **오프라인 진입은 즉시, 온라인 복귀는 2회 연속 성공**(히스테리시스)
- `/auth/me` 타임아웃 12초 → **2초**
- 요청당 엣지 재시도는 **한 번만**(중복 POST 방지), 쓰기 재시도는 **멱등키가 있는 경로만**
- 「연속 2회 실패로 오프라인 확정」 규칙은 백그라운드 안정화에만 남기고
  **콜드스타트의 blocking gate 로 쓰지 않는다**

### ✅ A-1 — 오프라인 판매의 자기 식별자 (2026-09-08 완료)

「이미 손댄 것」 3건은 이 세션 전에 이미 커밋돼 있었다
(`ventago-app@eabd3a5` · `api-ventago@6ef92b3`).

| 무엇 | 어디 |
|---|---|
| `sales.offline_number VARCHAR(40) NULL` + 부분 UNIQUE `uq_sales_offline_number` | `migrations/2026-09-08-offline-number-sales{,-b}.sql` |
| 모델 컬럼 (명시 타입) | `sales.model.ts` |
| `CreateSaleOpts` — 세 진입점이 **같은 타입**을 쓴다 | `sales-create.service.ts` |
| 번호 규칙 `OFF-<ULID>` (Crockford Base32, 무의존) | `edge-agent/src/ulid.js` · `server.js` |
| 형식 검증 + 판매는 통과 | `offline-push.service.ts` `normalizeOfflineNumber()` |

**적용 완료**: 로컬(5432) · 운영(5434) 양쪽. 스키마 대조 일치. 변경 행 0건.
적용 전 실측 — 양쪽 모두 `offline_sync_ops` 0행, `notes LIKE '%[OFFLINE %'` 0행
→ **백필 대상 없음.**

굳힌 규약 4가지 (전부 돌연변이로 죽는 것을 확인했다):

1. **번호는 op 상단 필드에서만 온다.** payload 안의 동명 필드는 `delete` 로 지운다 —
   판매 본문은 브라우저가 보낸 값이라 근거가 될 수 없다.
2. **DTO 에 넣지 않는다.** 본문으로 받으면 온라인 클라이언트가 자기 판매를
   「오프라인·NO FISCAL」로 주장해 전표를 피한다. `replacesSaleId` 와 같은 이유.
   (`create-sale-dto-boundary.spec.ts` — 대조군 포함)
3. **형식이 다르면 번호를 버리되 판매는 통과시킨다.** 판매는 이미 일어난 사실이다.
   옛 형식(`OFF-<지점>-<seq>`)은 지점 PC 재설치로 seq 가 1부터 다시 시작해 이미
   종이로 나간 번호를 재발급한다 → 그대로 넣으면 UNIQUE 위반으로 **판매가 죽는다.**
   원본은 `offline_sync_ops.offline_number` 에 그대로 남는다.
4. **지점은 인증된 엣지가 정한다.** `sale.branchId ?? scope.branchId` 를 `scope.branchId`
   로 바꿨다. 종전에는 payload 가 같은 매장의 다른 지점을 지목할 수 있었고,
   지점별 채번(`uq_sales_branch_daylocal_dn`)과 지점별 재고 원장이 그 값을 따랐다.

★ `peekNextOutboxSeq()` 는 제거했다. 유일한 사용처가 옛 번호 규칙이었고,
  남겨 두면 「번호의 출처」로 다시 쓰일 자리가 된다.

### ✅ A-2 — 영수증 «NO FISCAL» + 손님 참조 (2026-09-09 완료)

**고친 것 두 가지. 둘 다 손님 손에 잘못된 종이가 가는 문제였다.**

**① 오프라인 영수증이 「PRESUPUESTO」로 찍혔다.**
`printPayload.invoice.number` 는 `dailyNumber || id` 인데 엣지 응답에는 **둘 다
없다**. null 이 되면 formatter 가 견적 분기로 떨어진다 — 이미 돈을 받은 판매에
「견적서 · 증빙 아님」이라 적힌, 번호도 없는 종이를 줬다.

| 경우 | 렌더 |
|---|---|
| 캡처 직후 | 배너 2줄(«VENTA REGISTRADA SIN CONEXIÓN» + «NO FISCAL — DOCUMENTO NO VÁLIDO COMO FACTURA») · 제목 「Venta sin conexión」 · 뒤 6자 56px + 전체 26자 · 푸터 3줄 |
| 동기화 뒤 재인쇄 | 평소 「Venta # N」 + 「Ref. sin conexión」 한 줄 |

**② 동기화가 이미 건넨 영수증을 한 번 더 인쇄했다.** ★ CODEX 가 잡았다.
`afterCreateCommit()` 의 무인 출력 경로가 **둘**이다 — `printTicket` 감열 영수증과
**AFIP 자동 발급 성공 후 감열 출력**. 오프라인 판매의 종이는 캡처 때 이미 나왔는데
동기화가 같은 두 경로를 다시 탄다 → 인터넷이 돌아온 순간(다음 날일 수도) 아무도
안 보는 때에 같은 판매의 종이가 한 장 더. `CreateSaleOpts.suppressAutoPrint` 로
두 경로를 한 번에 막는다(payload `printTicket:false` 는 ②가 안 막혀 반쪽이다).
**세무 발급 자체는 막지 않는다 — 발급은 되고 출력만 안 한다.**

굳힌 규약:
- **형식 검사가 곧 이스케이프다.** `^OFF-[0-9A-HJKMNP-TV-Z]{26}$` 를 통과한 값은
  `[0-9A-Z-]` 뿐이라 HTML 보간이 안전하다. 느슨하게 바꾸면 그 보장과 「아무
  문자열이나 NO FISCAL 을 켜지 못한다」가 **같이** 사라진다.
- **큰 글씨 6자는 전화용이지 키가 아니다.** ULID 뒤 6자는 난수 30비트 —
  하루 1,000건이면 0.05%, 10,000건이면 4.5%가 겹친다. 전체 번호를 같이 찍는다.
- **재인쇄도 참조를 유지한다.** 손님 종이에 찍힌 건 `dailyNumber` 가 아니다.
  `buildInvoiceData` · `SaleReviewPanel` · `formatInvoiceHtml` 셋 다 실어 보낸다.

검증: 5가지 경우를 576px 실제 렌더로 눈 확인 · **대조군**(온라인 티켓 HTML 이 수정
전후 렌더 동일) · 돌연변이 5개 전부 죽음 · api·front 빌드 0 · Jenkins #879/#719 SUCCESS.

★ `formatTempTicketHtml` 의 날짜 출처는 그대로 뒀다. `formatInvoiceHtml` 쪽은
  `data.invoice.date` 를 파싱하는데 ProductList 가 es-AR 문자열("13/9/2026")을
  보내 **13일부터 Invalid Date** 다. temp 경로는 `new Date()` 라 그 함정이 없다.
  → 별도 항목: `formatInvoiceHtml` 날짜 파싱 (매달 13일 이후 재인쇄 티켓 날짜 깨짐)
