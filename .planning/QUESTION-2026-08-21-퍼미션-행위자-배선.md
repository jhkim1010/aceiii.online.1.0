# 퍼미션 쓰기 경로에 감사 행위자를 배선하는 방법 — codex 자문 요청

2026-08-21. 타임캡슐 1단계(감사 트리거)는 배포 전이고 스테이징 검증까지 끝났다.
가격 경로 3곳은 행위자(`ventago.actor_user_id`)를 걸었다. **퍼미션 경로가 남았다.**

## 왜 트랜잭션이 걸림돌인가

운영 pgbouncer 는 `pool_mode = transaction` 이라 **`SET LOCAL` 은 트랜잭션 안에서만**
유효하다. 세션 수준으로 걸면 커넥션이 다음 클라이언트에게 넘어갈 때 값이 따라가
**남의 변경이 이 사용자 것으로 기록된다** — NULL(모른다)보다 나쁘다.
즉 **행위자를 걸려면 그 쓰기가 트랜잭션 안에 있어야 한다.**

## 실측 — 퍼미션 쓰기 경로 8개 중 트랜잭션은 1개뿐

| 서비스 | 메서드 | 쓰기 문 | 트랜잭션 |
|---|---|---:|---|
| role-function | `createWithActions` | 2 | **없음** |
| role-function | `updateActionsForRoleFunction` | 2 | **없음** |
| role-function | `bulkUpdateRoleFunctionActions` | 5 | 있음 |
| role-function | `updateFunctionsForRole` | 1 | **없음** |
| user-function | `setUserFunction` | 1 | **없음** |
| user-function | `removeUserFunction` | 1 | **없음** |
| user-function | `updateUserFunctionActions` | 5 | **없음** |
| user-function | `resetToRoleDefaults` | 2 | **없음** |

★ 여러 개가 **`destroy` 후 `create`** 하는 쌍이다(`updateActionsForRoleFunction`,
`updateUserFunctionActions`, `resetToRoleDefaults`). 트랜잭션이 없으면 중간 실패 시
**권한이 통째로 사라진 상태로 남는다.** 이 저장소는 같은 형태를 Phase 64 에서 겪었고
CLAUDE.md 가 "하나의 업무 동작이 만드는 모든 행은 하나의 트랜잭션" 을 규약으로 박아 뒀다.

## 선택지

### (A) 8개 전부 트랜잭션으로 감싸고 행위자를 건다
- ✔ 요건("퍼미션 변경은 반드시 감사")을 **행위자까지** 만족. destroy+create 부분 실패도 사라짐
- ✘ **권한 쓰기 경로 전체의 원자성 의미가 바뀐다.** 지금 통과하던 것이 이제 통째로 실패할 수 있다
- ✘ `bulkUpdateRoleFunctionActions` 주석에 "175개 기능 × ... ≈ 900회 왕복, 모바일 15s
  타임아웃" 이력이 있다 — 트랜잭션을 늘리면 잠금 보유 시간이 는다

### (B) 트랜잭션이 이미 있는 1곳만 걸고 나머지는 NULL(미귀속)로 둔다
- ✔ 변경 범위가 작다. **기록은 어차피 트리거가 다 남긴다** — 잃는 것은 행위자뿐
- ✘ 실제 UI 의 권한 편집이 어느 경로를 타는지에 따라 **대부분이 미귀속**일 수 있다

### (C) 요청 단위로 트랜잭션을 열어 주는 공통 장치(인터셉터 등)를 만든다
- ✔ 경로마다 손대지 않는다. 앞으로 생기는 경로도 자동으로 덮인다
- ✘ NestJS 요청 스코프 트랜잭션은 이 저장소에 전례가 없고, 읽기 전용 요청까지
  트랜잭션을 열게 되면 pool 점유가 는다

## 묻는 것

1. **(A)/(B)/(C) 중 무엇인가?** 특히 (A)의 "원자성 의미가 바뀐다" 를 위험으로 볼 것인지,
   아니면 **지금이 잘못된 상태**이고 고치는 것이 맞는지.
2. (A)라면 `bulkUpdateRoleFunctionActions` 의 900회 왕복·15초 타임아웃 이력을 감안할 때
   나머지 7개를 감싸는 데 실질적 잠금 위험이 있는가?
3. `destroy` 후 `create` 쌍에서 트랜잭션이 없을 때, **감사 기록은 어떻게 남는가?**
   (destroy 는 커밋되고 create 가 실패하면 감사에는 "권한 삭제" 만 남는다 — 이게 오히려
   사실에 부합하는가, 아니면 오해를 부르는가?)
4. 행위자를 못 거는 경로를 **그대로 두는 것**과 **트랜잭션을 도입하는 것** 중,
   감사 신뢰성 관점에서 무엇이 더 나쁜가?
5. 내가 놓친 선택지가 있는가?
