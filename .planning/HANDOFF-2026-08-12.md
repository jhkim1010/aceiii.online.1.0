## 2. talleres 생산 입고 — 설계 확정, 1단계만 완료

### 지금 상태 (실측)
- 운영 `stocks` 에 `type='production'` **0건** — 생산으로 재고가 들어온 적이 없다.
- 로트 5건 전부 store 6. 로트 10 은 **3개 공정 다 돌고 pendiente 0 인데 재고 0**.
- `talleres_lotes.size_color_matrix` 에 `qty[colorId][sizeId]` 가 실제 ID 로 있고
  자식 상품이 `color_id`/`size_id` 를 가져 **1:1 매핑이 추측 없이 떨어진다**.
- `ingresarAStock`(수동 입고)은 **이미 존재**했다 — 수령 업무와 연결이 없어 아무도 안 눌렀다.

### 확정된 설계 결정
1. **변형별 수량은 두 지점에서만** — `corte`(실제 재단량, 재고 영향 없음)와
   최종 공정(실제 입고량, 재고 기록). 중간 공정은 총량만. 업계 표준과 일치.
2. **기준선은 `cortado`** (corte 수령 양품 누적). 없거나 불완전하면 **plan 폴백**하고
   화면에 출처를 표시한다(`Referencia: corte real` / `Referencia: plan`).
3. **재작업은 정상 입고**다(중복 아님) — 원 수령에서 불량으로 빠졌던 것이 처음 들어오는 것.
   검증식을 `sum(final.received) ≤ cortado` 로 두면(rejected 제외) 재작업이 이 식을
   깨지 않는다. 분기·플래그·새 컬럼 불필요.
4. **최종 공정 판정은 `MAX(order)` 가 아니다.** `buildRoutingPath` 가 order 를 1..N 으로
   재정규화하므로, canonical 검증(비어있지 않음 · order 정확히 1..N · etapaId 중복 없음)
   후 **배열의 마지막 원소**. 검증 실패 시 자동 입고 금지.
5. 데이터는 `talleres_recepcion_items` 자식 테이블(JSONB 아님). 멱등 키
   `UNIQUE(recepcion_id, product_id)`. 헤더-항목 합계 일치를 같은 트랜잭션에서 강제.
6. 부분 수령은 **수령할 때마다 즉시 부분 입고**.

### ★ 새로 드러난 것 — `talleres_recepciones` 에 쓰는 곳이 **셋**이다 (3단계에서 발견)

변형별 격자를 붙인 곳은 **하나뿐**이다. 나머지 둘로 수령하면 그 로트의 cortado 기준선이
비게 된다(설계상 plan 폴백으로 degrade 되지만, 4단계 검증식의 정밀도가 떨어진다).

**4단계에서 처리한 방식**: 격자를 세 곳에 다 붙이는 대신, 넣을 수 없는 수령을

재고가 조용히 비지 않고 **미결로 보인다** — 5단계 배너가 그걸 드러낸다.

### ★ 미해결 위험 — routing 이 바뀌면
`updateRoutingPath` 는 FREE(envío 없는) 공정의 **추가·제거·재정렬을 허용**한다.
- **시나리오 1**: 입고 후 뒤에 공정 추가 → 새 최종 공정 수령 시 **이중 입고**.
  → `sum(final.received) ≤ cortado` 총량 검증이 잡는다(cortado 실측일 때 하드 블록 가능).
- **시나리오 2**: 최종 뒤 공정을 제거 → 이전 수령이 최종이 됐는데 입고 안 됨 →
  **조용한 구멍**(로트 10 과 동형). 검증으로 안 잡힌다 → **상시 감지 배너**가 필요하다.
  mockup 섹션 5 의 경고를 일회성이 아니라 상시 규칙으로 승격할 것.
- 원칙: **최종 공정 판정을 캐시하거나 수령 시점에 굳히지 마라.** 매번 routing_path 에서 계산.

### 마스터 데이터 문제 — ★ 재확인 결과 **지금은 무해하다** (2026-08-12)
`talleres_etapas`(store 6)에 `order 5` 가 둘인 것은 맞다(`planchero` id 5, `costurero` id 6).
그러나 **`costurero` 는 `is_active = false`** 이고, `buildRoutingPath` 는 기본 경로를
`where: { storeId, isActive: true }` 로 뽑는다 → **애초에 후보에 들어가지 않는다.**
"명시 지정 안 하면 costurero 가 최종이 된다"는 기재는 **성립하지 않는다.**
운영 변경은 하지 않았다. 남는 위험은 **누가 costurero 를 재활성화하면** 그때 동점이
실제로 문제가 된다는 것 — 그때 order 를 6 으로 올리면 된다. 우선순위 낮음.
