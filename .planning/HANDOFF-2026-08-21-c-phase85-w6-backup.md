## 한 것

### W6-A — 커버리지를 테스트로 강제 (W4·W8 과 같은 형태)

`store-backup-coverage.ts` 가 **담는 것 / 전용 처리 / 이유를 붙인 제외**를 선언하고
`store-backup-coverage.spec.ts` 가 강제한다. 감시는 **두 겹**이다:

1. **인벤토리 대조** — DB 에서 뽑은 기준선(`store-backup-inventory.txt`)과 선언을 맞춘다
2. **마이그레이션 컷오프** — 인벤토리 재생성을 **잊어도** 새 테이블·새 민감 컬럼이 잡힌다

★ ①만 두면 "재생성 스크립트를 안 돌리면 통과" 라는 구멍이 남는데, **그 구멍이 바로
이 spec 이 막으려는 것과 같은 종류다.** "인벤토리가 비어 있지 않다" 를 첫 검사로 둔 것도
같은 이유 — 빈 기준선은 **아무것도 검사하지 않으면서 통과**한다.

### W6-B — 선언이 실제로 돌게 + 자격증명 마스킹

- 손으로 쓴 쿼리 13개 → `SIMPLE_STORE_TABLES`(83개) 루프 하나. **41 → 119개 테이블.**
  새로 담기는 행: store 9 **4,978** · store 6 **1,539** · store 3 **1,129**
- 옛 camelCase 키 유지(복원이 그 이름으로 읽는다) · 새 테이블은 `tables[<이름>]`.
  **옛 키와 새 그릇에 동시에 싣지 않는다**(파일 두 배 + 어느 쪽이 진짜인지 모르게 됨)
- 8개씩 끊어 던진다 — 83개를 한 번에 하면 워커 풀(max 20)을 그 순간 다 쓴다
- 읽지 못한 테이블은 **버리지 않고 `coverage.unreadable` 에 이름을 남긴다**
- 자격증명 마스킹: MP OAuth 토큰 · WooCommerce 키·시크릿 · WhatsApp 토큰 · `branches.api_key`

## ★ codex 가 잡은 것 — 둘 다 내가 만든 결함이다

### [P1] 범위를 넓히면서 **노출도** 넓혔다

`SELECT *` 로 119개를 담는 순간 **MercadoPago OAuth 토큰 · WooCommerce 소비자 시크릿 ·
WhatsApp 액세스 토큰**이 다운로드되는 JSON 과 서버 디스크(`backups/`)의 평문 파일에
실리게 됐다.

★ **나는 "무엇이 빠졌나" 만 세고 "무엇이 새로 나가나" 는 안 셌다.
커버리지를 늘리는 일과 노출을 늘리는 일은 같은 동작이다.**

그 조사에서 **W6 이전부터 새고 있던 `branches.api_key`** 도 나왔다(ORM 경로라 안 보였다).

★ 반대로 `EXCLUDED_TABLES` 의 판단이 여기서 값을 했다 — `active_sessions.session_token` ·
`support_tokens.token` · `terminal_devices.device_token` · `vendedor_devices.api_key` ·
`despacho_devices.api_key` 는 **애초에 안 담기므로** 손댈 것이 없었다.

### [P2] 테이블에는 컷오프 감시를 걸고 **컬럼에는 안 걸었다**

인벤토리 재생성을 잊으면 새 민감 컬럼을 spec 이 모른 채 통과하는데 `SELECT *` 는
**즉시** 그 값을 싣는다. **내가 테이블에서 막은 것과 똑같은 구멍이었다.**
판정 패턴도 단일 출처로 만들어 regen 스크립트가 TS 에서 읽어 가게 했다 —
패턴이 두 벌이면 인벤토리와 spec 이 서로 다른 것을 보면서 **둘 다 통과**한다.

## 내가 스스로 잡은 것

- spec 이 마스킹 규칙을 **복사**해 갖고 있었다 — 내가 이 저장소에서 반복해 경고한
  "두 곳이 들고 있으면 갈라진다" 를 내가 저질렀다. `redactBackupRows()` 하나로 합쳐
  **테스트가 검증하는 코드 = 운영이 실행하는 코드**로 만들었다.
- **이름이 두 벌이다** — raw SQL 은 `api_key`, ORM `toJSON()` 은 `apiKey`.
  한쪽만 지웠다면 ORM 경로(branches)는 **아무것도 안 지우면서 지웠다고 믿었을** 것이다.
  마스킹에서 가장 위험한 실패 양식이다.
- spec 첫 실행이 **내가 쓴 제외 사유 2건("위와 같음.")을 반려**했다.

## 감시가 실제로 잡는지 증명했다

통과는 "위반이 없다" 와 "검사를 안 한다" 를 구분하지 못한다. 임시 마이그레이션에
`mp_accounts.client_secret` 추가 + `store_id` 를 가진 `probe_new_table` 생성 →
**두 감시 모두 잡았고**, 제거 후 16/16 복귀. 대조군 없는 시험은 아무것도 검증하지 않는다.

운영 컨테이너에서 직접 실행해 마스킹도 확인했다:
`mp_accounts` access/refresh → `null`, `public_key` 는 보존, ORM `apiKey` → `null`.

## ★★ 남은 것 — 정확히 말하면

**백업(내보내기)은 온전해졌고 자격증명은 막혔다. 복원(되돌리기)은 여전히 부분적이며
제자리 복구가 아니다.**

| 남은 것 | 내용 |
|---|---|
| **복원의 `tables` 처리** | 복원은 아직 옛 키만 읽는다 — 새로 담긴 **70개 테이블은 백업엔 들어가지만 되돌아가지 않는다** |
| **W6-C 제자리 복구** | 지금의 "복원" 은 `Store.create` + ID 재매핑, 즉 **새 매장으로의 복제**다. W6 요건("어제 데이터로 돌려주세요")과 다른 동작이다 |
| **W6-D MinIO manifest** | DB 엔 key 만 있다. JSON 에 key 를 넣는 것은 백업이 아니다 |

### ★ W6-C 는 **사용자 판단이 필요하다** (기술 문제가 아니다)

제자리 복구는 `stocks` 를 되돌려야 하는데 `trg_stocks_immutable` 이 DELETE·UPDATE 를
둘 다 막는다. 길이 둘이고 **회계적 주장이 다르다**:

| | 방법 | 뜻 |
|---|---|---|
| (가) | 반대 부호 **보정 행**을 append | "되돌렸다" 는 사실이 원장에 남는다. 원장 규약을 지킨다 |
| (나) | `SET LOCAL ventago.stocks_maintenance='on'` 후 DELETE | "그 기간 원장을 없던 것으로 한다". 가드가 의도적으로 열어 둔 경로 |

2026-08-11 에 운영 더미 데이터를 지울 때는 (나)를 썼다(존재한 적 없는 −1,800 출고를
영구히 남기지 않으려고). **제자리 복구는 그것과 다르다** — 되돌리기는 실제로 일어난
사건이므로 (가)가 기본이어야 한다고 보지만, **이건 회계 정책이지 기술 선택이 아니다.**
