## ③ 성능 — TLS 1.3 (사용자가 «지금은 안 한다» 로 결정)

**실측 (2026-09-17, `app.coolsistema.com/login/`)**

| 구간 | 시간 |
|---|---|
| TCP 연결 | 170ms (왕복 1회 — 물리적 거리) |
| TLS 핸드셰이크 | **338ms** (왕복 2회 — TLS 1.2 라서) |
| 요청→첫 바이트 | 168ms |
| **서버 처리** | **8ms** ← 서버는 느리지 않다 |
| 합계 | 685ms (`/login` 으로 들어오면 308 리다이렉트로 885ms) |

**원인:** `:443` 에 `default_server` 가 없어 **알파벳 순 첫 vhost** 가 소켓의 TLS 설정을 지배한다.
그 파일들이 전부 `ssl_protocols TLSv1 TLSv1.1 TLSv1.2;` 다(`nginx.conf:37` 전역엔 TLSv1.3 이 있지만 덮인다).
★ `ssl_protocols` 는 **server 블록별이 아니라 listen 소켓별**이다 —
  `shop-wildcard.conf` 는 `TLSv1.2 TLSv1.3` 인데도 실제 협상은 TLSv1.2 였다.

**제안했던 변경 (보류):** `ssl_protocols` 에 `TLSv1.3` 을 **더하기만** 한다(아무것도 빼지 않음).
옛 기기 호환이 깨질 수 없고, 새 연결마다 **약 170ms(25%)** 절감.
폐기 프로토콜(TLSv1/1.1) 제거는 매장 기기 실태 파악 후 별건.

**함께 발견 (별건, 미처리)**
- `include /etc/nginx/sites-enabled/*;` 가 확장자를 안 가려
  **`newapi.coolsistema.com.conf.bak-20260825-214627` 이 실제로 로드된다.**
  `nginx -t` 가 `conflicting server name ... ignored` 로 경고한다(`invoice`·`manager` 도 같은 형태).
  알파벳 순으로 진짜 파일이 먼저라 **지금은 무해**하지만, 그 백업은 `client_max_body_size 70m`
  (현재 128m)라 순서가 바뀌면 업로드가 깨진다. **지뢰다 — 치울 것.**
  ★ 앞으로 nginx 백업은 **`sites-enabled` 밖에** 둘 것.
- `/login` → `/login/` **308 리다이렉트가 약 200ms** 추가 (Next.js `trailingSlash` 결정 사안)
- 나머지 약 510ms 는 물리적 거리 — 설정으로 못 줄인다. 서버 이전/CDN 의 근거 수치
  (`.planning/PLAN-2026-09-16-서버-분리와-신규-이전.md`)

## ④ (참고) 로컬 dev 가 느린 것은 정상이다 — 조치 불필요

사용자가 «첫 화면이 오래 걸린다» 고 한 것은 **로컬** 이야기였고, **운영은 정상**이다.

| | script 수 | 합계 크기 |
|---|---|---|
| 로컬 `next dev` | 8 | **18.81 MB** |
| 운영 | 10 | **1.63 MB** |

로그인 화면 하나에 **11.5배** 차이. `next dev` 는 minify·트리셰이킹을 안 하고 소스맵까지 붙인다.
전송은 localhost 라 0.07초지만 **브라우저가 18.8MB 를 파싱·실행하는 데 몇 초**가 걸린다.
서버 HTML 응답은 첫 컴파일만 1.1초, 그 뒤 37ms — 서버 문제가 아니다.

완화: ① 경로는 첫 방문만 느리다(온디맨드 컴파일) ② `next dev` 를 오래 켜두지 말 것
(측정 시점에 **1일 10시간**째였다) ③ 운영과 같은 조건이 필요하면 `npm run build && npm start`.
