## 1. 지점별 입고 합계가 조용히 잘려 있었다 ✅

**증상**: Productos 「Historial del día」에서 HELGUERA 가 실제 360 인데 **40** 으로 표시.

**원인**: `getProductsWithStockAddedToday` 가 **product_branch 행 단위로 50개**를 잘랐다.
2지점 × 45변형 = 90행인데 pageSize=50 이라 뒤쪽 40행이 통째로 사라졌다.
잘린 사실이 응답에도 안 남았다 — `count` 가 `rows.length` 였다.

**수정**: 페이지 단위를 **codigo madre** 로. 한 madre 의 모든 변형·모든 지점이 항상
같은 페이지에 온다. 정렬 고정(최근 madre 우선) — 없으면 페이지 경계가 호출마다 달라진다.
`count` 는 "그날 입고가 있는 madre 수".

프론트: KPI 의 `productos` 를 행 수 → **distinct 상품 수**로(2지점이면 45가 90으로 보였다).
madre 가 pageSize 를 넘겨 잘리면 `+N códigos madre no mostrados` 표시.

## 2. envíos — 인계가 곧 배송인 운송사 ✅

`transportes.delivers_immediately` 가 true 면 `en_transito` 를 건너뛰고 바로 `entregado`.

- **바뀐 것은 목표 상태 한 줄뿐**. 재고·회계(commitSale/mirror/sale_credit/shipSaldo/
  paymentStatus)는 한 줄도 다르게 안 돈다 → **미수금은 그대로 남는다**.
- `metadata.deliveredImmediately` 스냅샷 — 운송사 설정이 나중에 바뀌어도 이력이 안 흔들린다.
- `revertOrder`: 즉시배송 주문은 `entregado → listo` 로 한 번에 un-ship. 겪은 적 없는
  en_transito 로 보내면 없던 단계가 생기고 외상이면 거기서 못 나온다.
  un-ship 회계는 `applyUnship()` 한 곳으로 모았다.
- `trackingCode` 필수 검증을 DTO → service 로. 자기 운송에는 추적번호가 존재하지 않는다.
- `TransportesService.create/update` 가 `carrierSlug`/`deliversImmediately` 를 **실제로 저장**
  (DTO 에만 있고 버려지고 있었다).
- despacho 단말 목록에도 `deliversImmediately` 포함 + Flutter 앱 대응.

프론트: 발송 다이얼로그(즉시배송이면 추적번호 칸 숨김 + 버튼 "Entregar"),
Configuración › Envíos 에 **Entrega inmediata 토글**.

## 4. 취소된 외상이 고객 채무로 남아 있었다 ✅ (CODEX [HIGH])

**결함**: 발송된 외상 주문을 취소하면 재고·mirror 는 역분개되는데 `sale_credit` 이 그대로
남아 고객 외상잔액과 aging 에 채무가 계속 남았다. (운영 미발동이었다 — 취소된 주문 0건)

**새 movement type `sale_credit_void`** (credito, −).
`payment_in` 은 "고객이 냈다"는 거짓 기록, `writeoff` 는 대손이라 둘 다 못 쓴다.
`adjustment` 는 bucket 은 맞지만 부호가 +1.

- `mirrorSaleId` 로 그 판매의 sale_credit 을 **전부**(sale 당 UNIQUE 없음) 찾아 미상환분만 void
- 없앨 금액을 **먼저 다 계산**하고 credito 잔액을 넘으면 **취소 전체를 롤백**(fail-closed).
  조용히 깎으면 주문은 취소됐는데 채무가 남아 원래 버그보다 나쁘다.
- `mirrorSaleId` 가 비면 `sales.online_order_id`(UNIQUE)로 복구, 복수 매칭이면 fail-closed
- 타임라인에도 `sale_credit_void` 노출

**함께 고친 [HIGH] — open 잔액 이중 차감**
useFavor 결제가 같은 parent 에 `favor_apply` + `payment_in` 을 **짝으로** 만드는데
open 계산이 둘 다 빼고 있었다(100 갚으면 채무 200 감소). 상쇄분에서 favor_apply 제외.
**적용처 4곳**: credit-payment(FIFO) / credit-report(aging, oldest_due) / dashboard-admin(연체일).
→ 자세한 내용은 메모리 `credit-open-balance-formula`.

- 마이그레이션 `credit-ledger-sale-credit-void.sql` — **로컬 5432 + 운영 5434 양쪽 적용, 대조 완료**
  (CHECK 를 먼저 넓히고 코드 배포. 반대면 INSERT 가 제약에 걸려 취소가 500)
- api `dfe31af` (#663) + `d715c8d` (#664), 테스트 5건(4건 뮤테이션 사멸)
- **실측**: 총 1000 중 500 지불 + 500 외상 주문을 만들어 취소 →
  `sale_credit_void −500`(credito 0) + `favor_in +500`(favor 500). sale#141 `Anulado` +
  역분개 sale#142 `-1000`. Cuentas por cobrar 에서 사라짐.

## 5. POS 카탈로그 즉시 갱신 ✅

**증상**: 새 제품이 ventas(POS)에 안 뜬다.
**원인**: POS 는 카탈로그를 **마운트 때 한 번만** 가져온다(pageSize=1000). 재조회 조건이
`showParentsState` / `saleBranchId` / `saleCreated` 셋뿐이라 제품 등록은 해당 없음.

신호 경로 3개:
1. 같은 탭 — `apiConnector` 응답 인터셉터(비-GET `/products` 성공) → window 이벤트
2. 같은 브라우저 — BroadcastChannel
3. **다른 단말** — 서버 `/realtime` `catalog:changed` (store room)

**출처별 debounce**: local **1.5s**(내 등록 = 즉시 피드백) / remote **5s**(다른 단말 = 몰아치기 방지).
타이머를 하나로 합치면 원격 신호가 낄 때마다 내 피드백까지 5초로 늘어난다.
`x-client-id` 헤더로 자기 echo 를 걸러 1000행을 두 번 받지 않는다.

서버는 `ProductsController` **전체에 인터셉터 하나**(라우트마다 넣으면 반드시 하나 빠뜨림).
GET 은 거른다 — 안 거르면 무한 재조회.

- api `4e0732c`(#665) `762be10`(#666) `a1f4e0c`(#667) / front `6fe5ea0`(#595) `47978da`(#596)
- **실측**: (a) POS 열어둔 채 다른 탭에서 등록 → 새로고침 없이 검색에 노출, 장바구니 유지
  (b) raw fetch(=apiConnector 우회)로 변경 → `origin:"remote"` 수신 + 5초 뒤 by-parent 재조회 1회

### ★ 도중에 발견한 별건 결함 (수정 완료, 파급 있음)

`WebsocketService.registerUser` 가 `userId`/`storeId` 중 **하나라도** 숫자가 아니면
**아무 room 에도 안 넣고 조용히 빠져나갔다.** 그런데 브라우저 JWT payload 에 **`id` 가 없다**
(`name/lastName/email/status/trialEndsAt/roles/storeId` 뿐 — 토큰 디코딩으로 실측).
→ `userId` 가 항상 undefined → **store room 가입이 통째로 막혀 `emitToStore` 가 브라우저에
도달한 적이 없다.** `join_error` 도 안 나서 아무도 몰랐다.

두 join 을 분리했다(store room 은 storeId 만 있으면 성립).

**파급**: `emitToStore` 를 쓰던 다른 기능도 같이 살아난다 —
`suspended-sale:changed`, `store_notice` 등. 그동안 브라우저에 안 가던 push 가 이제 간다.
의도된 개선이지만 **동작 변화**다. 예상 못 한 알림이 뜨면 `a1f4e0c` 를 보면 된다.

## 작업 방식 메모

- **CODEX 자문이 이번에 두 번 결정적이었다.** (1) open 잔액 이중 차감(기존 결함)을 새 항을
  더하기 직전에 잡았다. (2) `Math.min` 클램프가 원래 버그보다 나쁘다는 지적 → fail-closed 로 전환.
  다만 근거는 매번 코드로 직접 대조했다 — 지적이 맞아도 범위가 다른 경우가 있다.
- **뮤테이션 확인**을 새 테스트마다 했다(제품 코드를 일부러 깨서 테스트가 죽는지).
  이 프로젝트는 "통과하지만 아무것도 안 지키는 테스트"에 이미 데인 적이 있다.
- 이 세션에서 반복해서 나온 실패 형태: **부재가 침묵한다.**
  잘린 응답이 count 에 안 남음 / room 가입 실패가 join_error 없이 넘어감 /
  DTO 에만 있고 저장 안 되던 필드. 새 코드에는 전부 로그나 화면 표시를 붙였다.
