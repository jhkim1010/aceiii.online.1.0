# §B. `POST /sales/:id/modify/preview`

판정만 돌려주고 **아무것도 바꾸지 않는다.** `modifySale` 과 **같은 `decideMode`** 를 탄다.

```
{ mode, reason, originalSaleId, originalDailyNumber, keepsNumber, originalState }
```

- **잠그지 않는다.** 확인 화면을 띄워 둔 동안 판매 행이 `FOR UPDATE` 로 묶이면 취소·결제
  추가가 락 대기에 걸린다.
- **트랜잭션을 `READ ONLY`** 로 연다 — dry-run 계약을 주석이 아니라 엔진이 지킨다.
  실측 확인: `START TRANSACTION` 다음 첫 문장으로 걸리고 `transaction_read_only=on`,
  `UPDATE` 는 거부된다.
  ★ 단 `findOne`·`resolveSaleBranchIdPublic`·`prepareCreate` 는 **트랜잭션 밖**이라 이
  강제를 못 받는다. 셋 다 조회 전용임을 확인하고 두었다 — 주석에 명시했다.
- `prepareCreate` 까지 태운다 — 고객·판매원 소속 오류를 확인 화면에서 미리 보여준다.
- 새 번호는 **미리 알 수 없다**(채번은 커밋 시점 advisory lock 안). 추측해서 보여주지 않는다.

서버는 이 값들로 **분기하지 않는다.** 락 안에서 다시 판정하고, 어긋나면 거부한다.

## 프론트 라운드 — 판매가 복제되거나 엉뚱한 판매가 덮이는 경로들
- ★ **draft(localStorage)에 `editingSaleId` 가 없으면** 새로고침 한 번에 수정이 신규 판매로
  바뀌어 **같은 판매가 복제된다**(재고도 두 번 빠진다). → 내용과 출처를 함께 저장.
- ★ **수정 중 보류판매를 클릭하면** 카트만 바뀌고 `editingSaleId` 가 남아, 확정 시 보류
  내용으로 **원래 판매를 덮어썼다.** → 확인 후 함께 내린다.
- ★ **프로모션 재평가** — 복원된 할인은 `source` 가 없어 안 지워지고 새 promo 할인이 하나 더
  붙어 이중 차감되며, 아무것도 안 고쳤는데 금액이 달라져 **번호가 헛되이 바뀐다.**
  → 수정 중에는 promo 재평가를 멈춘다.
- **`branchId`** — `sales` 에 지점 컬럼이 없어 프론트는 원본 지점을 모른다. 지금 POS 의 지점을
  보내면 다른 지점에서 연 판매가 `branch_changed` 로 판정된다. → **안 보낸다**(서버가
  `undefined` 면 지점 비교를 건너뛰고 원본 지점을 이어받는다).
- 확인 Promise 누수(연타·unmount·preview 응답 대기 중 이탈) + 멱등키를 대상에 묶기
- **ESC 가 모달 위에서도 카트를 비웠다** — 확인창만 닫으려다 수정 내용을 잃는다(유일한 사본).
  같은 파일의 보류판매 ESC 핸들러가 이미 쓰던 가드를 붙였다. (기존 버그도 같이 고쳐졌다)

## 작업 방식 — 이번에 걸린 것

- ★ **"고쳤다" 를 실제로 확인했다.** READ ONLY 트랜잭션이 Sequelize managed transaction 안에서
  진짜 걸리는지 유닛 테스트는 증명하지 못한다(문자열이 전달됐는지만 본다). 실 DB 에 붙여
  `transaction_read_only=on` 과 UPDATE 거부를 눈으로 봤다. 3차의 `@IsOptional()` 교훈의 연장.
- ★ **codex 는 두 라운드 다 실제 결함을 냈고, 두 번째 라운드는 첫 번째 수정을 검증하면서
  새 것 둘을 더 찾았다.** "고친 것만 보라" 로 범위를 좁히는 게 계속 유효하다.
- ★ **범위를 줄이는 결정은 물어봤다.** 프로모션 부분 적용(§E-1)은 `bulk_tier` 때문에 업무
  판단이 필요해 반쪽짜리 기계를 만드는 대신 한계로 남기고 알렸다.
- **주석이 구현보다 강하면 그것도 결함이다.** "preview 는 read-only" 라고 썼는데 실제로는
  트랜잭션 안만 그렇다 — 경계를 정확히 적어야 다음 사람이 저 밖에 쓰기를 안 넣는다.
