# Reportaje abierto — CODEX 자문 (2026-10-17, 원문)

1. 설계 적합성 및 위험

- **결론:** `의미 카탈로그 → 검증된 JSON 요청 → SQL 컴파일러` 구조가 적합하다. 향후 AI도 동일 JSON만 생성하게 하는 방향이 안전하다.
- **[높음] 테넌트 격리:** `store_id`를 요청 JSON에서 받지 말고 세션에서 강제해야 한다. 모든 fact·JOIN·서브쿼리에 매장 조건이 포함되어야 하며, `branch_id`도 해당 매장 소유인지 검증해야 한다.
- **[높음] 기존 보고서와 의미 불일치:** “매출” 정의를 새로 만들면 숫자가 기존 보고서와 달라진다. `activity_type`, 취소, 반품·신용전표, 외상원장, `sale_date/created_at`, 비용 누락 처리 규칙을 먼저 하나의 버전화된 정의로 고정해야 한다.
- **[높음] 로컬 날짜:** UTC 컬럼을 직접 날짜로 자르면 안 된다. 매장 IANA timezone으로 변환한 뒤 일/주/월을 계산해야 한다. 기존 이익 보고서도 이 방식을 사용한다.
- **[높음] 성능·pool:** 임의 조합은 대형 집계·정렬·해시 JOIN을 만들 수 있다. 쿼리 하나가 연결 하나를 오래 점유하므로, 워커당 max 20을 늘리는 해결책은 금지하고 timeout·동시성 제한·인덱스·비용 사전검사가 필요하다.
- **[높음] 집계 오류:** 결제수단처럼 판매 1건에 여러 행이 연결되는 차원은 JOIN 후 매출·티켓이 중복될 수 있다. metric별 grain과 허용 JOIN 경로를 카탈로그에 명시해야 한다.
- **[중간] 비가산 지표:** 평균 티켓과 마진율은 평균값을 재합산하지 말고 `SUM(분자)/SUM(분모)`로 최종 단계에서 계산한다.
- **[높음] 재고:** 재고는 기간 합계가 아니라 특정 시점 snapshot이다. `stock_balances`만 사용하고 매출 시계열과 같은 요청에 섞지 않는 것이 안전하다.
- **[중간] 저장 보고서:** 저장된 JSON에도 `store_id`나 권한 결과를 저장하지 말고, 실행할 때마다 현재 세션·현재 권한·현재 카탈로그 버전으로 재검증해야 한다.
- SQL 값은 바인딩하고, 컬럼·JOIN·정렬 표현식은 카탈로그 allowlist에서만 선택해야 한다.

2. MVP 제한

- 차원: 최대 **2개**. 그중 고카디널리티 차원(상품·고객·판매자)은 최대 1개.
- 기간: 기본 30일, 일반 최대 **90일**. 일 단위 집계는 90일, 주/월 단위는 최대 12개월.
- 비교: 한 번에 하나만 허용. 전년 동기 비교는 최대 90일 범위.
- 화면 결과: 최대 **1,000행**, 기본 100행. 화면 표는 페이지당 최대 50행.
- CSV: 최대 **10,000행**. 초과 시 필터나 TOP N을 요구한다.
- TOP N: 최대 100, 상품은 TOP N 필수.
- timeout: 대화형 **5초**, CSV **20초**. timeout 후 자동 재시도 금지.
- 동시 실행: 매장당 **1개**, 사용자당 1개. 대기 중 요청은 최대 2개. MVP에서는 이것이 가장 보수적이다.
- 전체 시스템 동시 보고서는 별도 semaphore로 제한해야 한다. 초기값 4~6개 후 실측 조정.
- 금지 조합:
  - 재고 × 일/주/월 또는 기간 비교
  - 고객 차원/필터: 별도 개인정보 권한 없으면 금지
  - 원가·마진: 관리자 전용
  - 상품 × 일: TOP N과 31일 이하 없으면 금지
  - 상품 × 고객, 상품 × 결제수단: MVP 금지
  - 결제수단별 티켓 평균: 분할결제 의미를 정의하기 전 금지
  - 원시 행·자유 텍스트 검색·자유 SQL·임의 컬럼 정렬 금지

3. 최소 카탈로그

- 우선 metric:
  - 순매출액
  - 판매 수량
  - 티켓 수
  - 평균 티켓 = 순매출액 / 티켓 수
  - 반품액·반품 수량(순매출과 별도 표시)
- 우선 dimension:
  - 지점
  - 로컬 일·주·월
  - 카테고리
  - 상품/마드레 — TOP N 전용
- 우선 filter:
  - 기간
  - 지점
  - 카테고리
  - 판매 상태
- 2차 도입:
  - 판매자
  - 결제수단
  - 비용·마진
- 별도 보고서 유형:
  - 현재고 snapshot. 매출 metric과 같은 요청 모델에 섞지 않는다.
- 고객, 외상, 비용은 권한·PII·서로 다른 원장 의미가 있으므로 MVP 핵심 카탈로그에서 제외하는 편이 안전하다.

4. UX

- 빈 화면보다 “이번 달 지점별 매출”, “카테고리 TOP 10”, “전월 대비 일별 매출”, “현재고” 템플릿을 먼저 보여준다.
- 사용 순서를 `무엇을 볼까요? → 어떻게 나눌까요? → 기간/필터 → 비교`로 제한한다.
- 선택할 때마다 예상 결과 형태와 예상 행 수를 즉시 표시한다.
- 표 미리보기는 처음 20~50행만 제공하고, 그래프는 차원에 맞는 유형을 자동 추천한다.
- 비활성 항목에는 이유를 바로 표시한다. 예: “상품×일은 31일 이하 및 TOP 100이 필요합니다.”
- metric 설명에 포함/제외 규칙을 노출한다. 예: “순매출: 취소 제외, 반품 차감, 매장 로컬 날짜 기준.”
- 비가산 지표에는 안내 문구를 붙인다. 예: “평균 티켓은 그룹별 매출÷티켓으로 다시 계산됩니다.”
- 실행 전 기간, 그룹, 비교, TOP N을 자연어 한 줄로 요약한다.
- 한도 초과 시 단순 오류 대신 가능한 수정 버튼을 제공한다: “기간을 31일로 줄이기”, “TOP 100 적용”.
- 저장 보고서는 이름뿐 아니라 카탈로그 버전과 의미 정의 변경 경고를 보여줘야 한다.

5. 운용3 복제본 사용 여부

- **MVP에서는 아니오.** 우선 primary에서 강한 제한과 측정을 적용하는 편이 낫다.
- 이유:
  - 복제 지연으로 방금 발생한 판매와 기존 화면 숫자가 달라질 수 있다.
  - 별도 read pool·장애 전환·지연 감지·read-after-write 정책이 필요하다.
  - 복제본을 사용해도 비효율적 쿼리 자체는 해결되지 않는다.
- MVP 운영 조건은 timeout, 매장별 동시성 1, slow-query 로깅, `EXPLAIN` 검증이다.
- 이후에는 “최종 동기화 시각/지연”을 표시하고, 허용 지연 기준을 넘으면 primary로 fallback하지 말고 요청을 거부하는 방식이 안전하다. 자동 fallback은 장애 시 primary에 보고서 부하를 몰아넣을 수 있다.
