전제: Phase 49 Wave49-01 PoC(TryOnProvider 추상화 + 스텁) 완료 상태에서 출발

## 1. 다층 분석 (표면 → 구조 → 본질)

### 표면 문제
"고객 사진 + 옷 이미지 → 합성 이미지를 만드는 API를 어떤 것으로 고를 것인가"라는 기술 선택 문제로 보입니다. 실제로 이 층은 이미 90% 풀려 있습니다 — `api-ventago/src/app/tryon/`에 TryOnProvider 포트가 있고, 어댑터 하나만 갈아끼우면 됩니다.

### 구조적 원인
매장 판매의 전환율을 결정하는 것은 **시착률**입니다. 고객이 옷을 입어보는 데는 비용이 듭니다: 탈의실 대기, 갈아입는 귀찮음, "나한테 안 어울리면 민망함". 그래서 고객은 평균 2~3벌만 입어보고, 입어보지 않은 옷은 사지 않습니다. 가상 피팅은 **시착 1회의 한계비용을 사실상 0으로** 만듭니다. 사진 한 번 찍으면 10벌을 10분 안에 "입혀볼" 수 있고, 판매원이 "이것도 한번 보실래요?"를 무제한으로 던질 수 있게 됩니다. 이것이 판매촉진의 실제 메커니즘입니다.

### 근본 본질
이 기능의 성패는 AI 품질이 아니라 **데이터 자산**에 달려 있습니다. Wave49-01에서 이미 확인된 사실: 전체 상품 483개 중 이미지가 있는 것은 22개, store25는 0개. 옷 이미지가 없으면 세계 최고의 VTO API도 무용지물입니다. 역으로, 이 기능을 잘 설계하면 세 가지 자산이 동시에 쌓입니다:

1. **카탈로그 이미지** — 판매원이 매장에서 옷을 찍는 순간 상품 이미지가 등록되는 플로우를 넣으면, 피팅 기능을 쓸수록 공개몰(Phase 51)의 카탈로그가 완성됩니다.
2. **구매 의도 데이터** — "어떤 고객 세션에서 어떤 옷을 입혀봤나"는 장바구니보다 앞선 구매 의도 시그널로, 향후 AI 추천(로드맵 ②)의 학습 데이터가 됩니다.
3. **고객 접점** — 결과 이미지를 WhatsApp으로 보내주는 순간, 매장 방문 고객이 온라인 재접촉 가능한 리드로 전환됩니다.

즉, 이것은 "피팅 기능"이 아니라 **Phase 51(공개몰)과 AI 추천의 데이터 파이프라인을 매장 현장에서 돌리는 장치**입니다.

### 비용 시뮬레이션 (FASHN 기준)

파일럿 1개 지점, 판매원이 하루 고객 10명 × 옷 3벌 = 30회/일 → **월 ~900회 = 약 $67 (on-demand)**. 옷 3벌을 입혀보는 데 $0.22 — 의류 한 벌 마진 대비 무시 가능한 수준입니다. 4개 매장 전체 확대 시 월 ~3,600회 → Tier II($249/월, 4,150크레딧)로 커버됩니다. 실패 시에도 매몰 비용이 거의 없습니다(최소 구매 $7.50부터 시작 가능).

### 추천: FASHN.ai 단일 어댑터로 시작

이유 세 가지입니다. 첫째, PoC 주석에 이미 "실제 API는 FASHN.ai 어댑터 교체만"이라고 설계 의도가 박혀 있어 구현이 하루 안에 끝납니다. 둘째, **flat-lay 지원**이 결정적입니다 — 카탈로그 이미지가 없는 461개 상품도 판매원이 그 자리에서 옷을 펼쳐 찍으면 즉시 피팅이 됩니다(이미지 부재 병목의 현장 우회). 셋째, TryOnProvider 추상화 덕분에 나중에 Gemini(더 싸게)나 Kling으로 갈아타는 비용이 0에 가깝습니다. 지금은 벤더 선택에 시간을 쓸 이유가 없습니다.

## 3. 시스템 아키텍처

```
[판매원 Flutter 앱 (mobile-sales-app)]
  ├── "Prueba Virtual" 화면
  │     1. 고객 동의 화면 (스페인어 안내 + 탭 동의)
  │     2. 고객 사진 촬영 → 앱 메모리(세션)에만 유지
  │     3. 옷 선택: 바코드 스캔 / 상품 검색 / 없으면 "옷 직접 촬영"(flat-lay)
  │     4. 결과 표시 (~5-10초, 여러 벌 병렬 요청)
  │     5. [옵션] WhatsApp 공유 (고객 동의 시)
  │
  ├── 인증: x-device-key + x-seller-id (vendedor 인증 전환 SPEC과 동일 모델)
  ▼
[api-ventago /vendedor/tryon]  ← 기존 src/app/tryon/ 재사용
  ├── VendedorTryOnController (신규) — DeviceGuard 적용
  ├── ShopTryOnService 재사용 (productId → MinIO garment)
  │     + tryOnFromUpload (flat-lay 직접 업로드 경로 추가)
  ├── FashnTryOnProvider (신규 어댑터) ← TRYON_PROVIDER DI 교체 (env 선택)
  ├── tryon_events 테이블 (신규): seller_id, product_id, created_at
  │     — 사진 저장 X, "무엇을 입혀봤나" 이벤트만 기록 (구매 의도 데이터)
  └── 레이트리밋: 기기당 동시 2건 / 일일 한도 (비용 폭주 방지)
```

### Pool / 성능 관점 (중요)

외부 API 호출이 5~10초 걸리지만 **DB 커넥션은 잡지 않습니다**. 현재 `ShopTryOnService` 구조가 이미 올바릅니다: `Product.findOne()`이 완료되어 커넥션이 pool에 반환된 **후에** `provider.tryOn()`(순수 HTTP)이 실행됩니다. FASHN 어댑터도 같은 원칙 — 트랜잭션/커넥션 보유 상태에서 외부 호출 금지. tryon_events 기록은 외부 호출 완료 후 단건 INSERT로 처리합니다. 따라서 pool(min 10/max 80)에 추가 부담이 없습니다.

### 프라이버시 / 동의 (아르헨티나 Ley 25.326)

고객 얼굴 사진은 개인정보입니다. 원칙은 PoC와 동일하게 **무저장**: 사진은 서버 메모리에서 FASHN으로 중계 후 즉시 폐기, 결과는 data URL로 반환. WhatsApp 공유가 필요할 때만 MinIO에 TTL 24시간 임시 저장(자동 삭제 스케줄러 — @nestjs/schedule 기존 인프라 활용). 앱에는 동의 화면 필수: "Su foto se usa solo para la prueba virtual y no se guarda"(사진은 가상 피팅에만 사용되며 저장되지 않습니다) + 동의 탭 기록(타임스탬프만). FASHN 측 데이터 보존 정책도 계약 전 확인 항목입니다.

### 카탈로그 이미지 축적 루프 (본질 대응)

판매원이 flat-lay로 찍은 옷 사진이 괜찮으면 → "이 사진을 상품 이미지로 등록할까요?" 원탭 제안 → MinIO 업로드 + `products.image_urls` 등록. 피팅을 쓸수록 461개의 이미지 공백이 현장에서 메워지고, 이는 그대로 Phase 51 공개몰의 자산이 됩니다.

## 5. 빠지기 쉬운 함정 3가지

**함정 1 — 벤더 선택에 시간을 쓰는 것.** 진짜 병목은 이미 Wave49-01에서 판명됐습니다: 옷 이미지 부재(483중 22). 추상화가 있으므로 벤더는 언제든 바꿀 수 있지만, 이미지 없는 카탈로그는 어떤 벤더로도 못 삽니다. flat-lay 현장 촬영 + 카탈로그 등록 루프가 API 선택보다 중요합니다.

**함정 2 — 고객 사진을 저장하고 싶어지는 유혹.** "다음 방문 때 재사용하자", "마케팅에 쓰자"는 요구가 반드시 나옵니다. 얼굴 사진 보관은 법적 리스크(Ley 25.326)와 신뢰 리스크를 동시에 집니다. 무저장 원칙이 오히려 판매 멘트가 됩니다: "사진은 저장 안 됩니다, 지금 보기만 하는 거예요" — 동의율을 올리는 장치입니다.

**함정 3 — 품질 기대치 관리 실패.** VTO는 프린트·로고가 왜곡될 수 있고 바지/신발은 상의보다 약합니다. 고객에게 "정확한 착용샷"이 아니라 **"분위기 미리보기(así te quedaría)"**로 포지셔닝해야 합니다. 판매원 교육 문구 한 줄이 클레임을 예방합니다. 부수 함정: 판매원의 재미 삼아 남용 → 일일 한도로 비용 상한을 코드에 박아두세요.

## 7. 기능 2 — 사진 1장으로 매장 재고 중 어울리는 옷 추천 (AI 스타일리스트)

결론: **만들 수 있고, 기능 1보다 오히려 싸고 빠릅니다.** 단, 가상 피팅 AI(FASHN)로 푸는 문제가 아닙니다. VTO는 "이 옷을 입히면 어떻게 보이나"(렌더링)이고, 추천은 "어떤 옷을 입혀볼 것인가"(선별)입니다. 선별은 비전 LLM + 카탈로그 메타데이터 매칭으로 풀고, 선별된 3~5벌을 기능 1(VTO)에 넘겨 시각화하는 **2단 파이프라인**이 정답입니다. 같은 고객 사진 1장을 두 기능이 공유합니다.

### 다층 구조

표면적으로는 "사진 → 추천"이라는 AI 문제로 보이지만, 구조적으로는 **매칭 대상인 카탈로그에 속성 데이터가 없다**는 문제입니다(색·핏·격식도·계절감 태그가 상품에 없음). 본질적으로 이 기능은 판매원 개개인의 스타일링 감각(암묵지)을 시스템의 형식지로 바꾸는 것이고, 그 부산물인 "고객 유형 × 추천 × 구매 여부" 데이터는 로드맵 ②(AI 추천)의 학습 데이터 그 자체가 됩니다.

### 아키텍처 (3단계)

**0단계 — 카탈로그 속성 태깅 (일회성 배치 + 신규상품 훅).** 각 상품의 이미지+이름+카테고리를 비전 LLM(Gemini 3 Flash, 입력 ~$0.50/1M 토큰)에 넣어 구조화 태그 추출: 카테고리, 주색상, 패턴, 핏(slim/regular/oversize), 격식도, 계절, 스타일 무드(casual/elegante/urbano…), 어울리는 체형 힌트. 결과는 `products.ai_attributes`(JSONB) 저장. **483개 전체 태깅 비용 ≈ $1 미만.** 이미지 없는 상품은 텍스트만으로 부분 태깅(기능 1의 flat-lay 촬영 루프가 채워줄수록 정확해짐).

**1단계 — 고객 사진 분석 (사진 1장, ~3초, <$0.01).** 판매원이 찍은 사진 1장을 비전 LLM에 → 구조화 프로필 추출: 체형 실루엣, 퍼스널컬러 계열(피부·모발 톤), 현재 착장 스타일, 추정 무드. **프로필은 세션 메모리에만 — DB 저장 금지**(체형·피부톤은 민감 정보, 무저장 원칙 동일 적용).

**2단계 — 매칭 + 리랭크 (~2초).** ① SQL 필터: 해당 지점 재고 있는 상품 중(`ProductBranch`, 단 재고 0 차단은 금지 — 기존 정책대로 표시만) 사이즈·카테고리·계절 후보 20~30개 추출. ② 후보의 ai_attributes + 고객 프로필을 텍스트로 LLM에 → 상위 5벌 + **스페인어 추천 멘트**("Este verde le va a resaltar el tono de piel") 생성. 판매원이 고객에게 그대로 읽어줄 수 있는 판매 스크립트가 됩니다. ③ 탭하면 기능 1 VTO로 즉시 렌더.

### 비용·속도 요약

| 항목 | 비용 | 속도 |
|---|---|---|
| 카탈로그 태깅(483개, 일회성) | < $1 | 배치 수 분 |
| 고객 1명 추천 세션(분석+리랭크) | $0.005~0.02 | 5초 내외 |
| + 추천 5벌 중 3벌 VTO 렌더(선택) | $0.22 | 벌당 5~10초 |

고객 1명 풀코스(추천+피팅 3벌)가 **$0.25 미만**입니다. 임베딩(pgvector) 방식은 SKU 수천 개 규모부터 의미가 있으므로 지금(매장당 ~500 SKU)은 LLM 리랭크만으로 충분하고, 나중에 갈아탈 때도 0단계 태그 자산은 그대로 재사용됩니다.

### 구현 순서 (기능 1 위에 +3~4일)

1. (0.5일) 태깅 프롬프트 설계 + 20개 상품 수동 검증 → 2. (1일) `ai-catalog-tagger` 배치 + `products.ai_attributes` JSONB 마이그레이션(ALTER OWNER 규칙 동일) + 신규상품 저장 훅 → 3. (1일) `/vendedor/stylist` 엔드포인트(사진 분석→필터→리랭크, StylistProvider 추상화로 LLM 벤더 격리) → 4. (1일) Flutter 화면: 기능 1 촬영 화면에서 "Recomendar looks" 버튼 하나로 진입, 추천 카드 → 탭 → VTO.

### 추가 함정 2가지

**체형 언급 방식** — 결과 화면·멘트에 "체형: 통통" 같은 분석 노출 금지. 오직 긍정형 추천 이유만("이 핏이 잘 어울려요"). 프롬프트 단계에서 출력 형식을 강제해야 합니다. **재고 필터 누락** — 다른 지점에만 있는 옷을 추천하면 판매원 신뢰를 즉시 잃습니다. branch 단위 필터가 1순위 조건입니다(단, 기존 정책상 재고 0이어도 차단은 하지 않고 "다른 지점 재고" 표시).

### 점검 포인트 (기능 2)

1주: 태깅 품질 샘플 검수(20개 수동 대조), 추천 5벌 중 판매원이 "말 되네" 하는 비율. 1개월: 추천 → VTO 실행률, 추천 경유 구매 전환율 vs 일반 구매. 3개월: tryon_events + 추천 로그로 자체 랭킹 개선(어떤 태그 조합이 실제 구매로 이어졌나), Phase 51 공개몰 "Te recomendamos" 재사용.
