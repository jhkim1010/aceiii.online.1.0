i
왜 Seña 와 Favor 를 분리하나? (DB 는 항상 분리)
Seña 는 venta 가 취소되면 환불 의무가 명확하고, Favor 는 손님이 그냥 미리 맡긴 돈이라 다음 매출 어디든 적용 가능합니다. 합치면 분쟁/세무에서 구분 어려움. balance, senia_balance, favor_balance 모두 0 이상.
UI 모드는 매장 단위 선택 · separated(기본·가구/전자/도매) ↔ unified(의류/식료품/키오스코). 헤더 토글로 전환해보세요.

핵심 운용 흐름

5 patrones
A
외상 매출 (Venta a crédito)
고객이 물건을 가져가고 결제는 나중에. balance +증가, sale_credit ledger 기록.
※ DNI/CUIT 미등록 고객은 외상 불가 (시스템 차단).
B
외상 분할 입금 (Pago parcial)
손님이 N번에 나눠 입금. FIFO 로 가장 오래된 sale_credit 부터 차감, 잔여는 favor 로.
C
Seña — 예약금 입금 (특정 venta)
손님 "이 물건 잡아주세요, 일부 미리 낼게요" → sale 생성(DRAFT) + senia_in ledger.
senia_balance +증가, sale_id 필수. sale_senias 1행 생성.
D
Seña 흡수 / 환불 / 전환 (venta 확정 또는 취소)
• 확정: senia_apply 로 매출 일부 흡수 → 잔여는 favor 로 자동 전환
• 취소+환불: senia_refund 현금 출금
• 취소+favor 전환: senia_to_favor + favor_in 짝
E
Favor 사용 — 구입자 명시적 선택 (자동 차감 ✕)
favor_balance > 0 이면 결제 모달에 알림 박스만 표시. 손님이 "이번에 favor 쓸게요" 라고 결정 → 점원이 [Usar favor] 클릭해야 적용 (favor_apply). 사용 안 하면 favor 그대로 보존.
※ 손님 자산이므로 자동 차감 금지 — 분쟁 예방.
버킷 → balance 부호 규칙 (개정)
• balance: 외상만, 항상 ≥ 0
• senia_balance: 예약금만, 항상 ≥ 0, sale 별 추적
• favor_balance: 자유 잔액만, 항상 ≥ 0
※ 음수 balance 사용 폐지. 기존 store_clients.balance < 0 행은 favor_balance 로 마이그레이션.
