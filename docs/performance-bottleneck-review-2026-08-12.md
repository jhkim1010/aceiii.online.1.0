# Ventago 성능 병목 검토 보고서

- 검토일: 2026-08-12
- 검토 방식: 소스 코드 기반 정적 검토
- 성능 목표: 사이드바 클릭부터 렌더 완료까지 P95 300ms 이하, DB 쿼리 100ms 이상은 최적화 대상
- 제한 사항: 운영 데이터베이스 연결 및 실제 부하 테스트는 수행하지 않았다. 따라서 실제 P95, 쿼리 실행시간 및 pool 포화 여부는 별도 계측이 필요하다.

## 결론

현재 코드에는 병목 가능성이 높은 경로 2곳과 중간 위험 경로 2곳이 남아 있다.

우선순위는 다음과 같다.

1. 대량 가격 변경
2. 상품 가져오기
3. 변형 재고 편집
4. 재고 리포트 내보내기

## 발견 사항

### [HIGH] 대량 상품 가져오기가 하나의 긴 트랜잭션에서 순차 실행됨

- 파일: `api-ventago/src/app/import/import.service.ts:54`
- 관련 DTO: `api-ventago/src/app/import/dto/import-migrate.dto.ts:119`

문제:

카테고리, 색상, 사이즈, 부모 상품 및 변형 상품을 모두 하나의 트랜잭션에서 한 건씩 처리한다. 데이터가 많으면 DB 커넥션 하나를 장시간 점유하여 동시 POS 요청이 pool 대기에 빠질 수 있다.

근거:

`for` 루프 내부에서 `findOrCreate`, `findOne`, `create`를 모두 `await`로 순차 실행한다. 대략 `C + S + Z + 2P + 2V`회 이상의 쿼리가 발생한다. DTO 배열에도 `@ArrayMaxSize` 제한이 없다.

수정 방향:

- 입력 배열에 안전한 최대 크기를 설정한다.
- 기존 레코드를 종류별로 한 번에 조회하여 메모리 맵으로 만든다.
- 100~500건 단위로 `bulkCreate` 또는 upsert를 수행한다.
- 전체 작업 동안 하나의 트랜잭션을 유지하지 않고 배치별 커밋과 재시작 가능한 작업 상태를 도입한다.

### [HIGH] 일괄 가격 변경이 상품 × 변형 × 가격유형만큼 쿼리를 증가시킴

- 파일: `api-ventago/src/app/products/productsPrice.service.ts:443`
- 컨트롤러: `api-ventago/src/app/products/products.controller.ts:436`

문제:

요청 상품마다 자식 상품을 다시 조회하고, 각 대상과 가격유형마다 `findOne` 후 `update` 또는 `create`를 순차 실행한다.

근거:

부모가 `N`개, 부모당 변형이 `V`개, 가격유형이 `T`개라면 약 `N + 2 × N × (V + 1) × T` 쿼리까지 증가할 수 있다. 예를 들어 부모 50개, 변형 20개, 가격유형 3개라면 가격 레코드 처리만 약 6,300회가 된다. 컨트롤러도 요청 배열의 최대 크기를 제한하지 않는다.

수정 방향:

- 모든 자식 상품을 한 번에 조회한다.
- 기존 가격을 `(product_id, price_type_id)` 기준으로 한 번에 조회한다.
- 변경 가격을 bulk upsert한다.
- 요청 상품 수와 가격유형 수에 상한을 둔다.

### [MEDIUM] 변형 편집 트랜잭션에서 지점 수에 비례하는 순차 쿼리 발생

- 파일: `api-ventago/src/app/products/productStock.service.ts:2196`
- 새 변형 처리: `api-ventago/src/app/products/productStock.service.ts:2325`

문제:

변형 수정 전체를 하나의 트랜잭션으로 묶은 것은 데이터 정확성에는 도움이 되지만, `updateVariants × branchIds`마다 `findOrCreate`가 실행되고 새 변형도 지점별로 링크와 재고를 순차 생성한다.

근거:

수정 대상이 `U`, 추가 대상이 `A`, 지점 수가 `B`이면 최소 `U × B + 2A × B`회 수준의 쓰기 쿼리가 트랜잭션 안에서 발생한다. 변형별 색상 및 사이즈 조회도 반복된다.

수정 방향:

- 기존 `ProductBranch`를 조합 키로 일괄 조회한다.
- 누락된 링크만 bulk insert한다.
- 색상과 사이즈를 트랜잭션 시작 전에 한 번에 조회한다.
- 재고 원장 행도 안전한 범위에서 묶음 삽입한다.

### [MEDIUM] 재고 Excel 내보내기가 무거운 리포트 쿼리를 최대 40회 반복함

- 파일: `api-ventago/src/app/reports/reportsStocks.service.ts:100`

문제:

500행씩 최대 20,000행을 순차 조회하므로 최대 40페이지를 실행한다. 각 페이지에서 목록뿐 아니라 전체 `count`까지 다시 계산하면 동일한 고비용 집계를 반복하게 된다.

근거:

`EXPORT_PAGE_SIZE=500`, `EXPORT_MAX_ROWS=20000`이며 각 반복에서 `getItems()`를 호출한다. 실제 데이터량과 실행계획에 따라 쿼리 100ms 기준을 넘는지는 확인이 필요하다.

수정 방향:

- 전체 count는 첫 페이지에서 한 번만 계산하고 이후 페이지에서는 생략한다.
- offset 페이지네이션 대신 cursor 또는 keyset 페이지네이션을 검토한다.
- 대규모 내보내기는 서버 측 stream 또는 비동기 export 작업으로 분리한다.
- 운영과 유사한 데이터에서 `EXPLAIN (ANALYZE, BUFFERS)`로 핵심 집계 쿼리를 측정한다.

## 이미 보완된 항목

- 공개 쇼핑몰 전용 DB pool 분리가 적용되어 있다.
- 다중 서버의 cron 중복 실행이 DB lease 방식으로 보완되어 있다.
- 판매 생성 시 상품별 재고검증 N+1이 `ANY(array)` 일괄 조회와 정렬 잠금 방식으로 개선되어 있다.
- `sync_outbox`에 `(status, next_retry_at) WHERE status='pending'` 부분 인덱스가 존재한다.
- 이번 정적 검토 범위에서는 명백한 PostgreSQL pool 반환 누수나 트랜잭션 내부 외부 HTTP 호출이 확인되지 않았다.

## 추가 검증 권장 사항

정적 검토만으로 실제 병목을 확정할 수 없으므로 다음 계측이 필요하다.

1. 각 사이드바 모듈 API의 P50, P95, P99 응답시간을 기록한다.
2. 100ms 이상 DB 쿼리의 SQL, 호출 경로, 실행계획을 수집한다.
3. 동시 요청 중 Sequelize pool의 사용 중, 대기 중, 유휴 커넥션 수를 관찰한다.
4. 대량 가격 변경과 상품 가져오기에 현실적인 최대 크기의 테스트 데이터를 사용한다.
5. 테스트 중 다른 계산대의 판매 및 재고 API가 P95 300ms를 유지하는지 함께 검증한다.
