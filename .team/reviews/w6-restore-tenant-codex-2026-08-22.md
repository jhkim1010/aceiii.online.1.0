- ⑤ MP: 환불·이동·이체 기록은 회계 이력이므로 **재해복구에는 포함**, 신규 매장 복제에는 제외한다. 복원 후 계정은 비활성화하고 재인증 전 결제 동작을 금지한다.
- ⑥: 실제 관계라면 FK 추가에 동의. FK 없는 관계를 찾기 위해 `*_id` 컬럼도 전수 분류 대상으로 강제해야 한다.

또한 문서의 ②는 제목상 “6개”지만 실제 열거는 9개, ③은 “4개”지만 5개다. 기준선 생성 시 수동 개수 표기는 자동 검증해야 한다.

4. ID 재매핑과 ID 보존

결론: **별도 실행 경로로 분리해야 한다. 공통 라이브러리는 가능하지만 하나의 모드 플래그로 합치면 안 된다.**

- `clone`: 새 `store_id`, PK 재매핑, 전역 참조만 KEEP.
- `in-place recovery`: 동일 매장·동일 ID, 기존 데이터 제거/대체 정책과 시퀀스 재조정.
- 둘은 허용되는 테이블, 충돌 의미, 자격증명·회계 이력 정책이 다르다.

한 엔진의 `mode` 분기는 ID 보존 경로가 실수로 복제에 사용되는 위험이 가장 크다. API, 권한, manifest, 검증 절차를 분리하고 FK 정렬·bulk insert·검증 코드만 공유하는 것이 안전하다.

5. `role_function_actions` 40,557행 백업 주의점

결론: **역할 ID만 재매핑하고, 전역 `function_action` ID는 KEEP해야 한다. 복원 완전성을 행 수가 아니라 집합으로 검증해야 한다.**

- 일관된 스냅샷에서 roles와 함께 백업.
- 자연키/유일 제약으로 중복 삽입 방지.
- `(old_role_id → new_role_id)` 누락 시 즉시 실패.
- 대상 `function_action`이 현재 스키마에 없으면 조용히 버리지 말고 전체 롤백.
- 역할별 액션 집합의 count와 checksum을 복원 전후 비교.
- diff 저장 최적화와 백업 의미를 섞지 않는다. 백업은 특정 시점의 **완전한 권한 집합**이어야 한다.
- 감사 트리거로 40,557건의 무의미한 이벤트가 생기지 않도록 “복원 작업”으로 식별하되, 감사 자체를 무권한으로 끌 수 있게 해서는 안 된다.

6. 놓친 것과 최종 보장 조건

결론: **D1~D6만으로는 “절대”를 말할 수 없다. D2는 특히 수정해야 한다.**

- D2의 런타임 `information_schema` 기반 완전 제네릭 복원에는 반대한다. FK 순환, 트리거, 파생 테이블, 조건부 유일성, 업무상 전역 관계를 FK만으로 판별할 수 없다. **버전 관리되는 명시적 manifest를 권위로 두고, DB 메타데이터는 manifest 누락을 검증**해야 한다.
- 백업 파일에 스키마 버전, 테이블별 count/checksum, 생성 시점, 원본 `store_id`, manifest 버전과 서명을 넣는다.
- 복원 대상이 비어 있거나 해당 원본 매장임을 검증한다. 목적지 `store_id`를 요청값이 아니라 복원 컨텍스트 하나에서만 주입한다.
- 커밋 전 모든 FK 검증, 테넌트 불변식 검사, count/checksum 검사를 수행한다.
- D5는 “테이블 전체 복원 불가”보다 **비밀값만 제외하고 비활성 상태로 복원 후 재인증**이 적절하다.
- D6 단일 트랜잭션에 동의한다. 외부 HTTP·프린터·소켓 호출은 트랜잭션 밖에서 수행해야 한다.
- 복원 DB 계정에는 제약 우회, 트리거 비활성화, superuser 권한을 주지 않는다.
- 실제 혼입 시 반드시 실패하는 adversarial 테스트를 둔다: 남의 상품·결제수단·역할·지점·에이전트 ID를 백업에 주입해 DB가 거부하는지 확인한다.

따라서 최종 구조는 **전 테이블 명시 분류 + 분리된 복제/제자리복구 manifest + DB 복합 FK 강제 + D3 + 트랜잭션 내 D4 + 권한 최소화**다. 이 정도가 되어야 애플리케이션 버그 하나가 생겨도 다른 매장 데이터가 커밋되지 않는다고 말할 수 있다.

## 1. D3과 D4 중 무엇을 선택해야 하는가

결론: 둘 다 필요하며, 하나만 고른다면 D3입니다. 다만 최종 구조는 `D3 + DB 제약 + D4`여야 합니다.

D3는 복원 엔진이 알지 못하는 FK를 그대로 통과시키지 못하게 만드는 기본 강제 지점입니다. 현재 복원은 `sale_items`와 `sale_payment_methods`에서 부모 판매 ID만 바꾸고 나머지 FK를 그대로 펼칩니다.

- [store.service.ts:1762](/Users/marcoskim/TrabajoProgramming/aceiii.online.1.0/api-ventago/src/app/store/store.service.ts:1762): `itemFields` 전체를 그대로 복사
- [store.service.ts:1777](/Users/marcoskim/TrabajoProgramming/aceiii.online.1.0/api-ventago/src/app/store/store.service.ts:1777): `pmFields` 전체를 그대로 복사
- [store.service.ts:1752](/Users/marcoskim/TrabajoProgramming/aceiii.online.1.0/api-ventago/src/app/store/store.service.ts:1752): 판매 자체도 `storeId`, `userId`, `sellerId` 외 FK는 그대로 유지

따라서 모든 FK가 다음 중 하나로 선언되지 않으면 백업 생성과 복원을 모두 거부해야 합니다.

- `REMAP`: 같은 복원 단위에서 복제되는 테넌트 엔티티
- `KEEP_GLOBAL`: 명시적으로 분류된 전역 엔티티
- `CLEAR`: 선택적 관계이며 복원 후 재설정
- `REJECT`: 값이 존재하면 해당 복원 모드 자체를 거부

제안된 `NULL`이라는 이름보다는 `CLEAR`가 낫습니다. 실제 컬럼이 `NOT NULL`이거나 관계가 업무상 필수이면 NULL 처리할 수 없기 때문입니다.

D4만으로는 검사 목록 자체가 누락될 수 있고, 검사 구현에 없는 새로운 FK는 그대로 통과합니다. 반대로 D3만으로도 선언 실수, SQL 버그, 트리거 부작용은 남습니다. D4는 선언에서 자동 생성해야 하며 사람이 별도 SQL 목록을 관리하면 안 됩니다.

권장 강제 순서는 다음입니다.

`선언 완전성 검사 → DB 제약 → 트랜잭션 내 전수 불변식 검사 → COMMIT`

DB 제약이 없는 관계까지 포함한 D4 결과가 0행일 때만 커밋해야 합니다.

## 2. D4를 DB 제약으로 올릴 수 있는가

결론: 주요 업무 FK에는 올려야 합니다. DB가 강제하는 `store_id`는 이전의 잘못된 비정규화와 성격이 다르지만, 그 컬럼 자체를 소유권의 권위로 삼으면 다시 같은 함정입니다.

예시의 복합 FK 방식은 유효합니다.

```sql
UNIQUE (id, store_id)

FOREIGN KEY (product_id, store_id)
REFERENCES products (id, store_id)
```

여기서 `store_id`는 소유권을 판정하는 독립 권위가 아니라, 부모 관계와 일치해야 하는 “테넌트 증명값”입니다. 다음 조건이 필요합니다.

- 자식의 `store_id`를 호출자가 자유롭게 정하지 못하게 한다.
- INSERT 시 부모에서 채우거나, 호출값과 부모값이 같은지 DB가 검사한다.
- FK 관계가 존재하는 동안 `store_id` 변경을 금지하거나 연쇄적으로 안전하게 처리한다.
- 가능하면 `store_id NOT NULL`로 하여 NULL이 복합 FK 검사를 우회하지 못하게 한다.
- 부모에 `(id, store_id)` UNIQUE 제약이 있어야 한다.

전 테이블을 한 번에 바꾸는 것은 권하지 않습니다. 우선 사고 시 타 매장 데이터 노출·변조로 직결되는 관계부터 적용해야 합니다.

- 판매 품목 → 상품·프로모션
- 판매 결제 → 결제수단·옵션
- 판매 → 매장 고객·판매자·온라인 주문·테이블
- 단말 → 지점 에이전트
- 사용자/금전함 → 지점·역할 관계

정확한 대상 테이블 수와 잠금 비용은 현재 제공된 운영 스키마 덤프 없이 단정할 수 없습니다. 최소 13개 문제 FK에 자식 테넌트 컬럼, 부모 복합 UNIQUE, 백필, 검증, FK 추가가 필요합니다. 큰 테이블에서는 다음 단계로 나눠야 합니다.

1. nullable 컬럼 추가
2. 배치 백필
3. 불일치 0건 확인
4. `NOT VALID` FK 추가
5. `VALIDATE CONSTRAINT`
6. NOT NULL 전환

PostgreSQL 10 호환성을 고려하면 최신 버전 전용 기능을 전제로 하면 안 됩니다.

모든 관계를 복합 FK로 표현할 수는 없습니다. 여러 단계를 거친 소유권, 다형 관계, FK가 없는 레거시 테이블에는 제약 또는 트리거가 추가로 필요합니다. RLS만으로는 FK 테넌트 일치를 완전하게 대체하지 못합니다.

## 4. ID 재매핑과 ID 보존

결론: 공통 계획기와 검증기는 공유하되, 실행기는 두 모드로 분리해야 합니다. 하나의 범용 INSERT 루프에 플래그만 두는 설계에는 반대합니다.

두 작업은 의미가 다릅니다.

- `CLONE`: 새로운 매장 생성, PK 재매핑, 외부 자격증명 제거, 전역 참조 재검증
- `IN_PLACE_RECOVERY`: 동일 매장의 특정 시점 복구, ID 보존, 기존 데이터와의 충돌·삭제 범위 통제, 원장 보정

공유할 수 있는 것은 다음입니다.

- 스키마/매니페스트 로딩
- 백업 형식 검증
- 테이블 의존 순서
- 컬럼 허용 목록
- FK 정책 완전성 검사
- 커밋 전 불변식 검사
- 복원 결과 대조

공유하면 안 되는 것은 다음입니다.

- PK 생성 전략
- 기존 행 삭제/병합 전략
- 전역 참조 처리
- 외부 연동 및 자격증명 처리
- append-only 원장 처리
- 시퀀스 조정
- 충돌 의미

한 실행기에 `preserveIds: boolean` 같은 분기만 두면 ID 보존 모드에서 시퀀스 보정 누락, 복제 모드에서 FK 원 ID 잔존 같은 치명적 오류가 생깁니다. 특히 제자리 복구의 `stocks` 반대 부호 보정 행 추가는 일반적인 ID 보존 INSERT가 아니므로 이미 별도 의미를 가집니다.

백업 파일에도 목적을 고정해야 합니다. `backupPurpose: "clone" | "disaster-recovery"`와 스키마 버전을 넣고, 다른 목적의 엔진이 읽으면 거부하는 편이 안전합니다.

## 5. `role_function_actions` 40,557행 복원 시 주의점

결론: 반드시 포함하되, 행별 ORM INSERT가 아니라 검증된 일괄 적재로 처리하고 감사 트리거 폭증과 권한 캐시 재생성을 통제해야 합니다.

핵심 사항은 다음과 같습니다.

- `roles → role_functions → role_function_actions` 순서로 각각 ID를 재매핑해야 합니다.
- `function_id` 및 action 값은 전역 권한 정의에 대한 `KEEP_GLOBAL`인지 명시하고, 존재와 허용 action을 검사해야 합니다.
- `(role_function_id, action)` UNIQUE 위반을 백업 사전 검사에서 잡아야 합니다.
- 원본 역할별 action 개수와 복원 결과 개수를 대조해야 합니다.
- 권한 캐시는 복원하지 말고 커밋 후 새 원본에서 재생성해야 합니다.
- 40,557번 순차 `await`는 허용하면 안 됩니다. 배치 INSERT 또는 PostgreSQL COPY 수준의 적재가 필요합니다.
- 현재 감사 트리거가 모든 INSERT를 기록하므로 복원만으로 40,557개 이상의 감사행이 만들어질 수 있습니다. 복원된 과거 `audit_logs`와 새 복원 감사가 섞이는 문제도 생깁니다.

`session_replication_role`로 트리거를 일괄 끄는 것은 FK까지 무력화할 수 있으므로 권하지 않습니다. 감사 트리거가 복원 세션 식별자를 읽어 “복원 작업 1건 + 요약/manifest hash”로 기록하거나, 복원 전용 DB 함수를 통해 필요한 감사 정책만 적용하는 구조가 안전합니다.

복원 후 최소 검증값은 다음과 같습니다.

- 역할 수
- 역할별 기능 수
- 역할별 action 집합 또는 정렬된 해시
- 고아 `role_function_actions` 0건
- 타 매장 `role_functions` 참조 0건

- `REMAP`: 같은 복원 단위에서 복제되는 테넌트 엔티티
- `KEEP_GLOBAL`: 명시적으로 분류된 전역 엔티티
- `CLEAR`: 선택적 관계이며 복원 후 재설정
- `REJECT`: 값이 존재하면 해당 복원 모드 자체를 거부

제안된 `NULL`이라는 이름보다는 `CLEAR`가 낫습니다. 실제 컬럼이 `NOT NULL`이거나 관계가 업무상 필수이면 NULL 처리할 수 없기 때문입니다.

D4만으로는 검사 목록 자체가 누락될 수 있고, 검사 구현에 없는 새로운 FK는 그대로 통과합니다. 반대로 D3만으로도 선언 실수, SQL 버그, 트리거 부작용은 남습니다. D4는 선언에서 자동 생성해야 하며 사람이 별도 SQL 목록을 관리하면 안 됩니다.

권장 강제 순서는 다음입니다.

`선언 완전성 검사 → DB 제약 → 트랜잭션 내 전수 불변식 검사 → COMMIT`

DB 제약이 없는 관계까지 포함한 D4 결과가 0행일 때만 커밋해야 합니다.

## 2. D4를 DB 제약으로 올릴 수 있는가

결론: 주요 업무 FK에는 올려야 합니다. DB가 강제하는 `store_id`는 이전의 잘못된 비정규화와 성격이 다르지만, 그 컬럼 자체를 소유권의 권위로 삼으면 다시 같은 함정입니다.

예시의 복합 FK 방식은 유효합니다.

```sql
UNIQUE (id, store_id)

FOREIGN KEY (product_id, store_id)
REFERENCES products (id, store_id)
```

여기서 `store_id`는 소유권을 판정하는 독립 권위가 아니라, 부모 관계와 일치해야 하는 “테넌트 증명값”입니다. 다음 조건이 필요합니다.

- 자식의 `store_id`를 호출자가 자유롭게 정하지 못하게 한다.
- INSERT 시 부모에서 채우거나, 호출값과 부모값이 같은지 DB가 검사한다.
- FK 관계가 존재하는 동안 `store_id` 변경을 금지하거나 연쇄적으로 안전하게 처리한다.
- 가능하면 `store_id NOT NULL`로 하여 NULL이 복합 FK 검사를 우회하지 못하게 한다.
- 부모에 `(id, store_id)` UNIQUE 제약이 있어야 한다.

전 테이블을 한 번에 바꾸는 것은 권하지 않습니다. 우선 사고 시 타 매장 데이터 노출·변조로 직결되는 관계부터 적용해야 합니다.

- 판매 품목 → 상품·프로모션
- 판매 결제 → 결제수단·옵션
- 판매 → 매장 고객·판매자·온라인 주문·테이블
- 단말 → 지점 에이전트
- 사용자/금전함 → 지점·역할 관계

정확한 대상 테이블 수와 잠금 비용은 현재 제공된 운영 스키마 덤프 없이 단정할 수 없습니다. 최소 13개 문제 FK에 자식 테넌트 컬럼, 부모 복합 UNIQUE, 백필, 검증, FK 추가가 필요합니다. 큰 테이블에서는 다음 단계로 나눠야 합니다.

1. nullable 컬럼 추가
2. 배치 백필
3. 불일치 0건 확인
4. `NOT VALID` FK 추가
5. `VALIDATE CONSTRAINT`
6. NOT NULL 전환

PostgreSQL 10 호환성을 고려하면 최신 버전 전용 기능을 전제로 하면 안 됩니다.

모든 관계를 복합 FK로 표현할 수는 없습니다. 여러 단계를 거친 소유권, 다형 관계, FK가 없는 레거시 테이블에는 제약 또는 트리거가 추가로 필요합니다. RLS만으로는 FK 테넌트 일치를 완전하게 대체하지 못합니다.

## 4. ID 재매핑과 ID 보존

- `IN_PLACE_RECOVERY`: 동일 매장의 특정 시점 복구, ID 보존, 기존 데이터와의 충돌·삭제 범위 통제, 원장 보정

공유할 수 있는 것은 다음입니다.

- 스키마/매니페스트 로딩
- 백업 형식 검증
- 테이블 의존 순서
- 컬럼 허용 목록
- FK 정책 완전성 검사
- 커밋 전 불변식 검사
- 복원 결과 대조

공유하면 안 되는 것은 다음입니다.

- PK 생성 전략
- 기존 행 삭제/병합 전략
- 전역 참조 처리
- 외부 연동 및 자격증명 처리
- append-only 원장 처리
- 시퀀스 조정
- 충돌 의미

한 실행기에 `preserveIds: boolean` 같은 분기만 두면 ID 보존 모드에서 시퀀스 보정 누락, 복제 모드에서 FK 원 ID 잔존 같은 치명적 오류가 생깁니다. 특히 제자리 복구의 `stocks` 반대 부호 보정 행 추가는 일반적인 ID 보존 INSERT가 아니므로 이미 별도 의미를 가집니다.

백업 파일에도 목적을 고정해야 합니다. `backupPurpose: "clone" | "disaster-recovery"`와 스키마 버전을 넣고, 다른 목적의 엔진이 읽으면 거부하는 편이 안전합니다.

- 역할 수
- 역할별 기능 수
- 역할별 action 집합 또는 정렬된 해시
- 고아 `role_function_actions` 0건
- 타 매장 `role_functions` 참조 0건

### 현재 백업은 실패 폐쇄가 아님

[store.service.ts:1300](/Users/marcoskim/TrabajoProgramming/aceiii.online.1.0/api-ventago/src/app/store/store.service.ts:1300) 부근의 `fetchSimpleStoreTables()`는 읽기 실패를 `unreadable`에 적은 뒤 백업을 성공시킵니다. 이는 D6의 부분 복원 금지와 충돌합니다.

재해복구용 백업에서는 필수 테이블 하나라도 읽지 못하면 파일 생성 자체가 실패해야 합니다. 진단용 부분 스냅샷이 필요하다면 파일 형식을 별도로 두고 복원 엔진이 절대 받아들이지 않게 해야 합니다.

### D2 런타임 제네릭 엔진은 권위가 될 수 없음

런타임에 `information_schema`만 읽어 자동 결정하는 D2에는 반대합니다.

- FK는 소유권과 전역 참조를 구분하지 못합니다.
- FK 없는 관계를 놓칩니다.
- 순환 FK와 self-reference는 단순 위상 정렬이 불가능합니다.
- 다형 관계와 외부 식별자는 카탈로그에 의미가 없습니다.
- 스키마가 먼저 배포되고 코드가 뒤처지면 런타임에서 처음 사고를 발견합니다.

명시적이고 버전 관리되는 복원 매니페스트가 의미의 권위가 되고, DB 카탈로그는 매니페스트의 완전성과 실제 컬럼/FK 일치를 검증해야 합니다. 즉 D2는 “자동 결정 엔진”이 아니라 “선언 검증기와 실행 계획 생성기”로 축소해야 합니다.

### 백업 파일을 신뢰하면 안 됨

현재 `backupData: any`와 `...fields` 대입은 수정된 백업 JSON이 예상하지 않은 컬럼을 주입할 여지를 만듭니다. 복원 입력에는 다음이 필요합니다.

- 엄격한 JSON 스키마
- 백업 형식·DB 스키마 버전
- 테이블별 허용 컬럼 목록
- 알 수 없는 테이블·컬럼 거부
- 원본 store ID와 대상 모드 검증
- 파일 checksum/서명
- 백업 생성 완료 상태와 coverage hash
- 행 수와 부모-자식 해시
- 복원 전 원본 테넌트 불변식 검사

### “어떤 경로로도” 막으려면

다음 조건이 모두 충족되어야 “복원 경로뿐 아니라 어떤 쓰기 경로에서도 섞이지 않는다”고 말할 수 있습니다.

1. 모든 실테이블이 의미 기반 분류표에 정확히 하나의 분류를 가진다.
2. 모든 FK가 소유권/테넌트 참조/전역 참조/교차 테넌트 관계 중 하나로 선언된다.
3. 신규 테이블과 신규 FK가 미분류이면 CI가 실패한다.
4. 핵심 테넌트 관계는 DB 복합 FK 또는 동등한 제약으로 강제된다.
5. 앱의 D4 검사는 매니페스트에서 자동 생성되고 커밋 전에 실행된다.
6. 백업은 일관된 read-only 스냅샷이며 필수 데이터 누락 시 실패한다.
7. 복원은 목적별 별도 실행기를 사용하고 단일 트랜잭션으로 끝난다.
8. 커밋 후가 아니라 커밋 전에 행 수·FK·테넌트 불변식·권한 해시를 대조한다.
9. 복원 기능 자체에 동시 실행 잠금과 중복 실행 식별자가 있다.
10. 테스트가 단순 성공 여부가 아니라 의도적으로 다른 두 매장의 같은 형태 ID를 섞은 적대적 fixture를 사용한다.

최종적으로 D1~D6은 다음처럼 수정하는 것이 맞습니다.

- D1: 단순 FK 폐포가 아니라 전 테이블·전 FK 의미 매니페스트
- D2: 런타임 자동 판정이 아니라 매니페스트 기반 계획기 + DB 카탈로그 검증
- D3: 유지
- D4: 유지하되 매니페스트에서 자동 생성
- D5: 복원 모드별 `REAUTH/REJECT/CLEAR` 정책으로 확대
- D6: 유지하되 백업 생성 단계에도 동일하게 적용

이 구조에 핵심 관계의 DB 제약을 더해야 비로소 “애플리케이션의 특정 복원 코드가 실수해도 다른 매장 참조가 커밋되지 않는다”는 수준의 보장이 됩니다.
