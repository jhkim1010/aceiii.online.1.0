## ★ codex 가 반박한 것 — 둘 다 수용

### R1. D1(FK 도달 폐포를 소유권 권위로) — **반박 수용**

> "FK 자체는 '소유' 와 '참조' 를 구분하지 않는다. 권위는 전 테이블 매니페스트여야 한다."

맞다. 내 폐포는 `stores` 에서 자식 방향으로 퍼지는데, `global_categories.created_by_store_id
→ stores` 같은 FK 때문에 **교차 매장 레지스트리가 '매장 소유' 로 딸려 들어왔다.**
"누가 처음 만들었나" 를 "누구 것인가" 로 읽은 것이다 —
`store_id` 컬럼을 권위로 쓴 것과 **형태가 같은 실수**를 한 층 위에서 반복했다.

→ **폐포는 "빠진 것을 찾는 탐지기" 로만 쓰고, 분류의 권위는 매니페스트에 둔다.**
   테이블 분류 7종: `TENANT_OWNED` · `GLOBAL_SHARED` · `DERIVED` · `EPHEMERAL` ·
   `AUDIT_ARCHIVE` · `EXTERNAL_BOUND` · `LEGACY_UNCLASSIFIED`(있으면 테스트 실패)
   FK 분류 4종: `OWNERSHIP` · `TENANT_REFERENCE` · `GLOBAL_REFERENCE` · `CROSS_TENANT_RELATION`

### R2. D2(런타임 information_schema 제네릭 엔진) — **반박 수용**

> "FK 는 소유권과 전역 참조를 구분 못 하고, FK 없는 관계를 놓치고, 순환·다형을 못 푼다.
>  스키마가 먼저 배포되면 **런타임에서 처음 사고를 발견**한다."

마지막 문장이 결정적이다. 자동 판정은 **사고를 배포 이후로 미룬다.**
→ D2 를 "자동 결정 엔진" 이 아니라 **"매니페스트 검증기 + 실행계획 생성기"** 로 축소한다.
   DB 카탈로그는 매니페스트가 현재 스키마를 빠짐없이 덮는지 **검사하는 쪽**이다.

## ★★ codex 가 새로 찾은 것 — 내가 못 본 것 3개

### N1. 백업이 일관된 스냅샷이 아니다 (`store.service.ts:1168`)

`getStoreBackupData()` 는 트랜잭션 없이 ORM·raw 쿼리를 여러 번 던진다.
주석은 "단일 connection" 이라 적혀 있지만 `sequelize.query` 에 transaction 이 안 넘어간다.
→ **백업 도중 판매·상품·권한이 바뀌면 부모와 자식이 서로 다른 시점**이다.
   완벽한 복원 엔진을 만들어도 **입력이 이미 깨져 있다.**
→ 백업 전체를 하나의 `REPEATABLE READ` read-only 트랜잭션에 넣는다.

### N2. 백업이 fail-closed 가 아니다 (`fetchSimpleStoreTables`)

읽기 실패를 `unreadable` 에 적고 **백업을 성공시킨다.**
내가 W6-B 에서 "조용히 건너뛰지 않고 이름을 남긴다" 며 (다)를 골랐는데,
**재해복구용 백업에서는 그 선택이 틀렸다** — 필수 테이블이 빠진 파일이
"정상 백업" 으로 보관된다. 진단용 부분 스냅샷이 필요하면 **형식을 나누고
복원 엔진이 절대 안 받게** 해야 한다.

### N3. 백업 파일을 신뢰한다 (`backupData: any` + `...fields`)

수정된 JSON 이 **예상하지 않은 컬럼을 주입**할 수 있다. superadmin 전용이라도
파일은 외부에서 온다. → 테이블별 허용 컬럼 목록 · 알 수 없는 테이블/컬럼 거부 ·
형식 버전 · checksum · coverage hash.

## ★ codex 가 잡은 내 문서의 자기모순

> "②는 6이 아니라 9개, ③은 4가 아니라 5개, ④는 5가 아니라 6개"

맞다. **표 제목의 숫자와 표 안의 행 수가 어긋났다.**
2026-08-21 codex 지적 #4 가 정확히 이것이었다(*"SKU 대상 목록이 내 문서 안에서 자기모순"*).
**같은 실수를 하루 만에 반복했다.** → 숫자는 손으로 쓰지 않고 목록에서 세게 한다.

## 반박 — codex 가 틀린 것 1건

> "PostgreSQL 10 호환성을 고려하면 최신 버전 전용 기능을 전제로 하면 안 됩니다."

**틀렸다.** 2026-07-10 컷오버로 **로컬·운영 모두 PG18** 이다(CLAUDE.md 「DB 마이그레이션
적용 규칙」). 구 PG10(5433)은 롤백 안전망으로만 보존하며 신규 마이그레이션은 5434 전용이다.
codex 는 저장소의 옛 마이그레이션 주석(PG10 제약 회피)을 보고 현재로 오인했다.
→ PG18 문법을 제한 없이 쓴다.

## 보류 — 근거를 더 대야 하는 것 1건

> "정확한 대상 테이블 수와 잠금 비용은 운영 스키마 덤프 없이 단정할 수 없습니다."

잠금 비용은 **이미 쟀다** — `sales` 168행 · `sale_items` 685 · `stocks` 1,806
(2026-08-21 실측, 파티셔닝 보류 근거와 같은 값). 복합 FK 를 붙이기에 **지금이 가장 싸다.**
W4 의 "테이블이 작은 지금이 유일한 무통증 시점" 논지가 그대로 적용된다.

## 수용한 설계 (최종)

| | 내용 |
|---|---|
| **D1′** | 전 테이블 매니페스트(7분류) + 전 FK 매니페스트(4분류). FK 폐포는 **탐지기**로만. `LEGACY_UNCLASSIFIED` 존재 시 테스트 실패 |
| **D2′** | 런타임 자동 판정 폐기 → **매니페스트 기반 계획기 + DB 카탈로그 완전성 검증기** |
| **D3′** | FK 처리 선언: `REMAP` · `KEEP_GLOBAL` · `CLEAR` · **`REJECT`**. (`NULL` → `CLEAR` 개명 — NOT NULL 컬럼엔 NULL 을 못 넣는다) |
| **D4′** | 커밋 전 전수 불변식 검사. **매니페스트에서 자동 생성**(사람이 SQL 목록을 관리하면 갈라진다) |
| **D5′** | 자격증명은 모드별 `REAUTH`/`REJECT`/`CLEAR` |
| **D6′** | 단일 트랜잭션 — **백업 생성 단계에도 적용**(N1) |
| **+D7** | 핵심 13관계에 **DB 복합 FK** `(id, store_id)` UNIQUE + `(child_fk, store_id) REFERENCES parent(id, store_id)` |
| **+D8** | 실행기를 **모드별로 분리**: `CLONE` / `IN_PLACE_RECOVERY`. 공통은 계획기·검증기만. 백업 파일에 `backupPurpose` + 스키마 버전 |
| **+D9** | 백업 입력 검증 — 허용 컬럼 목록 · 미지 컬럼 거부 · checksum · coverage hash |

### 분류 수정 (codex Q3 반영)

- `branch_agents` · `branch_printer_configs` — 설정은 담되 **`api_key` 와 에이전트 신원은 재등록 대상**. 복제본이 기존 자격증명을 재사용하면 안 된다
- `campaign_recipients` — 발송 **대기 상태**가 섞여 있으면 복원 금지 (재발송 위험). 확인 필요
- `global_clients` — 무조건 `KEEP_GLOBAL` 이 아니다. **`owner_group_id` 범위**가 같은지 검사해야 한다. 다른 소유자 그룹으로 복제하면 KEEP 도 복제도 안 된다
- `mp_movements`·`mp_transfers`·`mp_refunds`·`mp_refund_attempts` — 테이블 단위 분류로 부족. **모드별**: `CLONE` 제외 / `IN_PLACE_RECOVERY` 포함 / `ARCHIVE` 별도
- 감사·접근 로그 — **"복원 안 함" 과 "백업 안 함" 은 다르다.** 보존은 하되 신규 매장의 활성 데이터로 되살리지 않는다
