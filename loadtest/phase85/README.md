# Phase 85 W1 — 캐시 봉인 검증 스크립트

2026-08-20 실행. 결과와 함정은 상위 `loadtest/README.md` 의
「실행 기록 (2026-08-20 밤 — Phase 85 W1 완결분 검증)」 절에 있다.

서버(`/tmp/`)에 scp 해서 쓴다. 대상은 `api_staging:5012` + `ventago_staging` 고정이다.

| 스크립트 | 무엇을 보는가 | 유의점 |
|---|---|---|
| `burst.sh` | **cold** 상태에서 동시 N 요청의 DB calls 증분 | 컨테이너를 2번 재시작한다(로그인이 남긴 캐시까지 제거). 이것이 stampede 의 정량 지표다 |
| `warm.sh` | **워밍 후** 동시 N 요청의 DB calls | "캐시가 붙어 있는가" 를 stampede 와 분리해서 본다. 워밍은 워커 수보다 넉넉히 |
| `fresh.sh` | 쓰기 후 **워커 간 무효화 전파**(Redis) | 단일 워커로는 절대 못 잡는다. 관리자 계정 필요(`ADMIN_EMAIL=`) |
| `churn.sh` | 배경 부하 중 쓰기 반복 — ack 후 낡은 응답 | ★ 이 시험은 **P1 경쟁에 민감하지 않다**(아래) |
| `kanban.sh` | 키 만드는 곳(dashboard) ↔ 지우는 곳(envio) 배선 | ★ 스테이징에 보드용 envío 데이터가 없어 **성립하지 않았다**(아래) |

## ★ 이 스크립트들이 증명하지 **못하는** 것

- `churn.sh` 는 "무효화 vs 진행 중 loader"(codex [P1])를 검증하지 **않는다.**
  수정 이전 이미지로 돌려도 똑같이 낡음 0 이 나온다 — loader 가 ~10ms 라 경쟁 창이 너무 좁다.
  그 결함의 검증은 `src/common/cache/memory-cache.spec.ts` 의 단위 spec 이 한다
  (해당 코드를 되돌리면 실제로 실패하는 것을 확인했다).
  **부하 시험을 새로 짜면 반드시 대조군(수정 이전 이미지)을 함께 돌릴 것.**
- `kanban.sh` 는 대상 envío 가 보드에 실제로 실릴 때만 의미가 있다. 2026-08-20 에는
  스테이징 envío 3건이 전부 `COMPLETED` 라 보드가 비어 있었고, 추출식이 `None` 을
  돌려주며 **아무것도 측정하지 않은 채 "불합격"** 을 찍었다. 실행 전에 보드가 비어 있지
  않은지 먼저 확인할 것. 배선 자체는
  `src/app/subcon/dashboard/dashboard-cache-key.spec.ts` 가 데이터 없이 고정한다.
